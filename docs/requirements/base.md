# 桃鉄の結果を記録し、集計するアプリケーションの要求仕様

毎週開催している深夜の桃鉄1年勝負の結果を記録し、後からCSV/TSVとして出力できるようにする。

本書は業務要求とMVP範囲の正本である。試合メモ固有の要求は `docs/requirements/match-note.md`、実装詳細、技術選定、検証コマンド、運用手順は `docs/requirements/system-design.md`、`docs/architecture.md`、`docs/domain-rule.md`、`docs/db-rule.md` を参照する。

---

## 1. 概要

- 操作はWeb上で行う。
- 仲間内だけで運用する。
- ログイン可能な利用者は `momo_login_accounts` で明示的に許可する。
- 試合参加者は summit アプリと共有する固定4名の `members` とする。
- ログインアカウントと試合参加者は別概念とする。`momo_login_accounts.player_member_id` がある場合だけ、ログインアカウントと `members` が紐づく。
- MVP では、画像取り込み、OCR下書き作成、手修正、確定記録、確定済み記録の編集・削除、CSV/TSV出力までを対象とする。
- 集計画面などの参照系UIは後から同じアプリケーション内に実装する。MVPでは参照画面よりもCSV/TSV出力を優先する。
- 確定済み試合には、任意の共有試合メモを1件まで記録できる。入力、更新、表示、初版の分析・出力境界は `docs/requirements/match-note.md` を正本とする。

---

## 2. summit アプリ・momo-db との連携

同じ開発ツリーにある summit アプリと DB 管理リポジトリ（`../momo-db`）と連携する。

- DBスキーマと migration の正本は momo-db リポジトリに集約する。
- summit アプリと本アプリは同じ Neon PostgreSQL スキーマを共有する。
- momo-db の `members`、`held_events`、`held_event_participants`、`app_sessions` などを契約として参照する。
- summit アプリの以下の情報を共有する。
  - 固定4名のメンバー情報（`members`）
  - 実開催履歴（`held_events`）。summit が作成した held_event は Discord 出席 session に紐づく。
- 本アプリ側でも開催を作成できる。本アプリ作成分は summit の出席 session に紐づかない（`held_events.session_id` が NULL）。
- 1つの `held_events` には、第1試合、第2試合のように複数の桃鉄1年勝負の試合結果を紐づけられる。
- 試合番号は同じ `held_events` 内で採番し、必要に応じて手動変更できる。同じ開催回内で同じ試合番号を重複させない。
- 結果作成時は開催を選択し、その中に第n試合を追加する。開催が存在しない場合は、本アプリから新規作成できる。

## 3. 認証・権限

### 3.1 ログイン

- ログイン方式は Discord OAuth とする。
- Discord OAuth のユーザーは `momo_login_accounts.discord_user_id` と照合する。
- `login_enabled = false` のアカウントはログインできない。無効化されたアカウントの既存 session は無効化対象とする。
- `player_member_id = NULL` のログインアカウントは、戦績を操作できるが試合参加者ではない運用者として扱う。

### 3.2 ロールと付与

ログインアカウントを次の3ロールで扱う。レーダー・分析・マスタの既存機能を運用担当へ委任し、アカウント管理等は管理者に残す。

ロール導入と本番反映の作業管理は [MOM-33](https://linear.app/ponta/issue/MOM-33)、Webの実装・受入は [MOM-37](https://linear.app/ponta/issue/MOM-37) で行う。

| 表示名 | ロール識別子 | 役割 |
| --- | --- | --- |
| 一般 | `user` | 試合の記録、閲覧、修正、削除、出力を行う |
| 運用担当 | `operator` | 一般の操作に加え、レーダー採点基準、分析再計算、シーズン・マップを管理する |
| 管理者 | `admin` | 運用担当の操作に加え、アカウント、作品、プレーヤー名エイリアス、Discord通知設定を管理する |

- 1アカウントにつき1ロールとする。新規アカウントの初期選択は一般とし、複数ロールの兼任やアカウント別の個別権限は設けない。
- ロールはログインアカウントへ付与する。試合参加者との紐づけ、試合の所有者・作成者とは独立し、プレーヤーに紐づかない運用担当も同じ操作を行える。
- ログイン許可とロールは別々に扱う。どのロールも、ログインを無効化されている間は操作できない。
- 初期管理者は「ぽんた」とする。アカウントの一覧・登録・更新、ログイン許可、ロールの付与・変更は管理者だけが行える。運用担当は自分や他者のロールを変更できない。
- 最低1名の有効な管理者を維持する。最後の有効な管理者のログイン無効化、一般・運用担当への変更を拒否し、同時更新でもこの条件を破らない。運用担当は管理者数へ含めない。
- 設定管理の「アカウント」タブには現在のロールを表示し、登録・変更時には3ロールから1つを選べるようにする。変更対象と変更後のロールを確認でき、保存結果が不明な場合は成功と断定しない。

### 3.3 操作権限

ログイン済みの有効アカウントは、誰でも以下を実行できる。

- マスタ一覧、試合記録、戦績比較・分析結果の閲覧
- 開催履歴の閲覧・作成
- 紐づく試合結果・下書きがない開催履歴の削除
- 画像アップロードとOCRジョブ作成
- 自分が作成した未確定下書きの更新・削除
- 試合結果の作成、確定、修正
- 試合メモの作成、更新、削除
- 確定済み試合結果の削除
- CSV/TSVダウンロード

追加の権限は次表を正本とする。「可」はログイン済みの有効アカウントに限る。

| 操作 | 一般 | 運用担当 | 管理者 |
| --- | --- | --- | --- |
| 上記の日常操作・通常のマスタ参照 | 可 | 可 | 可 |
| レーダー採点基準の管理情報・比較・操作状況・改訂履歴の閲覧 | 不可 | 可 | 可 |
| レーダー基準候補の作成・閾値の手入力調整・比較更新・適用・取り下げ・前回基準への復帰・再試行・現行基準の継続判断 | 不可 | 可 | 可 |
| 分析管理の状況・履歴閲覧、1作品の手動再計算 | 不可 | 可 | 可 |
| 全作品の一括再計算 | 不可 | 不可 | 可 |
| マップ・シーズンの追加・名前の編集・削除 | 不可 | 可 | 可 |
| 作品の作成・更新・削除 | 不可 | 不可 | 可 |
| プレーヤー名エイリアスの作成・更新・削除 | 不可 | 不可 | 可 |
| Discord通知設定の閲覧・変更 | 不可 | 不可 | 可 |
| アカウントの一覧・登録・更新、ログイン許可・ロールの変更 | 不可 | 不可 | 可 |

通常のマスタ参照には作品・マップ・シーズン・事件名・プレーヤー名エイリアスの一覧を含む。管理画面のタブを表示しないことを理由に、一般にも認められている参照権限を取り上げない。

MVPでは事件名マスタは固定6項目を読み取り専用で扱う。

確定済み結果の修正履歴は保存しない。

#### 委任する業務の範囲

- 運用担当は全作品を共通で担当する。作品・シーズン・マップごとの担当割当や、自分が作成したデータへの限定は設けない。
- レーダーは [採点基準の作成・更新](series-player-radar.md#4-採点基準の作成更新) の手入力調整を含む操作を一通り任せ、管理者による追加承認は不要とする。管理者・運用担当は作品ごとに共有された候補を引き継げる。操作ごとの依頼者の記録は維持する。
- 運用担当の分析再計算は1作品ずつとし、全作品の一括再計算は管理者だけに残す。全作品操作は対象範囲を示す既存の確認を維持する。状況・履歴の閲覧を含め、受付・計算中・完了・失敗を確認できるようにする。通常の再計算ではレーダーの固定閾値を作り直さない。計算・公開・冪等性・通知の意味は [分析バッチ](series-analysis-batch.md) に従う。
- 一括再計算の制限は、1回の操作で不要な全作品の処理を予約する事故を抑えるための境界とする。運用担当が複数作品を個別に再計算することは認め、実行件数の上限や作品ごとの権限分割へ広げない。
- マップ・シーズンは既存作品への追加、名前の編集、削除を対象とする。所属作品の付替え、並び替え、シーズンの日付・状態管理は今回追加しない。削除時には対象名を確認し、試合または有効な下書きが参照しているものは削除できない。参照データを連鎖削除せず、参照制約・破棄済み下書きの清掃を含む既存のデータ保全を維持する。
- 閾値の手入力調整と改訂履歴は [レーダー要求](series-player-radar.md#閾値の手入力と自動プレビュー) に従う。履歴も運用担当・管理者のみが閲覧でき、変更理由欄は設けない。任意のロール追加、承認ワークフロー、レーダー以外へ広げた汎用の監査ログ画面は追加しない。アプリのロール付与を、DB操作やリリース保守等の運用権限の付与として扱わない。

#### 認可と画面

- 認可はサーバーで操作ごとに判断する。画面の表示制御だけに依存せず、直接URL、直接API、改変したリクエストでも権限外の情報取得・更新・ジョブ受付を拒否する。運用担当を管理者として扱って既存の管理者専用操作を一括開放しない。
- 未認証は認証エラー、有効アカウントの権限不足は権限エラーとして扱い、拒否した操作の副作用を残さない。既存のCSRF対策を維持し、冪等キーを持つ操作の再送でも認可を省略しない。未定義のロールを認可しない。
- ロールの変更が確定した後のAPI認可には新しい権限を使い、再ログインを必要としない。古い画面やクライアント側のキャッシュから以前の権限を維持できない。ログイン無効化では既存sessionも無効化する。
- 管理用の取得・操作が権限エラーとなった場合は本人情報を再確認し、確認中と一時失敗中は保護内容の表示・取得・送信を停止する。同一アカウントの入力、開いていたダイアログ、進行中の操作と冪等キーは保持し、一時失敗には再試行を用意する。拒否だけで降格と断定しない。
- 許可が継続すれば同じ作業を再開する。権限喪失が確定した場合は、権限外のパネル・ダイアログ・入力・管理情報キャッシュを終了し、その未保存・処理中状態で離脱を妨げない。引き続き許可される入力、通常の共有参照、試合入力の一時保存、同一アカウントのCSRFは維持する。自分のロール変更も同じ境界で反映し、古い応答で権限や新しい作業を巻き戻さない。
- 同時の権限拒否は一度の本人情報再確認へまとめ、処理済みの拒否から再確認を繰り返さない。本人情報と管理用の取得の401/403を自動再試行せず、同じ権限へ復帰しても拒否された取得や変更操作を自動再送しない。初回・明示更新・権限拒否の検出から追従し、権限確認用のポーリング、focus・再接続による取得、他端末への即時配信は追加しない。
- 権限変更・ログイン無効化より前に受け付けた分析処理は取り消さず、保存済み候補も保持する。以後の比較更新・適用・取消・再試行等は現在の権限で判定し、権限を持つ別の担当者が引き継げる。
- 運用担当・管理者には「分析」「設定」の導線と対象画面への直接アクセスを提供する。一般には管理導線を表示せず、直接アクセスも拒否する。
- 運用担当の分析管理画面には全作品一括再計算の操作を表示しない。一括再計算APIは管理者だけを許可し、運用担当が直接呼び出しても全作品の予約を作成しない。
- 運用担当の設定画面では既存作品を参照・選択し、マップ・シーズンを操作できるようにする。作品の作成・編集・削除、名寄せ編集、通知設定、アカウント管理の操作・タブは表示しない。権限外のタブをURLで指定した場合や、表示中に権限を失った場合は、権限不足を伝えて利用可能な画面へ案内し、管理者専用APIの取得を開始・継続しない。
- 手入力・OCR確認からマスタ追加へ移動する前に、既存の一時保存が成功したことを確認する。保存できない場合は移動せず、保存できた場合はブラウザーの戻るで同じ作業の入力を復元する。設定滞在中に運用権限を失っても試合入力は保持し、別アカウント・別作業・更新された元データへ古い入力を上書きしない。一般には設定管理への導線を出さず、作品が未登録の運用担当には管理者による作品登録が必要だと伝える。

#### 導入と互換性

- `is_admin` による2区分からの移行では、`false` を一般、`true` を管理者へ対応させる。ログイン許可、プレーヤーとの紐づけ、アカウント識別子を維持し、既存アカウントを自動で運用担当へ変更しない。運用担当は管理者が明示的に付与する。
- 認証主体、本人情報、アカウント管理API、Webの権限判断が同じ3ロールを区別する。旧来の管理者真偽値を互換目的で残す場合も、運用担当を管理者として返さない。旧形式と新形式の値が食い違う状態を作らない。
- 永続化の変更はschema・migrationの正本であるmomo-dbで扱い、[DB利用規約](../db-rule.md#5-migration--deployment)に従って対応するconsumerと整合させる。3ロールを正しく認可できる状態になる前に運用担当を付与しない。

#### ロール拡張の受入条件

| ID | 受入条件 |
| --- | --- |
| A1 | 既存の一般・管理者の権限とログイン許可を保って移行できる。新規アカウントは一般を初期選択とし、管理者だけが3ロールを付与・変更できる。プレーヤーに紐づかない運用担当も担当操作を行える |
| A2 | 有効な運用担当がレーダー候補の作成・比較・適用、前回基準への復帰、取り下げ・再試行・現行基準の継続判断を行える。別担当者の候補を引き継げ、既存の競合・失敗・原子的公開の条件を維持する |
| A3 | 運用担当が各作品を個別に再計算し、受付後の状況と履歴を確認できる。一括再計算は管理者だけが確認付きで行え、運用担当の直接API呼出しでは予約が作成されない。状態の再読込みでは新しい計算を要求せず、通常の再計算で固定閾値を変えない |
| A4 | 運用担当がマップ・シーズンを追加・改名・削除できる。重複や参照中の削除は拒否し、試合・有効な下書きを失わない。試合入力を保存してマスタを追加し、ブラウザーの戻るで入力を復元できる |
| A5 | 権限表の許可・拒否が画面とAPIで一致する。一般や運用担当の権限外の読取・変更・ジョブ受付は、直接呼出しや再送でも成立しない。管理者専用タブの指定・非表示・権限変更から情報取得が漏れない |
| A6 | ログイン中の昇格・降格が以後のAPI認可へ反映され、古い画面で権限外の操作を完了できない。権限喪失時は画面を新しい権限へ更新し、受付済みの計算と保存済み候補は保持する。ログイン無効化後は既存sessionを使えない |
| A7 | 最後の有効な管理者の降格・ログイン無効化を、同時変更も含め拒否する。運用担当を残すだけではこの条件を満たさない |
| A8 | 一般・運用担当・管理者の既存の日常操作と通常のマスタ・分析結果の参照が維持され、運用担当への委任によって作品・名寄せ・通知・アカウント管理の権限が拡大しない |

実装時の認可は実際のAPI経路、移行・最後の管理者・参照データ保護は共有schemaを適用したDB経路、導線・入力保持・権限変更時の表示は実際の画面遷移で確認する。証拠の選定と必須gateは[テスト・品質規約](../test-rule.md)と[開発作業規約](../dev-rule.md#4-change-gates)に従い、上表の条件を文書の点検だけで検証済みとしない。

### 3.4 Discord通知設定

- 管理メニューの「設定」内の「通知」タブで編集する。全利用者に共通の永続設定で、OCR完了と分析完了を個別に選び、「保存」で2つをまとめて確定する。初期値は両方ON。
- OFFの保存と、該当種類の待機中・再送待ち・未送信の失敗通知の取消しは一体で成立する。送信開始済み・送信済みの部分は保持し、開始済みの通知は届く場合がある。
- ONに戻しても、取消済み通知、OFFで確定した送出・分析成功、以前のON期間から遅れて届いた通知は送らない。片方の変更は他方の通知可否を変えない。
- 保存はSummitの稼働状態に依存せず、APIが共有DBへ直接保存する。通知の業務判断はアプリが所有し、設定保存のための通知送出・再送機構は追加しない。
- 読込み前や取得失敗をONとして表示しない。未保存・保存中・保存成功・保存失敗を区別する。古い画面からの保存は2種類とも変更せず、現在の設定を確認して選び直す。通信切断などで結果が不明な場合は成功・失敗を断定せず、再読込みで確認する。
- この画面では配送失敗一覧や手動再送を提供しない。

#### OCR完了通知

- 1回の読み取り操作で固定した1〜3画像の「送出」を単位とする。全画像の受付・処理が終端となり、Workerが送出全体を確定した時点で1回だけ通知する。最後の画像終了と全体確定を区別し、途中通知や遅い画像だけの追加通知を行わない。
- 全失敗や画像jobが0件の受付失敗も通知対象とする。失敗には確定した受付拒否・受付期限切れ・OCR最終失敗・タイムアウト・個別jobの中止を含め、要確認を画像の失敗として列挙しない。下書きの確定・削除は通知全体の取消条件とする。
- 本文は完了案内、既知の作品・開催・試合の文脈、全体確定日時、現在の下書きへのリンク、失敗した画面種別と安全な短い理由に限る。失敗は総資産・物件収益・事件簿の順で最大3件、0件なら失敗欄を省く。成功・要確認の一覧・件数・警告、例外全文、OCR値、元画像を載せず、メンションを発生させない。
- 必須情報を保って1投稿に収める。長い表示名は省略を明示して短縮できるが、失敗した種別・理由・確認先は落とさない。本文と完了日時は固定し、リンク先が後の画像差替えを含む現在状態であることと区別する。
- 設定は送出全体の確定transactionで判定する。途中でOFF→ONとなっても確定時にONなら対象とし、OFFで確定した分を後のONで補完しない。確定時ONでも、その後OFFなら未開始配送を取り消し、ONへ戻しても復活させない。
- 同一下書きへの後の追加・読み取り直しは別の送出とし、過去通知を書き換えない。同じ受付操作の通信再試行、画像jobの内部再試行、通知配送の再試行は新しい送出にしない。
- 通知の失敗でOCR結果保存や下書き利用を失敗に変えない。永続受付前の通知欠落は許容し、確定済み送出からの通知再構築やproducerのHTTP再送は行わない。永続受付後の配送・再送はSummitが担う。通常時の1送出1投稿を障害時の厳密なexactly-once保証としない。
- 送出導入前の画像単位通知は新規受付・配送・手動再送を行わず、保存済みの本文・識別・履歴を保持する。旧処理を排出したメンテナンス中の一括切替を前提とし、過去jobから送出を推測して作らない。分析通知の契約は独立して維持する。

責務と復旧は [architectureのOCR](../architecture.md#ocr-capability--worker-role)、状態は [ドメイン規約](../domain-rule.md#ocr送出)、保存・wireは [共有通知契約](../../../momo-db/docs/discord-notifications.md) に従う。

#### 分析完了通知

試合の追加・変更・削除を反映した分析結果の公開成功を対象とし、設定は分析成功時に判定する。入力差分のない再計算や保守目的だけの処理は対象外とする。

前回成功から追加・変更した試合の保存順位、4人別の銀次回数と合計、メモ全文、作品通算・シーズン通算の平均順位の変化を伝える。未入力メモ欄は省略し、対象試合なしと全員銀次0回を区別する。本文は固定し、リンク先は現在の試合詳細と最新分析とする。対象集合・比較元・成功境界は [分析batchの通知契約](series-analysis-batch.md#分析完了通知) に従う。

#### 通知サイズと送出可否

新規通知の送出上限はSummitの標準受付範囲に合わせる。byte数はUTF-8で数え、HTTP本文とPostgreSQLの `jsonb::text` 表現を区別して、`data` だけでなく識別・時刻・設定世代を含む最終envelopeへ適用する。

| 対象 | 上限・適用範囲 |
| --- | --- |
| 新規HTTP本文 | 512 KiB |
| 新規OCRの最終envelope | JSONB text表現で16 KiB |
| 新規分析の最終envelope | JSONB text表現で256 KiB |
| 新規分析の掲載内容 | 50試合・影響する16シーズン |
| 分析の作品・マップ・シーズン名 | 各256 Unicode code points |
| 分析のプレーヤー表示名・owner名 | 各32 Unicode code points |
| 分析の試合メモ | 150 Unicode code points |
| OCRの作品名 | 長い場合は先頭200 Unicode code pointsと省略記号へ短縮 |
| 分析の比較履歴読取 | 128シーズン。新規掲載範囲とは独立 |
| 分析の描画後の投稿数 | 128投稿。Summitが検証。OCRは一投稿 |
| 共有wire・保存済み通知の互換範囲 | JSONB text表現で8 MiB。新規producer送出の許容量には使わない |

producerは新規送出のbyte数・件数・文字数を検証し、上限超過時は通知全体を省略する。OCR作品名の既存の短縮を除き、本文の切捨てや通知分割で収めない。省略してもOCR結果保存・分析公開の成功を変えず、分析の通知用入力基準は前進させる。producer outbox、HTTP再試行、未受付通知の再構築を追加しない。

分析の比較履歴は差分と比較元を確定するために読み、新規掲載上限へ縮めない。投稿数はSummitが固定本文と描画設定から検証し、producerへrendererを複製しない。共有schema・wireの正本は引き続き[共有通知契約](../../../momo-db/docs/discord-notifications.md)とし、保存済み通知の互換範囲を新規送出上限へ縮めない。

## 4. MVP画面

MVPでは以下の画面を提供する。

- ログイン画面
- 試合一覧画面。登録済みの試合結果と未確定下書きを一覧し、試合詳細または出力へすぐにアクセスできるようにする。
  - 各行で確定状況を判別でき、未確定下書きには確定へ進むための次の操作を示す。
  - メモがある確定済み試合には、本文を表示せず「メモあり」と示す。メモのない試合や未確定下書きへ「メモなし」を反復しない。
- 開催履歴一覧・作成画面
- 手入力での試合作成画面
- 試合詳細・編集画面
  - 試合詳細画面は、簡潔な画面名、開催日・作品・シーズン・マップ、特徴バッジ、4人の結果台帳、戦績比較への導線、試合メモ、記録管理情報の順に表示する。
  - ページ下部の試合結果・メモ・記録情報の後に置く「前の試合」「後の試合」は開催・作品・シーズン・マップ・起点の絞り込みによらず全確定試合を移動する。順序は [戦績比較の対戦順](series-comparison.md#2-data--scope-invariants) と共通の昇順で、前は直前、後は直後とする。欠番、削除済み試合、未確定下書きを飛ばし、端には存在しない方向へのlinkを作らない。
  - 行き先は対戦日時と開催内番号で示し、開催日時が異なる場合は所属開催の日時も補う。移動後の本文・メモ・編集・出力・比較条件は現在試合へ揃える。前後移動の完了時は識別見出しへfocusを移すが、待機中に利用者が別操作へ移った場合は奪わない。
  - 前後移動は通常の履歴に積み、ブラウザの戻る・進むで訪問した詳細や元の一覧条件・hashをたどれるようにする。遷移元URLは次の画面へ渡さない。画面内には現在試合が所属する開催へのlinkを置き、遷移元に応じて行き先を変えない。
  - 同じ試合の再取得中・一時失敗は本文と未保存メモを保って前後操作だけを一時停止し、局所的な更新状態・再試行を示す。前後情報の欠落・不正を端と混同せず、本文と所属開催への導線を保つ。不存在が確定した試合は通信失敗で復活させず、試合一覧への安全な導線を残す。削除時の未保存メモは [メモ保護](match-note.md#52-確定後の編集owner) に従う。
  - 結果台帳では順位、プレーヤー名、総資産を主情報とし、物件収益、物件収益順位、物件収益÷総資産、対象試合の直前から直後への通算平均順位変化を補助情報として表示する。通算平均順位は小さいほど良く、数値差だけでなく「改善」「後退」「維持」「初戦」を併記する。
  - 成績詳細は結果台帳へ統合し、1人分の名前・順位・総資産、物件収益、通算平均順位、プレー順、事件簿6項目を一つのまとまりにする。広い画面では2列、狭い画面では1列にし、1位からの順位順で走査できるようにする。2列では左上、右上、左下、右下の順に並べる。名前と順位を総資産とともに主情報として強調し、群内の近接と群間の余白を揃える。
  - 物件収益÷総資産は総資産が正の場合だけ計算し、0以下では「対象外」とする。物件収益順位の同率は平均順位法で扱う。
  - 戦績比較は同じ作品・シーズン・マップを対象とする。比較データの読み込み中、取得失敗、対象試合なしの場合も、試合詳細APIから得た順位・総資産・成績詳細を先に表示し続ける。
  - 試合の特徴は開催条件に続くバッジだけを表示する。見出し、解説、更新操作は置かず、取得中・取得失敗・対象なしではバッジ領域を表示しない。
  - 特徴バッジは、接戦、大差、スリの銀次多発、物件収益ねじれ、借金あり、目的地なし決着など、確定済み記録から決定論的に判定できるものに限る。
  - 通算平均順位は同じ作品・シーズン・マップの初戦からの累積で、矢印は対象試合の直前から直後への変化を表す。この範囲を台帳の近くに一度示し、特徴の相対判定も同じ範囲を用いる。
  - 試合メモには内容のある記録と編集操作を表示し、自明な用途説明を添えない。オーナー、対戦日時、確定日時、削除操作は結果とメモの後に置く。
- OCR取り込み画面
- OCR下書き確認・確定画面
- CSV/TSVダウンロード画面
- 運用担当・管理者向け設定管理画面（3節の権限に応じたマスタ管理・Discord通知設定・アカウントのログイン許可とロール管理）

## 5. 画像取り込み

### 5.1 取り込み方法

以下の両方に対応する。

- USB Video Class対応キャプチャーボードからのブラウザ撮影
- 画像ファイルアップロード

キャプチャーボード撮影UIには以下を含める。

- プレビュー
- 静止画撮影
- 再撮影
- 画像アップロードへの切替

対象ブラウザは Chrome / Firefox / Safari / Edge の最新安定版とする。ブラウザや端末の都合でキャプチャーボード撮影が使えない場合は、画像アップロードへフォールバックできればよい。

### 5.2 OCR対象画面種別

取り込む画像のOCR対象画面種別は以下の3種類である。

- 総資産
- 収益額
- 桃鉄事件簿

総資産と収益額の画像には、それぞれのプレーヤーと金額が順位順に表示されている。

桃鉄事件簿の画像には、各プレーヤーが遭遇したイベントの回数が表示されている。

MVPのUIでは、画像を3種類の分類トレイへ配置して読み取り対象を決める。分類が違う場合はユーザーが手動で入れ替えられる。API/OCR境界では `requestedScreenType` と `detectedScreenType` として扱い、「画像種別」ではなく「OCR対象画面種別」として表現する。

同じ種類の画像を複数取り込んだ場合は、最新の取り込み結果で上書きする。

### 5.3 画像の保存

- 画像は結果確定の必須条件ではない。
- 画像なしの手入力だけでも結果を確定できる。
- アップロード可能な画像形式は PNG/JPEG/WebP とする。
- アップロード画像は1枚3MBまでとする。
- API の upload / OCR 公開レスポンスは内部ファイルパスを返さない。画像参照は `imageId` と下書き単位の source image API で扱う。
- 取り込んだ元画像は、下書き確定またはキャンセルまでプレビュー・ダウンロード可能にする。
- 下書き確定またはキャンセル後、元画像は削除対象とする。
- DBには画像実体を残さない。DBに残すのは source image ID、保持期限、削除時刻などのメタデータだけとする。
- サーバーに画像を恒久保存しない。
- 結果確認では表示対象の元画像を優先し、取得後に残りの登録画像を順番に先読みする。回線条件による判定は行わず、画像本体の取得は画面内で同時1件までとする。
- 先読み済み画像への切替では追加の通信待ち・取得中表示を発生させない。全画像の事前デコードは要求しない。
- 画面内で保持する元画像は最大3枚、各3MiB、合計9MiBまでとする。この上限はBlobの保持量であり、ブラウザ全体のメモリや再試行を含む累計通信量の上限ではない。
- 先読みの失敗は入力を妨げず、同じ候補を自動再試行しない。後からその画像を選択した際に通常取得を1回行い、表示対象の取得が失敗した場合は手動で再試行できる。
- 画像の消失・差替えでは旧画像を破棄する。画面離脱、下書き切替、確定・削除の成功、ログアウトでは元画像の取得を中断し、画面内の保持を終了する。確定・削除の失敗時は作業中の画像を維持する。

## 6. OCR・下書き

### 6.1 OCR処理

- OCR/画像解析には外部APIを使わず、ローカル処理に限定する。
- OCRはサーバー側の OCR worker で実行し、ブラウザは画像を一時アップロードする。
- バックエンドはAPIサーバーとOCRワーカーを分離する。
- OCRジョブ状態の正本はDBに置く。
- 画像登録の前に、送出ID、対象画像の種別・内容識別、読取り条件を一括で固定する。同じID・同じ受付内容は既存状態へ収束させ、別主体・別内容での再利用を拒否する。現在の下書きslotから送出の対象集合を再構築しない。
- OCR受付には既存の対戦下書きIDを必須とし、画像ごとのOCRジョブ・結果と下書きのslotを同じtransactionで紐づける。開催と開催内の試合番号は、この時点では未選択でもよい。
- API は OCR job と受付時の入力 snapshot を DB へ原子的に保存し、Worker が直接取得する。commit 後の起床通知が失われても DB から回復する。
- 開始確認から再試行までを同じ受付操作として扱い、日時・下書き・アップロード済み画像を引き継ぐ。通信失敗だけで未受付と判断して自動取消しせず、成功した画像は再送しない。入力不備や確定した受付拒否は設定修正へ戻し、受付結果が不明な場合は同じ操作を安全に再送できるようにする。
- 受付済み送出はブラウザ終了・途中離脱・全画像未受付でも有限の受付期限で収束させる。期限は再送で延長せず、未登録枠だけを閉じる。登録済みjobの処理期限とは分け、閉じた枠を遅延requestで再開しない。期限前に登録済みの同一requestは既存jobへ収束させる。
- 一時的な転送失敗・混雑・rate limitを画像の確定失敗へ変換しない。送出状態の照会と同じ操作の再試行を提供し、期限終了後の読み取り直しは利用者が明示する新しい送出とする。受付前に失われた操作を通知対象として補完しない。
- 画像ごとの進捗と送出全体の確定を区別する。通知待ちを理由に下書き編集・確定を余計に止めず、全画像失敗後も手入力や新たな読み取りへ進める。
- OCR処理は、将来差し替え可能な構造にする。

### 6.2 下書き

- OCR結果は `ocr_drafts` と `match_drafts` を通じて下書きとして保存する。
- 下書きはユーザーが修正・確認できる。
- 確認画面は、その下書きが現在参照するOCR結果と元画像の一覧を一つの読み取りで取得する。元画像の本体は表示対象から取得し、結果の取得と画像転送を分ける。
- 確認中に別の画面から元画像が差し替えられた場合、古いOCR結果へ新しい画像を表示・保存しない。入力中の値は維持し、最新の画像とOCR結果を確認し直す必要があることを案内する。
- 未確定下書きは作業中の間だけDB上に残る。作成者は削除でき、削除時は元画像保持を閉じた上で `match_drafts` を物理削除する。下書き削除の成功応答は画像実体の削除完了を待たず、画像実体は定期回収で削除する。
- `confirmed` は確定 usecase の副作用とセットでだけ到達する。`cancelled` は過去データ互換の終端状態であり、新規のユーザー削除では残さない。
- OCRが失敗した場合は失敗理由を表示し、空の手入力下書きとして続行できる導線を残す。
- OCR結果の信頼度が低そうな項目や警告は、確認画面で強調表示する。

### 6.3 UIフロー契約

- OCR取り込みは記録先、camera、3分類トレイ、送信の順で扱い、cameraを主入力、ファイル選択をfallbackとする。撮影先は分類トレイ自体の選択面と押下状態付きの操作で示し、離れたラベルや選択変更の説明文を重複表示しない。画像追加後の次の空トレイ、置換対象をトレイ上で判別できるようにし、empty / selected / working のプレビューは同じ16:9領域を保つ。
- 開始確認時に設定と選択画像をsnapshotする。uploadとOCR job登録中は重複送信を防ぎ、部分handoffでは自動遷移せず、利用者が明示的に次へ進めるようにする。
- OCR確認は記録先・試合文脈、全体通知、4人のreviewとsource、確定操作の順とする。evidenceは表示行ではなくsemantic fieldとplayerへ結び付け、cell stateは決定的な優先順を持たせる。wideではledger、narrowではplayer単位のaccordionとし、未解決項目の確認はsoft gateにする。
- guided review は未解決数、active field、evidence、source kind、confidence、前後移動、明示acknowledgeを示す。source imageの自動追従は明示操作で停止・再開でき、未保存値とacknowledgementはtab単位で復旧し、dirty workの破棄前に確認する。

## 7. 結果記録

### 7.1 確定時の必須項目

試合結果の確定には以下を必須とする。

- 開催回
- 対戦日時
- 開催回内の試合番号
- 作品名
- シーズン
- オーナー
- マップ
- 固定4名全員のプレー順
- 固定4名全員の順位

試合メモは任意とし、未入力でも試合を確定できる。入力する場合の上限と保存契約は `docs/requirements/match-note.md` を正本とする。

対戦日時はその試合を行った日時とし、所属開催の日時とは区別する。`held_events` の開催日時を初期値として使えるが、実際の対戦日が異なる場合などは手編集でき、入力欄でも両者を区別する。[実績項目の適用開始](player-achievements.md#項目の追加と適用開始)は、この対戦日時の日本時間の日付で判定する。既存の対戦日時を推測で書き換えない。

開催回内の試合番号は1以上とし、同じ開催回内で重複させない。

固定4名全員の順位は 1〜4 で重複なく入力されている必要がある。

### 7.2 プレーヤー別結果

プレーヤーごとに以下を記録する。

- メンバーID
- プレー順
- 順位
- 総資産
- 収益額
- 事件簿の各項目の回数

プレーヤーは固定4名全員を1回ずつ含む必要がある。

総資産額と収益額は、万円単位の整数に正規化して保存する。

順位は総資産額から自動計算せず、OCRまたは手入力された順位を正として保存する。

プレー順は、画像内の色順から判別する。色順は青、赤、黄、緑の順で、画面下のインジケータ左から順番になっている。判別結果は手修正可能とする。

OCR上のプレーヤー名とDB内のメンバー名またはDiscord名が一致しない場合があるため、メンバーごとに複数の表示名エイリアスを持てるようにする。

### 7.3 オーナー・マップ・シーズン

- オーナーは固定4名のいずれかとする。
- 作品にはマップ候補とシーズン候補を紐づける。
- 試合結果ごとに作品、シーズン、オーナー、マップを入力する。
- 選択したマップとシーズンは、選択した作品に属している必要がある。

### 7.4 試合確定の2経路

試合確定には同じ `matches` 作成でも2つの経路がある。

| 経路 | 識別子 | 必須の副作用 |
|---|---|---|
| 手入力 / 画像なしの直接作成 | `matchDraftId` なし | `matches` / `match_players` / `match_incidents` を作成する。`match_drafts` は触らない。 |
| OCR下書きからの確定 | `matchDraftId` あり | `matches` / `match_players` / `match_incidents` を作成し、元 `match_drafts` を `confirmed` にして `confirmed_match_id` を保存し、元画像保持を閉じる。 |

`draftIds` は確定済み試合が参照した OCR 結果の履歴であり、元作業単位を閉じる識別子ではない。OCR下書きから確定する経路では、`draftIds` だけでなく `matchDraftId` を必ず保持して API に渡す。

## 8. マスタ

MVPでは以下のマスタを扱う。

- 作品
- マップ
- シーズン
- 事件名
- プレーヤー名エイリアス

### 8.1 作品・マップ

- 作品はマスタとして登録する。
- マップは作品に紐づける。
- 作品・マップの操作権限は [3.3 操作権限](#33-操作権限) に従う。
- 新規作成時の表示順はAPI側で末尾追加として採番する。

### 8.2 シーズン

- シーズンは期間で区切る大会・集計単位である。
- 1つのシーズンは複数の開催結果を束ねる。
- シーズンは作品に紐づける。
- 結果確定時はシーズン選択を必須とする。
- シーズンの操作権限は [3.3 操作権限](#33-操作権限) に従う。
- 新規作成時の表示順はAPI側で作品ごとの末尾追加として採番する。

### 8.3 事件名

桃鉄事件簿は、事件名マスタとプレーヤーごとの回数として構造化して記録する。

MVPでは以下の6項目を固定で扱い、アプリ上では読み取り専用とする。

- 目的地
- プラス駅
- マイナス駅
- カード駅
- カード売り場
- スリの銀次

### 8.4 プレーヤー名エイリアス

- OCR名寄せ用に、メンバーごとの表示名エイリアスを管理する。
- エイリアスの作成、更新、削除は管理者だけが行える。
- OCR実行時は、入力された hints とDB上のエイリアスを合わせて worker に渡せる。

## 9. CSV/TSV出力

### 9.1 権限

- CSV/TSVダウンロードは非公開APIとする。
- ログイン中UIからのみ実行できる。
- ログイン済みの有効アカウントがダウンロードできる。

### 9.2 出力範囲

以下の範囲を指定してCSV/TSVを出力できる。

- 全試合
- シーズン単位
- `held_events` 単位
- 試合単位

`format` は `csv` または `tsv` とする。

### 9.3 行構造

CSV/TSVは、1行を1プレーヤーの試合結果明細とする。

列は以下の順序を正とする。

| 列 | 内容 |
|---|---|
| シーズン | シーズン名 |
| シーズンNo. | シーズン内の対戦連番 |
| オーナー | 試合結果ごとに入力されたオーナー |
| マップ | 試合結果ごとに入力されたマップ |
| 対戦日 | 開催日 |
| 対戦No. | 同じ作品内の通算対戦番号 |
| プレー順 | プレーヤーのプレー順 |
| プレーヤー名 | プレーヤー名 |
| 順位 | 最終順位 |
| 総資産 | 万円単位の総資産 |
| 収益 | 万円単位の収益額 |
| 目的地 | 桃鉄事件簿の回数 |
| プラス駅 | 桃鉄事件簿の回数 |
| マイナス駅 | 桃鉄事件簿の回数 |
| カード駅 | 桃鉄事件簿の回数 |
| カード売り場 | 桃鉄事件簿の回数 |
| スリの銀次 | 桃鉄事件簿の回数 |

`シーズンNo.` は選択範囲内だけでなく該当シーズン全体での連番とする。`対戦No.` は選択範囲内だけでなく該当作品全体での通算対戦番号とする。

初版の試合メモはCSV/TSVへ含めず、上記の列順と1行1プレーヤーの契約を変更しない。

### 9.4 UIフロー契約

- 出力画面はscope、必要なtarget、format、生成summary、downloadの順で扱い、action直前に選択targetとformatを明示する。short listは既存control、long listは選択dialogとpaginationを使い、pageをまたいでもselectionを保持する。
- confirmed matches only、1 player per row、金額単位などの不変条件はaction付近の1か所へ集約し、button labelはscopeとformatを含める。
- loading、refreshing、empty、invalid URL、progress、success、timeout、failureは所有するcontrolの近くへ置き、local retryまたはresetを用意する。
