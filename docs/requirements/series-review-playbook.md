# 戦績比較 振り返り・行動プレイブック要求仕様

目的: 戦績比較の保存済み指標を、次回4戦で試すプレーヤー別の行動仮説へ決定論的に変換する。

責務の境界:

| 関心事 | 正本 |
| --- | --- |
| プレイブックの候補、選定、文面、表示 | 本書 |
| 基礎指標、scope、詳細分析 | `docs/requirements/series-comparison.md` |
| 非同期計算、artifact、状態、公開・復旧 | `docs/requirements/series-analysis-batch.md` |
| HTTP / artifact shape | OpenAPI、JSON Schema、共有fixture |
| 開催単位の事実表示 | `docs/requirements/held-event-detail.md` |

本書は基礎指標の数式、job / artifact lifecycle、endpoint path、DTO field、component構成を複製しない。

## 1. Outcome / Scope

- 「次戦に備える」は戦績比較ページ内の上位解釈layerであり、別ページや開催回reviewにしない。
- 選択中の作品、season、mapの確定済み戦績から、各プレーヤーへ0〜3件の期間playbook cardを返す。
- cardは最適手や勝敗予測ではなく、保存済み結果から次回試す価値がある行動仮説である。
- AI、外部推論、自由文生成、新規プレーデータをMVPで使わない。候補採否と意味順はworkerが決定し、API / Webで再判定しない。
- 直近傾向、高度分析、事件簿は補助根拠にできるが、未保存の行動順、card内容、距離、turn状態、因果を推定しない。

成功条件:

- 利用者が短時間で4人の最優先仮説を把握し、card本文だけで発動場面と試す行動が分かる。
- 全cardから症状、差分、対象件数、信頼度、詳細指標、試合後の検証へたどれる。
- 弱い候補を無理に出さず、件数不足や不安定な候補を断定しない。
- 詳細指標のtable / graphを再掲せず、対応する分析viewと根拠試合へ往復できる。

## 2. Output / Presentation

表示順:

1. 複数人に共通する論点を最大2件、一度だけ示す。
2. 4人の最優先cardを比較する。
3. 各人の2〜3件目を「ほかの仮説」として開示する。

各cardは次の意味を持つ。

| 項目 | 要求 |
| --- | --- |
| 分類 | `再現する`、`見直す`、`検証する` のいずれか |
| 行動仮説 | 試合中に思い出せる短い行動文 |
| 発動条件 | 次回、本人が自己観察する場面。リアルタイム判定ではない |
| やること / 避けること | その場面で優先することと抑えること |
| データ上の理由 | 症状、上位・下位間などの差分、主要数値 |
| 品質 | 対象件数、信頼度、4人内の特徴度、除外理由 |
| 試合後の検証 | 次回開催後に仮説を評価する観点 |
| 詳細リンク | 対応する分析view / 指標。cardの意味をリンクだけに依存させない |

`再現する` は成績を支える方針の継続、`見直す` は悪化条件での優先順位変更、`検証する` は件数または差分が限定的な試行候補を表す。

- 初期表示は行動仮説、発動条件、やること、平易な理由を優先し、詳細根拠を一つの補助開示へ置く。
- card群の前に置く説明は、選択scope、試す期間など解釈を変える前提だけにする。読解順は、対象と分類の読み方、4人共通の行動仮説、4人の個別card群とし、内容を解釈する前提を結果より後置しない。`発動条件に当てはまるとき使う` のように項目名や構造から自明な利用方法を別のラベルと値で復唱せず、実際の発動条件を各cardで直接示す。
- 分類・信頼度・発動条件の読み方は一度だけ説明し、cardごとに繰り返さない。
- 同じcategoryが3人以上に現れる場合は特徴の強い1〜2人だけを個人cardへ残し、残りを共通論点へ寄せる。
- 候補0件では弱い仮説を補充せず、「今の差」へ進む空状態を出す。
- PCは4人の最優先cardを比較しやすく、mobileは1人ずつ読めるようにする。分類、品質、linkを色だけで伝えない。
- URLは `review` viewを復元し、詳細viewへの移動後にbrowser backでscopeとreview状態へ戻れること。

## 3. Candidate Model

| Category | 検出する症状・差分 | 行動仮説の方向 |
| --- | --- | --- |
| 物件収益 | 収益上位でも勝ち切れず、上位・非上位で目的地や事故に差 | 収益先行時の目的地・下位回避 |
| 目的地 | 目的地なしで悪化し、上位・下位で収益順位や事故に差 | 目的地なし時の収益順位・事故回避 |
| 低資産 | 低資産帯が多く、非低資産時と収益順位などに差 | 逆転待ち前の収益基盤回復 |
| 番手 | 苦手番手で順位と行動接続可能な指標が悪化 | 苦手番手での早い補正 |
| 銀次 / 事故後 | 被害時に悪化し、入賞・下位で回復指標に差 | 勝ち切りから入賞維持への切替 |
| 下位後 | 前戦下位後の入賞復帰・下位継続で目的地、収益順位、事故に差 | 次戦で2位圏へ戻す方針 |
| 目的地到着後 | 到着後の入賞・下位で収益順位や事故に差 | 到着後も収益順位を維持 |

直近成績、card売り場、直接対決、順位ブレは単独cardにせず、行動へ接続できる主categoryの補助に限定する。「順位を読む手掛かり」は全体品質とfold方向が安定し、既存categoryへ接続できる場合だけ二次的な `検証する` 候補にする。「予測より上位だった勝利」と「王座の確からしさ」は候補へ使わない。

## 4. Deterministic Selection

生成順:

1. 本人baselineまたはscope全体との差から症状を検出する。
2. 症状対象を勝利 / 非勝利または上位 / 下位へ分け、行動接続可能な差分を求める。
3. 小標本を縮小し、件数、効果量、発生頻度、行動接続度、4人内特徴度を評価する。
4. categoryごとのtemplateへ写像する。
5. 非表示候補と重複を除き、共通論点と各人最大3件を確定する。

順位比較には `rankScore = 5 - rank` を使う。総資産は最終順位と循環するため主driverにせず、物件収益順位、目的地順位・回数、マイナス駅・銀次、card売り場を優先する。

小標本の極端値はbaselineへ縮小する。代表形は次のとおりで、weightと各thresholdはalgorithm versionで固定する。

```text
shrunkEffect = rawEffect * targetCount / (targetCount + priorWeight)
shrunkRate = (successCount + priorWeight * baselineRate) / (targetCount + priorWeight)
```

品質境界:

| 対象 | 主採用 | 参考 | 非表示 |
| --- | ---: | ---: | ---: |
| 通常指標 | 20件以上 | 3〜19件 | 2件以下 |
| 条件付き指標 | 8件以上 | 3〜7件 | 2件以下 |

候補順は次の要素をすべて含む決定論的scoreで決める。

```text
abs(shrunkSymptom)
* contrast
* exposure
* reliability
* actionConnection
* peerDistinctiveness
* commonnessPenalty
```

開催安定性は、対象8件以上かつ3開催以上の候補について開催を1件ずつ除外した効果の方向・大きさから算出し、全categoryの説明用根拠にする。事故後と目的地到着後のdriver根拠だけは、開催を再標本化する固定seed・96回のbootstrapによる2.5% / 97.5%区間も示す。seedはmember、category、metricのUTF-8値から決定論的に作る。

- 8件未満または3開催未満では安定性・信頼区間を補完せず、対象なしとして保持する。
- bootstrap区間と開催安定性は採否の説明を補う値であり、上記scoreへ追加しない。
- API / Webは区間や安定性を再計算せず、method、効果量、上下限、安定性を同じevidenceから表示する。

- 同じcategoryから複数cardを出さない。
- 行動接続度が低い候補だけならcardを出さない。
- 差分が行動へ接続できない場合、症状が強くてもcard化しない。
- 件数不足では強い差分があっても `参考` とし、4人内順位だけで断定しない。
- `再現する`、`見直す`、`検証する` の多様性は、弱い候補を採用する理由にしない。

## 5. Writing Contract

- 見出しは「〜を優先する」「〜で終えない」「〜へ切り替える」のような試合中の行動文にする。
- 「確認する」「見る」「切り分ける」は試合後の検証にだけ使い、行動仮説や「やること」の主文にしない。
- 「勝てる」「負ける」、能力、人格、運、判断ミスを断定しない。偶発eventを本人の責任へ読み替えない。
- 保存していないcard選択、物件選択、距離、局面を含む文を生成しない。
- ネタ表現は短い見出しに限り、根拠は平易かつ厳密に書く。
- プレーヤー名と指標名は表示labelを使い、master ID、DB列名、API field、内部keyを表示しない。
- 文面はalgorithm versionで追跡できるtemplateから生成し、実データの差分に応じて根拠と行動を対応させる。

## 6. Detail / Artifact Boundary

- cardは判断に必要な症状・差分を保持し、詳細viewは同じ値の再掲ではなく追加根拠を示す。
- 詳細linkは「今の差」「勝因候補」「推移」「条件別」の対応blockへ移動する。開催をまたぐ傾向は「推移」、単一開催の事実は開催詳細を正本とする。
- reviewは同じartifactのbounded chunkから読み、API / Webで推薦、score、sort、title加工、統計fallbackを再実行しない。
- workerはcard採否、primary / secondary、evidence順、品質、共通論点を確定する。APIは認証・schema検証・取得、Webはlabel・layout・navigationを担う。
- 定義済みの候補なし・件数不足は空playbookを含む正常成果物とする。予期しない推薦失敗は作品artifact全体を失敗させ、部分公開しない。
- review resourceの取得失敗で、他viewの取得済み表示を消さない。

## 7. Acceptance Evidence

| 領域 | 必要な証拠 |
| --- | --- |
| 生成 | category別golden、症状・差分、縮小、品質境界、決定的な順序 |
| 選定 | 最大3件、category重複なし、4人内特徴、共通化、候補0件 |
| 表現 | 必須項目、未保存データ・因果・能力断定なし、表示labelのみ |
| 往復 | review URL復元、詳細link、browser back、scope維持 |
| artifact | 同一artifact、API / Web再計算なし、正常な空結果、予期しない失敗時の部分公開拒否 |
| UI | 4人比較、mobile、補助開示、色非依存、他viewとのtable / graph重複なし |
