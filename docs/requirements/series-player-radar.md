# プレーヤーレーダー比較 要求仕様

状態: 基本要求確定。採用軸・採点式・必要件数・具体的な閾値・基準の適用単位は、先行する実データ試作で確定する。本書の作成は試作・機能実装・公開を意味しない。

対象: [MOM-29](https://linear.app/ponta/issue/MOM-29)。評価軸・採点方式・マップ別基準の先行検証は [MOM-30](https://linear.app/ponta/issue/MOM-30) で行う。戦績比較の追加機能として扱う。

## 1. 目的と確定要求

- 複数の観点でプレーヤーの成績を点数化し、レーダーチャートで各人の特徴を比較できるようにする。
- 主目的は成績の強み・弱みの比較とし、各軸は外側ほど良い成績を表す。行動回数の多寡だけを並べたプレースタイル図を主目的にはしない。
- 評価指標は、プレーヤーの行動による成績を反映しやすいものを一から検討する。参考として提示された手動採点表の指標・閾値・軸数を、そのまま採用する要件にはしない。
- 現在取得している記録、そこから算出済みの各種指標、新たに算出する派生指標を幅広く候補に含める。OCRで得られる結果情報を超える新たな試合中の事実は、今回のために取得しない。
- 全試合の代表値に加え、収益トップ時の勝率、低収益時の入賞率、下位後の復帰など、条件付きの成績も試作して評価軸を選ぶ。対象件数が少ない場合に採点できないことを許容する。
- 作品内の固定4人を比較し、シーズン・マップで絞り込めるようにする。
- 採点の閾値は作品ごとの記録から自動計算する。作品内で共通にするかマップ別に分けるかは、実際に採点を試作して判断する。シーズン・マップの絞り込みへの対応と、採点基準の単位は別の決定とする。
- 閾値は毎回の集計では更新しない。管理者が必要なタイミングで計算・更新できるようにする。
- 固定基準に対して好成績を伸ばし、満点を含む特徴的な形を表せるようにする。一方、満点が容易になりすぎたときは基準を見直せるようにする。
- 満点は基準作成時の記録に照らしてかなり好成績な水準とする。達成者がいない軸も許容し、各軸で4人の誰かを必ず満点にしない。理論上の最高成績だけを満点にする要求でもない。
- 基準更新後は過去シーズンも新基準で採点し、使用基準を表示する。過去に見た点数が変わることを許容し、初版では当時の点数への切替を要求しない。
- 各軸を1〜10点で表示し、4人分を同じ軸・目盛りで個別に並べる。平均点はグラフの軸へ追加せず、別のテキストとして表示する。
- システムが基準見直しの目安を表示し、管理者が基準候補の計算、変更前後の確認、適用を行う。目安に達しただけでは基準を自動変更しない。

## 2. 既存機能との境界

| 関心事 | 正本・前提 |
| --- | --- |
| レーダーの目的、評価指標、採点、基準の更新 | 本書。未決部分は実装要件として扱わない |
| 固定4人、作品・シーズン・マップ、確定試合、金額・順位の意味 | [戦績比較](series-comparison.md)、[ドメインルール](../domain-rule.md) |
| 非同期計算、成果物の一括公開、状態、権限、互換性 | [分析バッチ](series-analysis-batch.md) |
| 画面の共通要件、品質証拠、変更gate | [UI規約](../ui-rule.md)、[テスト・品質規約](../test-rule.md)、[開発作業規約](../dev-rule.md) |
| 保存形式、API、成果物の構造 | 実装時にmomo-db、Tapir、JSON Schemaで定義する |

現在の分析入力には、各試合の4人分の順位・総資産・物件収益・事件簿6項目と、開催・作品・シーズン・マップ・オーナー・番手がある。事件簿は目的地、プラス駅、マイナス駅、カード駅、カード売り場、スリの銀次の回数である。

カードの種類・使用順、移動経路、購入機会、銀次に遭遇する機会の総数は記録していない。保存値から新たな行動ログを推定したり、事件簿の合計を総行動回数に見立てたりしない。

既存の試合追加・訂正・削除による分析更新と、今回追加する採点基準の更新は別の意味を持つ。通常の分析更新で採点基準を暗黙に作り直さない。

## 3. 指標の検討候補（軸の採用は試作後）

確定した「成績の強み・弱みを、外側ほど良い点数で表す」という目的に対する候補とする。既存指標と新しい派生指標の両方を検討し、全候補をレーダーへ並べることは要求しない。既存指標の意味は [戦績比較](series-comparison.md#5-metric-semantics) と現在の計算経路を確認して使う。

| 候補 | 検討する指標 | 判断上の注意 |
| --- | --- | --- |
| 最終成績 | 平均順位、勝率、入賞率 | 保存順位を使う。平均順位は小さいほど良い。似た順位指標を多数の独立した強みとして扱わない |
| 資産形成 | 平均・中央値の総資産 | 負の資産を保持する。順位との重なりがある |
| 大きな資産を残す成績 | 総資産の上位側分位点（既存P90など） | 最高額との違い、少数例での不安定さを比較する |
| 資産の下振れ | 総資産の下位側分位点（既存P10など）、新たな損失側の集計 | 平均資産との重複を検証する。小標本での極端値をそのまま能力に読み替えない |
| 収益確保 | 平均・中央値の物件収益、平均物件収益順位 | 金額と試合内順位は意味が異なる。物件の購入判断そのものを観測した値ではない |
| 目的地獲得 | 到着回数の1試合平均、1回以上到着した試合の割合 | 回数と試合割合を区別する。回数は1試合で複数になり得る |
| 収益トップ時の勝ち切り | 収益最大値と同値だった試合の勝率 | 既存のトップ条件は同値を含む。全員同値・収益0の扱いも試作で確認し、途中の優勢を観測したように表現しない |
| 低収益時の入賞 | 物件収益順位が2.5より下位だった試合の1・2位率 | 既存の条件付き成績を候補にする。条件を満たした試合数が分母 |
| 目的地なしの成績 | 目的地到着0回の試合の平均順位・入賞率 | 到着しなかった理由や、その後の逆転を推定しない |
| 銀次遭遇試合の成績 | 銀次1回以上の試合の平均順位・入賞率 | 平均順位は既存値、入賞率は派生候補。遭遇後の回復経路は観測していない |
| 下位後の復帰 | 選択scope内の前戦3・4位から次戦1・2位への率 | 既存の試合間遷移を使う。試合中の逆転や心理的な切り替えとは区別する |
| 銀次への非遭遇 | 銀次0回の試合数 / 対象試合数 | 遭遇機会や回避行動を記録していないため、「回避能力」とは断定しない |

選定時は、何を良い成績とするかを説明できること、別の軸と役割が重なりすぎないこと、対象件数が確保できること、基準固定後も意味を保つことを確認する。軸数を先に埋めるために弱い候補を採用しない。

次の既存値も検討対象には含めるが、そのまま「高いほど強い」軸へ変換しない。

- 順位のばらつき、番手間の差、目的地依存度: 差が小さくても、すべての条件で成績が低い場合がある。
- 物件収益順位と最終順位の差、目的地順位と最終順位の差: 最終順位が同じまま収益・到着成績だけが下がっても値が上がり得る。
- 物件収益÷総資産: 総資産が下がることで比率が高まる場合があり、総資産0以下では対象外になる。
- カード売り場・カード駅・プラス駅・マイナス駅の回数: 多寡と良い結果の関係を決めずに採点しない。関連する条件付き成績や補助説明への利用も検討する。
- 高度分析のモデル出力、行動仮説の選定score、品質・信頼度: 観測された成績そのものの尺度とは区別する。

最高額は試合数による更新機会の差、平均と中央値の併用は同じ性質の重複を検討する。基準を固定しても、元の指標が毎回変わるscope内の相対基準に依存すれば評価の意味が変わるため、その依存も確認する。

## 4. 採点基準の作成・更新

- 採点基準を保存済みデータとして持ち、各人の集計値をその基準で採点する。作品共通・マップ別の適用単位は5節の試作で決める。
- 比較中の4人の最大・最小値だけから点数を引き伸ばす方法は避ける。表示中のscopeからその都度閾値を生成せず、定義済みの適用範囲に対応する保存済み基準を選ぶ。マップ別基準を採用した場合は、その規則に従って対象マップの基準を選ぶ。
- 基準作成には、採点対象と同じ意味の集計値を使う。例えば、1試合の金額分布と複数試合の平均金額分布を混同しない。
- 基準候補の計算、変更前後の閾値・点数の確認、適用を区別する。候補計算だけで現行表示を変えない。
- 基準の識別子、対象作品、指標定義、計算方法、元にした記録の範囲、作成・適用時点を追跡できるようにする。
- 基準更新後の点数と基準を一緒に公開する。候補計算中や失敗で、公開中の基準・点数を部分的に置き換えない。
- 満点の出現だけを不具合や更新理由にしない。見直す目安と、その判断に使う対象期間・件数を別途定める。

### 管理者の操作

1. 管理画面で対象作品の適用中の基準、作成時の記録範囲・件数、見直しの目安を確認する。
2. 管理者が基準候補の計算を依頼する。初回は基準未作成として扱い、必要件数を満たさなければ不足条件を示す。
3. 計算後、現行基準と候補の各閾値、同じ評価対象記録での4人の点数・平均点の変化、採点不能になる軸、適用範囲を確認する。初回は変更前の点数を作らない。
4. 管理者が候補の適用を依頼する。候補を作っただけでは適用しない。数値を直接手入力する閾値編集は初版の対象にしない。
5. その基準を使った対象作品の必要なscopeを計算し、成功した点数と基準を一緒に公開する。受付・計算中・適用済み・失敗を区別する。

候補と現行の比較は、基準の違い以外の入力を揃える。確認後に元の記録、指標定義、適用中の基準が変わった場合は、古い確認結果のまま適用せず、最新条件で候補・差分を再確認できるようにする。二重操作や再送で同じ候補を重複適用しない。

計算中・失敗時は直前に成功した基準と点数を維持する。一度も基準作成に成功していなければ採点値を出さず、既存の戦績比較は継続して利用できるようにする。権限・非同期実行・部分公開の禁止は [分析バッチ](series-analysis-batch.md) に従う。

### 見直しの目安

満点付近への集中を中心に、初回作成に必要な記録の蓄積、基準作成元の記録訂正、対象マップの追加など、基準を確認する理由を管理者へ示す。目安は判断材料であり、更新の強制や自動適用の条件にはしない。見直しが必要か確認するために、毎回新しい閾値を生成することはしない。

試作では、どの記録集合のどの軸を、どれだけの期間・件数で観測するかを定める。1人の好成績や1回の満点を、基準が易しすぎる根拠にはしない。対象件数が足りない場合は、問題なしと判断せず「判断に必要な件数が不足」と区別する。

基準の計算方法自体を変更する場合は、単なる再採点と区別して指標・採点方法の版を進める。基準の適用範囲や軸定義との互換性を確認せず、古い閾値へ新しい意味を与えない。

### 更新後の過去期間

過去シーズンも現在適用中の基準で採点することは確定要求とする。新しい基準と、その基準で採点した過去・現在の各scopeを一組として表示する。元の記録が同じでも基準変更で点数が変わり得るため、使用した基準、基準の適用範囲、元の指標値を確認できるようにする。

基準の版と指標の計算方法の版は区別する。試合の追加で更新される分析入力の版を、採点基準の版として扱わない。通常の作品再計算や画面の表示更新を、採点基準の見直し操作に読み替えない。

### 分析成果物との接続

基準の識別子・内容を計算入力と成果物の来歴に含める。同じ試合入力・algorithm versionであっても、採点基準が異なる結果を同じ再利用対象として扱わない。基準変更で結果が変わったことを、既存の非決定性検出で誤判定しない契約にする。

API・Webで採点、平均点、見直し目安を補完計算しない。基準切替前の計算が遅れて完了しても、異なる基準の点数を現在のものとして公開しない。具体的な保存形式・versionの接続は実装設計で定義し、[分析バッチ](series-analysis-batch.md) の公開・再利用・互換性の契約へ反映する。

## 5. 試作で確定する事項

[MOM-30](https://linear.app/ponta/issue/MOM-30) は本機能の実装前に、次の比較から採用案を決める。今回の要求整理では実データの採点試作はまだ行っていない。

### 評価軸と採点方式

- 各候補について正確な式、分母、良い方向、同値の扱い、必要件数、対象なしの条件を明らかにする。
- 条件付き指標は4人それぞれの条件対象件数を示す。対象0件、観測値0、参考値を区別し、採点不能を0点・満点・中間点で補わない。
- 採点の元となる観測単位と期間を固定する。各人の通算値4点、開催別値、一定試合数の集計値などでは分布の意味が異なるため、採用理由を説明する。
- 指標同士の関連、軸の重複、少数例、特定の開催・極端値を除いた場合の変化を確認する。相関があるだけで機械的に採否を決めない。
- 閾値を作る記録と、その後の評価用記録を時系列で分けて試す。基準に使用した記録への当てはまりだけで、将来も適切に採点できると判断しない。
- 1人だけ突出する例、全員近い例、上限へ達する例、条件対象なし・少数例を含める。差の小ささを失敗として扱わず、特徴的な形を作るために値を加工しない。

### 作品共通基準とマップ別基準

同じ評価対象記録を使い、基準の単位による違いを比較する。少なくとも金額、回数、順位、条件付き率を分けて判断し、すべての軸を一律にマップ別にすることを先に決めない。

| 判断対象 | 試作で示すもの |
| --- | --- |
| 作品共通基準 | マップ別の元の値・点数分布、上限・下限への集中、件数、対象シーズン |
| マップ別基準 | 共通基準からの点数差、各基準に使える件数、少数例での閾値変動 |
| 条件の混在 | マップとシーズン・開催・記録件数の偏り。観測差をマップの因果効果とは扱わない |
| マップ未指定 | 総合成績として何を採点するか。異なる基準の点数を根拠なく平均しない |
| 新規マップ・記録不足 | 基準作成前の状態、共通基準を使う条件の有無、採点できない場合の表示 |

採用方式を、作品内で比較できる意味、マップ内で比較できる意味、利用者に必要な説明とともに示す。実データが足りず判断できない場合は不足条件を明記し、未検証の方式を確定扱いにしない。

### 試作の成果物

- 元の集計値、件数、基準、点数を照合できる4人分の比較例。
- 採用軸と不採用理由、採点式・境界・同値・負値・対象なしの規則。
- 基準の単位、初回作成条件、見直しを判断する対象期間・件数・目安。
- 利用者が比較例を確認したうえでの採用案。結果を本書の確定要求・受入条件へ反映する。

## 6. 表示と読み方

- 各軸は1〜10の整数点とし、4人に共通の軸順・尺度・適用基準で個別のレーダーを表示する。点数を人数内の順位へ置き換えたり、各人で目盛りを変えたりしない。
- 初版は個別比較とし、複数人の重ね表示を追加しない。広い画面では比較しやすく並べ、狭い画面では1人ずつ読める配置にする。
- 作品・シーズン・マップ、対象試合数、使用した採点基準を確認できるようにする。各軸では点数だけでなく元の指標値、単位、分母、品質状態、算出方法にたどれるようにする。
- 基準の境界判定は表示用に丸める前の値で行う。整数点の具体的な境界は試作で決め、原指標と点数を同じ値として扱わない。
- グラフに描けない軸を0点や中間点で埋めず、「対象なし」「件数不足」「基準未作成」など理由を区別する。欠けた頂点を結んで、すべて採点済みの図形に見せない。
- 色だけでプレーヤーや品質を区別せず、名前・軸名・値・必要な状態を数値でも読めるようにする。

### レーダー平均

総合的な要約として、採用された全軸の点数の算術平均を「レーダー平均」としてグラフの外にテキスト表示する。各軸は同じ重みとし、平均を追加の軸にはしない。参考画像に合わせた要約として平均を採用し、合計点を重複して表示することは初版では要求しない。

- 採点された点数を合計し、採用軸数で割る。表示は小数第2位までとし、各軸から再現できるようにする。
- 一つでも採点不能の軸があれば平均を表示せず、採点済み軸数と算出できない理由を示す。採点可能な軸だけの平均で人ごとに異なる内容を比較しない。
- すべて採点可能でも参考値を含む場合は、平均も参考値として示す。
- 採用軸・指標定義が異なる版の平均を、同じ評価内容の増減として扱わない。図形の面積を総合点にしない。

| [MOM-29](https://linear.app/ponta/issue/MOM-29) | MOM-30の結果を受けて計算・基準保存と更新・比較画面を実装し、8節の受入条件を満たす |

MOM-30の決定は実装前に本書へ反映する。未解決の採点設計を実装側の暗黙の既定値にせず、軸や採点方式を利用者と確認した状態を設計検証の完了条件とする。

## 8. 受入条件

以下は本機能の実装時に満たす条件である。具体的な採点式・件数・マップの扱いは5節の試作結果で補完する。今回の文書作成により、機能の動作検証まで済んだとは扱わない。

| ID | 受入条件 | 実装時に選ぶ証拠 |
| --- | --- | --- |
| R1 | 新たな試合中の事実の入力を要求せず、保存済み記録から基礎・派生指標を再現できる。各軸の式・分母・良い方向を説明できる | 試作の比較例、計算経路の手計算可能な例 |
| R2 | 作品・シーズン・マップの選択に従って4人を比較できる。採点基準の適用範囲を表示し、マップ未指定・新規マップ・基準不足も試作で決めた規則に従う | scopeと基準選択の契約、画面操作 |
| R3 | 同じ指標定義・指標値・適用基準なら同じ点数になる。良い方向へ元の指標値だけを変化させた場合、点数が下がらない | 境界値・同値・単調性・決定性の計算証拠 |
| R4 | 全員が満点未満でも正常に表示し、基準作成後に満点へ達する成績も表現できる。比較中の4人へ点数を強制配分しない | 基準固定前後の具体例 |
| R5 | 通常の試合追加・訂正・削除や通常の再計算で採点基準が変わらない。固定基準のまま対象の指標・点数を更新する | 記録更新から保存済み成果物までの接続 |
| R6 | 基準の更新後は過去シーズンも新基準で採点され、元の値と使用基準を確認できる。基準が異なる点数を同じ基準の比較として混在させない | 基準切替と過去scopeの接続 |
| R7 | 条件付き指標は各人の条件対象件数を示す。負値、観測値0、対象なし、少数例、基準未作成を区別し、採点不能を0点・満点・中間点で補わない | 分母と品質状態の計算・表示 |
| R8 | 管理者以外が採点基準を更新できない。計算中や失敗で公開中の基準・点数を部分的に置き換えず、基準と点数を一緒に切り替える | 認可、非同期計算、公開・失敗経路 |
| R9 | グラフと元の集計値・件数・採点基準を照合でき、PCとmobileで同じ人・同じ軸の差を読める。色だけで系列や品質を区別しない | component、Playwright MCPによる読解・操作確認 |
| R10 | API・Webは保存済みの採点結果を読み、通常表示で採点や閾値を再計算しない。既存比較と同じ成果物・更新状態を扱う | 成果物契約、読み取り境界、変更したconsumerの検証 |
| R11 | 各軸を1〜10点とし、同じ軸順・尺度の4人分のレーダーを個別に表示する。採点不能の軸を別の値で埋めない | 保存済み点数と表示の対応、PC・mobileの読解確認 |
| R12 | 全軸が採点できたときだけ、等しい重みの算術平均をグラフ外へ表示する。採点不能があれば平均を出さず、参考値があれば平均も参考値とする | 手計算可能な平均と欠測・参考状態の例 |
| R13 | 見直しの目安と候補計算・適用を区別する。目安到達や候補計算だけで現行基準を変えず、管理者が同じ記録での変更前後を確認して適用できる | 管理画面から候補計算・確認・適用までの操作 |
| R14 | 候補確認後の入力・定義・現行基準の変更を検出し、古い確認のまま適用しない。二重操作や再送が重複適用や世代の混在を起こさない | 保存・公開境界の競合と冪等性の検証 |

品質証拠は [テスト・品質規約](../test-rule.md) から選び、[Change Gates](../dev-rule.md#4-change-gates) に割り当てる。各行をすべての層で重複検証する要求ではない。
