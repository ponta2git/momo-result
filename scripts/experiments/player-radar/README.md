# Player radar design experiment (MOM-30)

実データから採点案を検討するための、独立したローカル試作。アプリ、分析Worker、DBの基準や公開結果は変更しない。採用された方式を本番へ組み込む作業はMOM-29で行う。

要求の正本は [プレーヤーレーダー比較](../../../docs/requirements/series-player-radar.md)。作品共通基準を採用。4軸の要約よりも参考画像に近く成績の特徴が見える構成を探り、現在は目的地を外す・別指標へ替える案と銀次遭遇試合の成績を比較中。採用軸・採点式・件数は未確定であり、このディレクトリの定数や選択肢をすべて採用済みの要求として扱わない。

## 再現

Python 3.10以降の標準ライブラリを使う。DBへの接続機能はなく、明示したJSONだけを読む。

```sh
python3 scripts/experiments/player-radar/analyze.py \
  --input /path/to/source.json \
  --output /path/to/report.json

python3 scripts/experiments/player-radar/render.py \
  --report /path/to/report.json \
  --output /path/to/index.html

python3 -m unittest discover -s scripts/experiments/player-radar -p 'test_*.py' -v
```

出力HTMLは計算済みの結果を内包する。HTTPで見る場合は出力専用のディレクトリをloopbackで配信する。WebからDBへ接続せず、外部CDNや通信も使わない。管理操作は試作画面内の模擬操作であり、状態はブラウザー内に保存する。

実データ、生成HTML、測定結果、スクリーンショットはgit管理外の作業領域に置く。生成HTMLには集計値と、銀次の条件に該当した試合の日付・順位・金額・遭遇回数を埋め込む。利用者が本番記録と照合するための情報であり、公開しない。認証情報、OCRの原文、画像、メモは埋め込まない。

## 入力

`schemaVersion: "mom30-source-v1"`、`snapshotAt`、`totalMatchCount`、`titles`、`maps`、`seasons`、`players`、`matches`を持つJSON。

本番からの読み取りには任意の`provenance`として`kind: "neon-production"`、`label`、`readOnly: true`を付ける。これは抽出時に確認した来歴の表示であり、分析scriptがDBへ接続して確認する仕組みではない。画面に取得時点、作品別の件数・期間を示し、基準作成用の期間と区別する。

- `titles`: `id`、`name`、`revision`。
- `maps` / `seasons`: `id`、`titleId`、`name`。
- `players`: `id`、`name`。4人がすべての確定試合に参加していること。
- `matches`: `id`、`titleId`、`seasonId`、`mapId`、`eventId`、`eventNo`、`playedAt`、`revision`、`players`。
- 各試合の`players`: `id`、`order`、保存済みの`rank`、万円単位の整数`assets` / `revenue`、`incidents`。事件簿のキーは既存の`incident_*` ID、値は非負の整数。省略された事件は現行分析と同じく0回として扱う。

OCR下書き、メモ、画像、認証情報は含めない。複数の取得結果を混ぜず、確定済み試合と表示名を同じ読み取りsnapshotで抽出し、件数を照合する。金額から順位を再計算しない。入力のSHA-256、分析scriptのSHA-256、基準作成元の試合ID・revision由来の識別子を結果に記録する。

## 試している方式

候補指標の元の値と条件対象件数を算出し、4軸の基本案、資産を中央値へ替える案、資産を除く3軸、下位資産を足す5軸、参考画像に近い9軸を比較する。さらに最高額を90%分位点に替えた9軸、資産の90%分位点・中央値・10%分位点を含む8軸を試す。共通軸の算術平均を計算し、金額の軸が全体に占める割合も表示する。軸や基準を切り替えるUIは検討用であり、製品の自由設定機能ではない。

今回の比較では、銀次非遭遇率を外し、目的地なしの6軸（平均順位、収益の平均・P90、資産のP10・中央値・P90）を土台にする。勝率、前戦下位からの入賞率、銀次遭遇試合の平均順位をそれぞれ加えた7軸と切り替えられる。既定の6軸も採用案ではなく、目的地の扱いを比較するための出発点である。勝率は平均順位と重なり、前戦下位からの入賞は選択scope内の試合間の成績であり、試合中の逆転や心理的回復ではない。

銀次遭遇試合の平均順位・入賞率・資産中央値は補助表でも比較する。遭遇回数が何回でも1試合を分母の1件とし、入賞は保存順位1・2位とする。対象0件は値なし、観測された入賞0件は0%と区別する。被害前後の資産・被害額・時刻がないため、実際に取り戻した金額や回復速度を算出したとは扱わない。

### 基準の作成

作品の最初のシーズンを基準作成用、その後を時系列の検証用に分ける。両者の時系列が交差したり、同じ開催が含まれたりする入力は、この試作では拒否する。全記録で作り直す候補は変更前後を比較する例であり、将来の記録での検証とは区別する。

基準作成用の記録を時系列の連続20試合の窓にし、1試合ずつ進めて4人の指標値を集める。各窓は独立した人・試合ではなく、重複する固定4人の実績である。試合数・開催数と窓の値の個数を分け、窓を増やしたことで証拠が増えたとは扱わない。10 / 30試合窓や重複しない20試合窓も比較する。

採点対象は選択した全試合の同じ集計指標であり、直近20試合だけに限定しない。基準側の窓幅により代表値の分布幅が変わるため、窓幅は点数の意味の一部として保存し、件数差による変動も検証する。

平均順位など小さいほど良い値は符号を反転して、以下を高いほど良い方向に計算する。分位点はソート後の位置`(n - 1) × p`を線形補間する。

| 方式 | 2〜10点へ上がる境界 |
| --- | --- |
| `spread` | 中央値を`c`、上側の幅を`Q90 - c`、下側の幅を`c - Q10`として、点数`s`の境界を`c + (s - 6) / 2.5 × 幅`で作る。`s < 6`では下側、それ以外は上側。10点の境界は上側の幅の1.6倍となり、現時点の最高値を超えてもよい |
| `quantile` | `Q5 / Q10 / Q20 / Q35 / Q50 / Q65 / Q80 / Q90 / Q99`。10点の境界は`Q99` |

境界と同値なら高い点を付ける。両端は1〜10へ制限し、4人内での点数の再配分はしない。`Q10 < 中央値 < Q90`が成立しないなど、分布が退化している軸は採点不能にする。表示用の丸めで境界を判定しない。閾値の数値は候補計算後に固定する。

率は100%、平均順位等は1位という理論上の上限を持つ。spread方式では上側の幅を`min(Q90 - c, (上限 - c) / 1.6)`に制限してから6〜10点の境界を作り、満点が理論上到達不能にならないようにする。この調整も未採用の案であり、率の10点が容易になりすぎないかを別途確認する。

最高額は集計試合数と基準作成窓の試合数が違うと更新機会も違う。今回の比較では、その点数と最高額を含む平均を参考表示にし、総合順位を出さない。最高額の指標自体を不適切と断定する規則ではなく、最高額を採用するなら必要な基準設計を明らかにするための制約である。

作品共通、全軸マップ別、順位系は共通で金額・目的地等をマップ別とする案を並べる。全マップ表示には作品共通の基準を使い、マップごとの点数を平均しない。比較用のマップ別案が作れない場合は、自動で共通基準に切り替えず理由を表示する。

銀次を加えた案では、通常の20試合窓では条件対象が足りない場合も検討できるよう、遭遇した試合だけを各人5件ずつ集計する窓で銀次3指標の閾値を試算する。その他の軸は通常の作品共通基準を使い、銀次のマップ別基準は試作していない。基準の窓を3・5・8件に変える診断も用意する。窓は1件ずつ進み、8個以上の値と退化していない分布を必要とする。遭遇の多い人から多くの窓が得られ、観測は重複する。窓の数を独立した標本数として扱わない。この方法や窓幅を採用した決定ではない。

### 件数の暫定ルール

- 通常の基準作成: `max(40, 窓幅×2)`試合以上、8開催以上。条件付き指標の窓には10件以上の条件対象を必要とする。銀次の追加試算は前述の遭遇試合窓を別に使う。これらは比較用の仮設定であり、条件付き指標が一般に採点不可能という結論にはしない。
- 点数: 3試合以上。0件は対象なし、1〜2件は元の値のみ。
- 総合順位: 4人の全軸が40試合以上・8開催以上で採点できる場合だけ表示。それ未満の算出可能な点数・総合点には参考と付ける。中央値型の採用後に少数例の感度を見直した暫定案であり、順位が安定する保証ではない。
- 表示上同じ総合点は同率。1位が2人なら次は3位。欠けた軸を補完したり、個人ごとに平均の分母を変えたりしない。

これらは利用上の下限案であり、信頼区間や統計的な有意差の条件ではない。開催を1つずつ除く感度を、基準作成側と採点対象側で別々に確認する。点数順の変化には同率の発生・解消も含まれる。

### 見直し目安の暫定案

冬の作品共通基準で、その後の記録を20試合ずつ重複なく区切る。同じ軸で4人中3人以上が9点以上になる状態が2区間連続し、その40試合が8開催以上にわたるとき、基準の見直しを提案する。完成した直近2区間を使い、端数の追加で判断対象をずらさない。基準と対象記録から判断材料の識別子を作る。

単発の満点、1人の継続的な好成績、異なる軸で一度ずつ起きた高得点は、この目安に該当しない。不足時は判断用の追加記録が足りないと表示する。画面で実データの状態と手計算例を区別する。基準の自動変更は行わない。

適用範囲ごとの監視、保留後の再表示、別の見直し理由との組合せは採用前の決定事項。試作では冬の作品共通基準の目安を検証しており、管理操作で仮適用した候補の監視と混同しない。

## 出力と確認

`report.json`には取得元・時点、指標と分母、実在する比較条件、各基準の境界、各人の点数・総合点・順位、全候補の件数充足、窓幅・重み・開催除外の感度、後の期間での上限集中の状態を保存する。銀次には条件対象試合の根拠、遭遇窓での追加基準・評価、窓幅の診断を含む。比較条件の数は入力に依存する。既存4軸の感度と上限集中の対象は`diagnosticAxisSet`、追加案の開催除外は`profileDiagnostics`に記録し、未検証の軸へ診断結果を流用しない。

管理操作の例では最後の1試合を除いた記録で候補を作り、その試合が追加された前後を同じ候補で比較する。記録訂正・失敗・再試行・取り下げ・直前基準への復帰は、入力の見せ方を確認する模擬状態である。認可、非同期Worker、同時更新制御の本番実装を検証するものではない。

自動テストは、保存順位・同値収益・条件機会なし、負の資産、境界の同値、上限への外挿、同率、参考値、基準不足、入力不整合を手計算可能な例で確認する。表示と操作の確認にはPlaywright MCPを使う。自動操作の成功を、利用者自身が意味を理解できた証拠にはしない。

時間の前後を分けて評価する原則は [Forecasting: Principles and Practice](https://otexts.com/fpp3/tscv.html) を参照した。本試作は勝者予測の精度検証ではなく、固定した採点基準が後の記録へどう作用するかを見るもの。具体的な窓幅、係数、必要件数が同資料で実証されたとは扱わない。
