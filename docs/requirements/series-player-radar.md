# プレーヤーレーダー比較 要求仕様

状態: 実データ試作を進め、作品共通の採点基準を採用。参考画像に近く成績の特徴が見える構成を探り、目的地を外す・別指標へ替える案と銀次遭遇試合の成績を比較中。採用軸・採点式・必要件数は未確定。機能実装・公開は未実施。

対象: [MOM-29](https://linear.app/ponta/issue/MOM-29)。評価軸・採点方式・マップ別基準の先行検証は [MOM-30](https://linear.app/ponta/issue/MOM-30) で行う。戦績比較の追加機能として扱う。

## 1. 目的と確定要求

- 複数の観点でプレーヤーの成績を点数化し、レーダーチャートで各人の特徴を比較できるようにする。
- 各軸で成績の強み・弱みを比較し、その平均点で4人の総合的な強さも順位づけする。各軸は外側ほど良い成績を表す。
- 総合評価は複数の成績をどう評価するかを定めた尺度であり、実際の平均順位・勝率と異なる順位を許容する。ただし、両者の関係が納得できるかは試作で検証する。次戦の勝者や観測していない能力を予測・断定するものにはしない。
- 評価指標は、プレーヤーの行動による成績を反映しやすいものを一から検討する。参考として提示された手動採点表の指標・閾値・軸数を、そのまま採用する要件にはしない。
- 現在取得している記録、そこから算出済みの各種指標、新たに算出する派生指標を幅広く候補に含める。OCRで得られる結果情報を超える新たな試合中の事実は、今回のために取得しない。
- 全試合の代表値に加え、収益トップ時の勝率、低収益時の入賞率、下位後の復帰など、条件付きの成績も試作する。レーダーには4人の日常的な比較が成立しやすい少数の軸を優先し、稀な条件付き指標は詳細分析に位置づける。
- 作品内の固定4人を比較し、シーズン・マップで絞り込めるようにする。
- 採点の閾値は作品ごとの記録から自動計算し、作品内で共通にする。マップを絞っても同じ指標値は同じ点数にする。シーズン・マップの絞り込みへの対応と、採点基準の単位は分けて扱う。
- マップによって戦い方が異なることを考慮し、特定の稼ぎ方・行動を選ぶほど有利になる指標への偏りを減らす。同時に、単なる成績の要約よりも参考画像に近く各人の特徴が見える構成を優先する。収益・目的地を一律に除外する要求にはしない。
- 目的地到着は戦略によって選ばない場合もあるため、目的地を除いた案と他の指標へ替えた案を比較する。銀次系を採用するなら非遭遇率よりリカバーを重視し、「遭遇した試合でも最終的に好成績で終えられたか」を代理指標として検討する。レーダーへ採用する指標と必要件数は試作で決める。
- 閾値は毎回の集計では更新しない。管理者が必要なタイミングで計算・更新できるようにする。
- 固定基準に対して好成績を伸ばし、満点を含む特徴的な形を表せるようにする。一方、満点が容易になりすぎたときは基準を見直せるようにする。
- 満点は基準作成時の記録に照らしてかなり好成績な水準とする。達成者がいない軸も許容し、各軸で4人の誰かを必ず満点にしない。理論上の最高成績だけを満点にする要求でもない。
- 基準更新後は過去シーズンも新基準で採点し、使用基準を表示する。過去に見た点数が変わることを許容し、初版では当時の点数への切替を要求しない。
- 各軸を1〜10点で表示し、4人分を同じ軸・目盛りで個別に並べる。平均点とその総合評価順位はグラフの軸へ追加せず、別のテキストとして表示する。順位は図形の面積から求めない。
- 総合評価順位は4人全員を同じ条件で十分に採点できる場合だけ表示する。少数例の参考順位や、採点可能な人だけの順位は出さない。
- システムが基準見直しの目安を表示し、管理者が基準候補の計算、変更前後の確認、適用を行う。目安に達しただけでは基準を自動変更しない。

## 2. 既存機能との境界

| 関心事 | 正本・前提 |
| --- | --- |
| レーダーの目的、評価指標、採点、基準の更新 | 本書。未決部分は実装要件として扱わない |
| 固定4人、作品・シーズン・マップ、確定試合、金額・順位の意味 | [戦績比較](series-comparison.md)、[ドメインルール](../domain-rule.md) |
| 非同期計算、成果物の一括公開、状態、権限、互換性 | [分析バッチ](series-analysis-batch.md) |
| 画面の共通要件、品質証拠、変更gate | [UI規約](../ui-rule.md)、[テスト・品質規約](../test-rule.md)、[開発作業規約](../dev-rule.md) |
| 保存形式、API、成果物の構造 | 実装時にmomo-db、Tapir、JSON Schemaで定義する |

現在の分析入力には、各試合の4人分の順位・総資産・物件収益・事件簿6項目と、開催・作品・シーズン・マップ・オーナー・番手がある。事件簿は目的地、プラス駅、マイナス駅、カード駅、カード売り場、スリの銀次の回数である。

カードの種類・使用順、移動経路、購入機会、銀次に遭遇する機会の総数は記録していない。保存値から新たな行動ログを推定したり、事件簿の合計を総行動回数に見立てたりしない。

既存の試合追加・訂正・削除による分析更新と、今回追加する採点基準の更新は別の意味を持つ。通常の分析更新で採点基準を暗黙に作り直さない。

初版では、重ね描き、利用者による軸・重み・閾値の編集、過去基準への表示切替、作品間ランキングを追加しない。レーダーに採用しない指標のために新しい詳細画面を一通り作ることも、今回の必須範囲には含めない。既存の詳細分析で読める指標は、その場所を利用する。

## 3. 採用軸と検討候補

### 現在の選定状況

最初に次の4軸を試し、資産については平均より中央値を使う方針を選んだ。利用者が改めて表示を確認した結果、4軸案は候補に残してよいが、単なる「まとめ」に寄り、参考画像に近い方向をさらに探ることになった。収益・目的地は残してよい。軸数の削減を次の方針として確定せず、上側・普段・低い側の成績を含む構成を比較する。下表全体を確定済みの軸構成として扱わない。

| 軸 | 元の指標・式 | 良い方向・意味 |
| --- | --- | --- |
| 平均順位 | 保存済み順位の合計 / 対象試合数 | 小さいほど良い。最終成績を評価する |
| 総資産の中央値 | 対象試合の総資産を昇順に並べた中央の値。偶数件では中央2値の平均 | 大きいほど良い。大勝を含む平均獲得額より、普段残せる資産の水準を評価する。負値を保持する |
| 平均物件収益 | 物件収益の合計 / 対象試合数 | 大きいほど良い。収益の水準を評価し、購入判断そのものを推定しない |
| 目的地の平均到着回数 | 目的地到着回数の合計 / 対象試合数 | 大きいほど良い。1試合での複数回到着も数え、到着した試合の割合とは区別する |

平均と中央値を併用する場合はそれぞれの役割を説明し、独立した強みとして暗黙に加算しない。平均順位・勝率・最下位回避などを増やす場合も、勝敗が平均点に占める比重を確認する。稀な条件付き成績は詳細分析の候補に残す。採用後の軸構成は条件・人物ごとに変えない。

追加の試作では、元画像に近い9軸、最高額を90%分位点へ替えた9軸、資産の90%分位点・中央値・10%分位点を含む8軸を比べる。分位点は高い側・低い側の境界であり、その範囲の試合の平均ではない。最高額の試合数依存、銀次非遭遇の意味、資産・収益の軸数が平均点に占める比重を併せて確認する。同系統の指標を併用する場合は役割と実質的な重みを説明し、採用を決める。

その後の指摘を受け、銀次非遭遇率を新しい比較案から外し、遭遇した試合の最終成績を別に確認する。目的地なしの案は平均順位、収益の平均・P90、資産のP10・中央値・P90を比較用の土台とし、勝率、前戦下位からの入賞率、銀次遭遇試合の平均順位を加えた案を並べる。この6・7軸は比較用であり、軸数の削減や金額中心の構成を採用した決定ではない。勝率は平均順位との重複、前戦下位からの入賞率は条件機会の有無、銀次は少数例による採点・順位の制約を確認する。

銀次について記録されているのは試合ごとの遭遇回数と最終成績であり、被害時刻・被害額・被害前後の資産はない。「遭遇した試合で最終的にどの成績を残したか」を試算し、実際の回復額・回復率・回復速度とは表示しない。入賞率、平均順位、最終資産の中央値を対象試合数と共に示す。同一試合で複数回遭遇しても条件対象は1試合とし、非遭遇者を満点にしない。非遭遇試合との成績差も、元の強さや遭遇条件が混ざるため、銀次の因果効果とは扱わない。

### 検討した候補と注意

確定した「成績の強み・弱みを、外側ほど良い点数で表す」という目的に対する候補とする。既存指標と新しい派生指標の両方を検討し、全候補をレーダーへ並べることは要求しない。既存指標の意味は [戦績比較](series-comparison.md#5-metric-semantics) と現在の計算経路を確認して使う。

| 候補 | 検討する指標 | 判断上の注意 |
| --- | --- | --- |
| 最終成績 | 平均順位、勝率、入賞率 | 保存順位を使う。平均順位は小さいほど良い。似た順位指標を多数の独立した強みとして扱わない |
| 資産形成 | 平均・中央値の総資産 | 負の資産を保持する。順位との重なりがある |
| 大きな資産を残す成績 | 総資産の上位側分位点（既存P90など） | 最高額との違い、少数例での不安定さを比較する |
| 資産の下振れ | 総資産の下位側分位点（既存P10など）、新たな損失側の集計 | 平均資産との重複を検証する。小標本での極端値をそのまま能力に読み替えない |
| 収益確保 | 平均・中央値の物件収益、平均物件収益順位 | 金額と試合内順位は意味が異なる。物件の購入判断そのものを観測した値ではない |
| 目的地獲得 | 到着回数の1試合平均、1回以上到着した試合の割合 | 回数と試合割合を区別する。回数は1試合で複数になり得る |
| 収益トップ時の勝ち切り | 収益最大値と同値だった試合の勝率 | 既存のトップ条件は同値を含む。全員同値・収益0の扱いも試作で確認し、途中の優勢を観測したように表現しない |
| 低収益時の入賞 | 物件収益順位が2.5より下位だった試合の1・2位率 | 既存の条件付き成績を候補にする。条件を満たした試合数が分母 |
| 目的地なしの成績 | 目的地到着0回の試合の平均順位・入賞率 | 到着しなかった理由や、その後の逆転を推定しない |
| 銀次遭遇試合の成績 | 銀次1回以上の試合の平均順位・入賞率・総資産中央値 | 平均順位は既存値、入賞率・資産中央値は派生候補。回復を考える代理指標であり、遭遇後の回復経路は観測していない |
| 下位後の復帰 | 選択scope内の前戦3・4位から次戦1・2位への率 | 既存の試合間遷移を使う。試合中の逆転や心理的な切り替えとは区別する |
| 銀次への非遭遇 | 銀次0回の試合数 / 対象試合数 | 以前の比較案に残すが、新しい案では優先しない。遭遇機会や回避行動を記録していないため、「回避能力」とは断定しない |

選定時は、何を良い成績とするかを説明できること、別の軸と役割が重なりすぎないこと、4人全員の対象件数が確保できること、基準固定後も意味を保つことを確認する。軸数を先に埋めるために弱い候補を採用しない。採用軸・軸順・重みは作品内の比較で固定し、絞り込みやプレーヤーごとに採点可能な軸へ入れ替えない。

例えば、一度も下位にならない人には「下位後の復帰」の機会がない。その人だけ総合評価から外れてしまう構成は、日常的な比較という目的に適さない。軸ごとの採点可能率だけでなく、4人の全軸が同時にそろう条件と頻度を選定に使う。

次の既存値も検討対象には含めるが、そのまま「高いほど強い」軸へ変換しない。

- 順位のばらつき、番手間の差、目的地依存度: 差が小さくても、すべての条件で成績が低い場合がある。
- 物件収益順位と最終順位の差、目的地順位と最終順位の差: 最終順位が同じまま収益・到着成績だけが下がっても値が上がり得る。
- 物件収益÷総資産: 総資産が下がることで比率が高まる場合があり、総資産0以下では対象外になる。
- カード売り場・カード駅・プラス駅・マイナス駅の回数: 多寡と良い結果の関係を決めずに採点しない。関連する条件付き成績や補助説明への利用も検討する。
- 高度分析のモデル出力、行動仮説の選定score、品質・信頼度: 観測された成績そのものの尺度とは区別する。

最高額は試合数による更新機会の差、平均と中央値の併用は同じ性質の重複を検討する。基準を固定しても、元の指標が毎回変わるscope内の相対基準に依存すれば評価の意味が変わるため、その依存も確認する。

## 4. 採点基準の作成・更新

- 採点基準を作品共通の保存済みデータとして持ち、各人の集計値をその基準で採点する。
- 比較中の4人の最大・最小値だけから点数を引き伸ばす方法は避ける。表示中のscopeからその都度閾値を生成せず、その作品の保存済み基準を選ぶ。マップの選択や追加によって別の基準へ自動で切り替えない。
- 基準作成には、採点対象と同じ意味の集計値を使う。例えば、1試合の金額分布と複数試合の平均金額分布を混同しない。
- 基準候補の計算、変更前後の閾値・点数の確認、適用を区別する。候補計算だけで現行表示を変えない。
- 基準の識別子、対象作品、軸構成・重み・指標定義、計算方法、元にした記録の範囲、作成・適用時点を追跡できるようにする。
- 基準更新後の点数と基準を一緒に公開する。候補計算中や失敗で、公開中の基準・点数を部分的に置き換えない。
- 満点の出現だけを不具合や更新理由にしない。見直す目安と、その判断に使う対象期間・件数を別途定める。

### 管理者の操作

1. 管理画面で対象作品の適用中の基準、作成時の記録範囲・件数、見直しの目安を確認する。
2. 管理者が基準候補の計算を依頼する。初回は基準未作成として扱い、必要件数を満たさなければ不足条件を示す。
3. 計算後、同じ評価対象記録での4人の点数・総合点・総合評価順位の変化、順位を出せなくなる条件、適用範囲を確認する。詳細で各閾値と算出方法を照合できるようにする。初回は変更前の点数を作らない。
4. 管理者が候補の適用を依頼する。候補を作っただけでは適用しない。数値を直接手入力する閾値編集は初版の対象にしない。
5. その基準を使った対象作品の必要なscopeを計算し、成功した点数と基準を一緒に公開する。受付・計算中・適用済み・失敗を区別する。

候補を作る記録集合と、変更前後を比べる評価対象記録を保存し、それぞれの時点・範囲・件数を示す。変更前後は基準の違い以外の入力を揃え、「採点基準の変更による差」として示す。確認後の変更は次のように扱う。

| 確認後の変更 | 必要な対応 |
| --- | --- |
| 候補作成元の集合に含まれない試合の追加 | 保存済みの候補を維持する。追加があったことを示し、最新の記録で変更前後の比較を更新して再確認する。追加のたびに候補の閾値を作り直さない |
| 候補作成元の試合の削除、成績・所属・対戦順等の計算に影響する訂正 | 影響を受ける候補を無効にし、理由を示して作り直す |
| 評価対象だけに含まれる試合の訂正・削除 | 候補の閾値を維持し、比較結果を更新して再確認する |
| 軸・重み・指標定義・採点方式・適用範囲の変更 | 候補を無効にし、変更後の定義で作り直す |
| 別の管理操作で適用中の基準が変更された | 互換性を確認し、現在の基準との比較を更新して再確認する |

計算に影響しない表示名等の変更は、候補の無効化理由にしない。適用の受付時には確認した比較結果が現在も有効かを検証し、二重操作や再送で同じ候補を重複適用しない。受付後の試合追加は、新基準による分析更新へ引き継ぐ。記録が増えるたびに承認済みの適用をやり直す必要はない。一方、公開までに作成元の訂正や定義変更等で候補が無効になった場合は、適用を止めて旧基準を維持し、再確認が必要な理由を示す。

画面を離れても処理・候補・確認状態を失わず、管理画面へ戻って続けられるようにする。未適用の候補は取り下げられ、公開中の基準と点数を維持できる。通信失敗時は処理状態を確認してから再試行する。適用後に直前の基準へ戻す場合も、現在の定義との互換性と作成元記録の有効性を確認し、同じ比較・適用手順で現在の記録を再採点する。試合記録そのものは巻き戻さない。

計算中・失敗時は直前に成功した基準と点数を維持する。一度も基準作成に成功していなければ採点値を出さず、既存の戦績比較は継続して利用できるようにする。権限・非同期実行・部分公開の禁止は [分析バッチ](series-analysis-batch.md) に従う。

### 見直しの目安

満点付近への集中を中心に、初回作成に必要な記録の蓄積、基準作成元の記録訂正、対象マップの追加など、基準を確認する理由を管理者へ示す。目安は判断材料であり、更新の強制や自動適用の条件にはしない。見直しが必要か確認するために、毎回新しい閾値を生成することはしない。

試作では、どの記録集合のどの軸を、どれだけの期間・件数で観測するかを定める。1人の好成績や1回の満点を、基準が易しすぎる根拠にはしない。対象件数が足りない場合は、問題なしと判断せず「判断に必要な件数が不足」と区別する。

見直しの目安は管理画面に理由と根拠の件数・期間を示す補助情報とする。通常の比較画面に警告を繰り返さず、同じ根拠を新しい問題として再通知しない。「今の基準を継続する」判断を許容し、過去の最高点を取り消すための更新作業にしない。基準作成元の訂正等による確認事項と、満点付近への集中による任意の見直しは区別する。

基準の計算方法自体を変更する場合は、単なる再採点と区別して指標・採点方法の版を進める。基準の適用範囲や軸定義との互換性を確認せず、古い閾値へ新しい意味を与えない。

### 更新後の過去期間

過去シーズンも現在適用中の基準で採点することは確定要求とする。新しい基準と、その基準で採点した過去・現在の各scopeを一組として表示する。元の記録が同じでも基準変更で点数が変わり得るため、使用した基準、基準の適用範囲、元の指標値を確認できるようにする。画面では基準の適用日・対象範囲を読める名前で示し、内部の識別子だけを見せない。基準変更による差を成績の向上・低下として扱わない。

基準の版と指標の計算方法の版は区別する。試合の追加で更新される分析入力の版を、採点基準の版として扱わない。通常の作品再計算や画面の表示更新を、採点基準の見直し操作に読み替えない。

### 分析成果物との接続

基準の識別子・内容を計算入力と成果物の来歴に含める。同じ試合入力・algorithm versionであっても、採点基準が異なる結果を同じ再利用対象として扱わない。基準変更で結果が変わったことを、既存の非決定性検出で誤判定しない契約にする。

API・Webで採点、総合点・総合評価順位、見直し目安を補完計算しない。基準切替前の計算が遅れて完了しても、異なる基準の点数を現在のものとして公開しない。計算中に旧結果を表示する場合は、その結果の基準表示も維持する。具体的な保存形式・versionの接続は実装設計で定義し、[分析バッチ](series-analysis-batch.md) の公開・再利用・互換性の契約へ反映する。

## 5. 試作で確定する事項

[MOM-30](https://linear.app/ponta/issue/MOM-30) は本機能の実装前に、次の比較から採用案を決める。[再現用の試作](../../scripts/experiments/player-radar/README.md)で既存記録の集計、時期を分けた基準作成・検証、軸・採点方式・マップ単位の比較と表示・管理操作の確認を進めている。実データと測定結果は公開文書へ含めない。

本番の確定記録を読み直した試算を利用者が確認できるようにする。試作画面には取得時点、作品・対象期間・件数、採点基準を作った記録の範囲を明示し、元の値と根拠の試合を照合できるようにする。取得日時と基準作成に用いた期間を混同しない。本番の記録や基準を変更せず、実データを含む成果物はローカルの非公開領域に置く。

作品共通基準を合意し、参考画像に近く成績の特徴が見える構成を追加検討している。資産中央値を選んだ経緯は引き継ぐが、4軸への固定や収益・目的地の除外を合意したとは扱わない。最終的な軸構成と平均点への比重、基準生成の式、集計窓・必要件数、記録不足の作品での扱い、見直しの目安は未確定。試作の数値をそのまま実装要件にせず、表示の自動確認と利用者自身の読解・採用判断も区別する。

### 評価軸と採点方式

- 各候補について正確な式、分母、良い方向、同値の扱い、必要件数、対象なしの条件を明らかにする。
- 条件付き指標は4人それぞれの条件対象件数を示す。対象0件、観測値0、参考値を区別し、採点不能を0点・満点・中間点で補わない。
- よく使うシーズン・マップの絞り込みごとに、4人の全軸を十分な件数で採点できるかを調べる。常に好成績な人に条件対象が発生しない例も含め、総合評価が頻繁に消える軸構成は採用しない。採点・参考表示・総合順位表示に必要な件数の条件を決める。
- 採点の元となる観測単位と期間を固定する。各人の通算値4点、開催別値、一定試合数の集計値などでは分布の意味が異なるため、採用理由を説明する。
- 指標同士の関連、軸の重複、少数例、特定の開催・極端値を除いた場合の変化を確認する。相関があるだけで機械的に採否を決めない。
- 閾値を作る記録と、その後の評価用記録を時系列で分けて試す。同じ試合を両方に含めた集計窓で検証せず、開催のまとまりも考慮する。重なる集計窓や同じ4人の反復値を、独立した多数のプレーヤーの実績と見なさない。基準に使用した記録への当てはまりだけで、将来も適切に採点できると判断しない。
- 1人だけ突出する例、全員近い例、上限へ達する例、条件対象なし・少数例を含める。差の小ささを失敗として扱わず、特徴的な形を作るために値を加工しない。

### 平均点による総合評価

各軸を等しい重みで平均する案を出発点とし、「資産の軸を増やすだけで資産が総合評価を支配する」といった重複を、採用軸の選択で解消する。相関だけでなく、何を独立した評価観点として数えるかを先に説明する。

- 軸の採否・重み・閾値の妥当な変更で総合評価順位がどれだけ変わるかを確認する。変更に敏感な結果を、安定した強さの差として提示しない。
- 点数1段階の差を平均上は同じ重みで扱う意味と、ある観点の弱さを他の観点の高さで補える意味を確認する。整数化による同点・近接も含め、見かけだけ細かい順位を作らない。
- 同じ記録での平均順位・勝率と総合評価順位を並べ、一致する例・異なる例の両方を確認する。「総合点が高い人は勝敗でも強い傾向がある」という期待を検証するが、特定の人や既存の順位に合わせるために重み・閾値を調整しない。
- 単純平均で目的を満たせない場合は、理由と代案を利用者に示して決め直す。重みづけや別の集約式を暗黙に導入しない。採用する計算規則は実装前に一つへ確定する。

### 作品共通基準とマップ別基準

同じ評価対象記録で両案を比較し、利用者は作品共通基準を選んだ。マップ別の点数差を埋めるために基準を分けるのではなく、戦い方への偏りが少ない指標を選ぶことを優先する。比較に使った観点を下表に残す。

| 判断対象 | 試作で示すもの |
| --- | --- |
| 作品共通基準 | マップ別の元の値・点数分布、上限・下限への集中、件数、対象シーズン |
| マップ別基準 | 共通基準からの点数差、各基準に使える件数、少数例での閾値変動 |
| 条件の混在 | マップとシーズン・開催・記録件数の偏り。観測差をマップの因果効果とは扱わない |
| マップ未指定 | 総合成績として何を採点するか。異なる基準の点数を根拠なく平均しない |
| 新規マップ・記録不足 | 基準作成前の状態、共通基準を使う条件の有無、採点できない場合の表示 |

採用方式では、全マップ・個別マップ・新規マップに同じ作品共通基準を使い、全マップの元指標を改めて集計して採点する。異なるマップの点数を平均しない。作品自体の基準が未作成なら採点せず、元の集計値を表示する。マップの記録が少ない場合は採点対象の件数規則で参考表示・順位非表示を判断する。

### 利用者が読めるかの確認

実データによる4人の比較と、誤解を起こしやすい手計算可能な例を、PC・mobile相当の大きさで示す。レーダーと数値表を用い、説明者の口頭補足に頼らず次の判断ができるかを確認する。

1. 4人の同じ軸の強み・弱み、総合点、同率の順位を区別する。
2. 平均順位・勝率と総合評価順位が異なる理由を、指標の内訳から説明する。
3. 条件対象0件、観測値0、少数例を区別し、順位が表示されない理由と、選べる比較条件を把握する。
4. 元の成績が同じでも基準更新で点数が変わることを把握し、成績自体の変化と区別する。
5. 管理者が候補の計算から比較・適用まで進み、新しい試合の追加、記録訂正、失敗後の再開を扱える。

「説明すれば分かる」「4枚の図が描ける」だけで完了にしない。読めなかった箇所は表示・名称・既定動作を見直し、結果と残る制約を記録する。実データ不足による未検証と、手計算例で確かめた挙動を区別する。

### 試作の成果物

- 元の集計値、件数、基準、点数・総合点・総合評価順位を照合できる4人分の比較例。
- 採用軸と不採用理由、4人の比較が成立する範囲、採点式・境界・同値・負値・対象なし・総合順位の規則。
- 基準の単位、初回作成条件、見直しを判断する対象期間・件数・目安。
- 総合評価の重複・感度と実際の平均順位・勝率との関係、PC・mobileでの読解・管理操作の確認結果。
- 利用者が比較例を確認したうえでの採用案。結果を本書の確定要求・受入条件へ反映する。

## 6. 表示と読み方

### 比較への入口と情報の順序

既存の戦績比較「今の差」に「プレーヤーレーダー」の区画を置く。比較条件と対象試合数、4人のレーダーと総合点・総合評価順位、数値による内訳、算出方法の順に読める構成とする。比較のためだけに新しい全体ナビゲーションや独立した設定画面を作らない。

作品・シーズン・マップ、使用基準の適用日・対象範囲、参考値など判断に必要な状態は、方法説明を開かなくても分かるようにする。詳細へ移動して戻っても、既存のURL復元・focusの規則に従って比較条件と読み位置を維持する。集計全体の点数に、特定の1試合だけで説明できるような目印を付けない。

### レーダーと数値表

- 各軸は1〜10の整数点とし、4人に共通の軸順・向き・大きさ・尺度・適用基準で個別に表示する。中心を0、外周を10に固定する。0は作図上の基点であり、採点結果や欠測の代用値にはしない。
- 軸順と4人の並び順を固定する。点数順で軸を並べ替えたり、順位変化のたびにプレーヤーの表示位置を動かしたりしない。順位は名前と総合点に添えて伝える。
- 点と線で各軸の値を読み取れるようにし、平滑化や塗り面積の大きさで総合評価を伝えない。広い画面では4人を並べ、狭い画面では1人ずつ読める配置にする。
- 「数値で比較」から、同じ軸の4人分の点数・品質を一度に照合できる表に到達できるようにする。mobileでも前の人の値を記憶して比較するだけの構成にしない。行・列見出しで軸とプレーヤーの対応を示し、必要なスクロールは表内に収める。
- 各軸から元の指標値、単位、分母、採点の境界、算出方法へたどれるようにする。キーボード・タッチ・支援技術で同じ情報へ到達でき、hoverだけに値や注意を置かない。色だけで名前・値・品質を区別しない。
- 基準の境界判定は表示用に丸める前の値で行う。整数点の具体的な境界は試作で決め、原指標と点数を同じ値として扱わない。
- グラフに描けない軸を0点や中間点で埋めず、欠けた頂点をまたいで閉じた図形を作らない。軸ごとの値と理由は数値表で確認できるようにする。

### 総合点と総合評価順位

総合点は採用した全軸の算術平均を基本案とし、各人のグラフ外へ「総合点（各軸の平均）」として表示する。これは複数観点で評価した成績の順位づけに使う値であり、図形の面積ではない。軸を増やすことによる二重評価と点数段階の意味を5節で検証し、実装前に計算規則を確定する。合計点を重複して表示する要求はない。

- 等しい重みの案では各軸の整数点を合計し、固定の採用軸数で割る。総合点は小数第2位まで表示し、内訳から再現できるようにする。
- 総合評価順位は総合点の高い順とし、表示上同じ点数は同率とする。同率1位が2人なら次は3位とし、隠れた小数桁、別の成績指標、名前順で同率を解消しない。この表示順位は既存の指標内で計算する値順位とは区別する。
- その人に一つでも採点不能の軸があれば総合点を表示せず、採点済み軸数と理由を示す。利用可能な軸だけで分母・重みを変えない。全軸の点数を算出できても参考値を含むなら、総合点も参考値とする。
- 4人全員の全軸が同じ定義・適用基準で、試作で定めた十分な件数を満たす場合だけ順位を表示する。1人でも参考値・採点不能があれば4人の総合評価順位をすべて出さず、理由を示す。採点できる人の軸・総合点まで隠す必要はない。
- 実際の「平均順位」「勝率」とは別の名称・表示とし、それらが良い人と総合点が高い人の違いを内訳で説明できるようにする。小さな総合点の差を統計的な優劣や次戦の勝ちやすさとして断定しない。
- 軸構成・重み・指標定義や適用基準が異なる総合点を、同じ評価内容の増減として扱わない。過去シーズンと比較する場合も現在の同じ定義・基準で採点する。

### 表示できないとき・更新中

| 状態 | 利用者に伝えること・できること |
| --- | --- |
| 対象試合なし | 選択条件に試合がない。比較条件を変更できる |
| 条件対象なし・件数不足 | 該当軸の対象件数と不足理由。範囲を広げる選択肢がある場合は条件変更へ進める。観測値0やシステム障害として扱わない |
| 基準未作成・適用できる基準なし | その範囲はまだ採点できない。既存の集計値は読める。管理者には作成条件と操作への入口を示す |
| 更新中・更新失敗、以前の結果あり | 直前の結果とその基準・時点を示し、最新結果との違いを明確にする。既存の訂正済み試合に対する古い分析の非表示規則は維持する |
| 更新失敗、以前の結果なし | 採点結果を出さず、状態と次に取れる操作を示す。再読込・再試行は既存の権限と更新の規則に従う |

少数例や基準未作成は通常起こる状態として示し、エラーの強調を乱用しない。表示の読み方に内部用語のscope・artifact・versionを要求しない。

## 8. 受入条件

以下は本機能の実装時に満たす条件である。具体的な採点式・件数・マップの扱いは5節の試作結果で補完する。今回の文書作成により、機能の動作検証まで済んだとは扱わない。

| ID | 受入条件 | 実装時に選ぶ証拠 |
| --- | --- | --- |
| R1 | 新たな試合中の事実の入力を要求せず、保存済み記録から基礎・派生指標を再現できる。各軸の式・分母・良い方向を説明できる | 試作の比較例、計算経路の手計算可能な例 |
| R2 | 作品・シーズン・マップの選択に従って4人を比較できる。採点基準の適用範囲を表示し、マップ未指定・新規マップ・基準不足も試作で決めた規則に従う | scopeと基準選択の契約、画面操作 |
| R3 | 同じ指標定義・指標値・適用基準なら同じ点数になる。良い方向へ元の指標値だけを変化させた場合、点数が下がらない | 境界値・同値・単調性・決定性の計算証拠 |
| R4 | 全員が満点未満でも正常に表示し、基準作成後に満点へ達する成績も表現できる。比較中の4人へ点数を強制配分しない | 基準固定前後の具体例 |
| R5 | 通常の試合追加・訂正・削除や通常の再計算で採点基準が変わらない。固定基準のまま対象の指標・点数を更新する | 記録更新から保存済み成果物までの接続 |
| R6 | 基準の更新後は過去シーズンも新基準で採点され、元の値と使用基準の適用日・範囲を確認できる。異なる基準を混在させず、基準変更だけによる点数差を成績変化として示さない | 基準切替と過去scopeの接続、表示の確認 |
| R7 | 条件付き指標は各人の条件対象件数を示す。負値、観測値0、対象なし、少数例、基準未作成を区別し、採点不能を0点・満点・中間点で補わない | 分母と品質状態の計算・表示 |
| R8 | 管理者以外が採点基準を更新できない。計算中や失敗で公開中の基準・点数を部分的に置き換えず、基準と点数を一緒に切り替える | 認可、非同期計算、公開・失敗経路 |
| R9 | グラフと元の集計値・件数・採点基準を照合でき、数値表で同じ軸の4人分を比較できる。PC・mobile・キーボードで読め、色やhoverだけに情報を置かない | component、Playwright MCPによる読解・操作確認 |
| R10 | API・Webは保存済みの採点結果を読み、通常表示で採点や閾値を再計算しない。既存比較と同じ成果物・更新状態を扱う | 成果物契約、読み取り境界、変更したconsumerの検証 |
| R11 | 各軸を1〜10点とし、中心0・外周10、共通の軸順・大きさ、固定のプレーヤー順で4人を表示する。採点不能を別の値で埋めたり、図形の面積を総合点にしたりしない | 保存済み点数と表示の対応、PC・mobileの読解確認 |
| R12 | 全軸が採点できたときだけ、試作で確定した計算規則による総合点を表示する。採点不能では出さず、参考値を含めば参考とする。人ごとに利用可能な軸へ分母・重みを変えない | 手計算可能な総合点と欠測・参考状態の例 |
| R13 | 見直しの目安を理由・件数・期間とともに管理者へ示す。単発の満点、目安到達、候補計算だけで基準を変えず、管理者が同じ記録での変更前後を確認して適用できる | 管理画面から候補計算・確認・適用までの操作 |
| R14 | 確認後の変更を4節の規則で扱う。通常の追加で候補を作り直さず比較を更新し、作成元の成績訂正・削除等では再生成する。二重操作・再送が重複適用や世代の混在を起こさない | 保存・公開境界の競合、候補と比較の有効性、冪等性の検証 |
| R15 | 4人の全軸が同じ条件で十分に採点できたときだけ総合評価順位を出す。同じ表示点は同率とし、実際の平均順位・勝率と区別する | 全員十分、1人だけ参考・採点不能、同率、勝敗と異なる順位の例 |
| R16 | 軸構成が日常的な4人比較を妨げず、総合評価の重複・感度、実際の成績との関係、マップごとの意味を試作で確認し、利用者と採用案を決めている | 5節の試作成果と読解課題の確認結果 |
| R17 | 比較条件・読み位置を維持して詳細から戻れ、未作成・不足・更新失敗の理由と次の操作を区別できる。管理操作は画面を離れても再開でき、候補の取り下げ・再試行・互換な直前基準の再適用を扱える | 空状態、遷移、失敗・復帰、再適用の操作確認 |

品質証拠は [テスト・品質規約](../test-rule.md) から選び、[Change Gates](../dev-rule.md#4-change-gates) に割り当てる。各行をすべての層で重複検証する要求ではない。

## 9. 設計上の根拠

- 総合指標は、同じ重みでも軸の選び方で実質的な重みが変わり、重複や集約方法によって順位が変わり得る。評価観点を定義し、感度を確認する根拠とする。[OECD・EU・JRC『Handbook on Constructing Composite Indicators』](https://www.oecd.org/en/publications/handbook-on-constructing-composite-indicators-methodology-and-user-guide_9789264043466-en.html)
- レーダーの面積は軸の並び順に依存する。軸順を固定し、総合点は別に計算する。[Duanら, 2023](https://pure.johnshopkins.edu/en/publications/origami-plot-a-novel-multivariate-data-visualization-tool-that-im/)
- グラフの内容には利用できるテキスト表現も必要である。同じ値を表で照合できる要件へ適用する。[W3C WAI: Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
- 状態の可視化、記憶に頼らない比較、取消・復帰、必要な情報から詳細へ進む構成を採用する。[Nielsenの10原則](https://www.nngroup.com/articles/ten-usability-heuristics/)、[Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- 少数例や未作成などの通常状態を重大なエラーのように示さない。[NN/g: Hostile Patterns in Error Messages](https://www.nngroup.com/articles/hostile-error-messages/)

本機能への具体的な適用は本書の設計判断である。これらの資料だけで、適切な軸数・必要件数・重み・閾値が実証されたとは扱わない。
