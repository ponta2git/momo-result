# Web UI / UX 規約

目的: momo-result の全画面で、同じ意味・状態・操作を一貫して表し、4人が記録、確認、比較、出力を迷わず完了し、その結果を囲んで楽しめるようにする。

本書は Web の横断的な体験方針、情報設計、意味表現、視覚階層、操作文法、状態表示、文言の正本である。業務用語・状態遷移は [ドメイン規約](domain-rule.md)、画面固有の目的・順序・指標は対象要求（例外は [画面固有の要求](#画面固有の要求)）、層・server state・motion・form の実装境界は [Web 実装規約](web-rule.md)、検証の選択は [テスト・品質規約の UI の検証を選ぶ基準](test-rule.md#ui-の検証を選ぶ基準)、アクセシビリティの最低水準（WCAG AA 相当）は [システム要求](requirements/system-design.md#9-performance--client-quality) を正本とする。許容 scale と役割の対応は本書、component・class・token の現在名と値は実装が持つ。shared UI 部品の内部契約（キー操作、scroll の所有、内部の余白と境界、反応の時間など）は各部品の doc comment と test を正本とし、本書は部品を選ぶ基準と画面をまたぐ契約を書く。役割から実装への入口は [Web 実装規約の Implementation Entry Points](web-rule.md#implementation-entry-points) にある。

## 判断の優先順位

規則が競合する場合は次の順で判断する。

1. 正確性・データ保全・利用者の制御
2. アクセシビリティとタスク完遂
3. 意味の一貫性と体験の温度。両者は両立させる同順位の義務であり、体験の温度を「余裕があれば」に下げない。同じ意味を保てる案のうち、歓待が届く案を選ぶ。
4. 視覚上の洗練

統一感とは同じ意味が同じ原則で働くことであり、異なる文脈にはそれぞれに合う外形を使う。

## 体験方針

- 主な利用場面は、4人の仲間が1試合ごとに OCR 取り込み、下書き確認、確定、次の対戦を繰り返し、開催分が揃った後に累積結果と傾向を囲んで振り返る時間である。記録から雑談と仮説の発見までを分断せずに支える。
- momo-result は、卓を囲む4人の記録と語り草をつくる道具である。照合と入力は静かに支え、確定と振り返りには見せ場をつくる。勝者を称え、不調を笑いの材料にしない。次へ進む楽しみと、気持ちよく終える自由を両立する。
- 画面を二つの領域で扱い、画面全体ではなく領域と状態で切り替える。同じ画面に両方がある場合も入力と focus を守る。
  - **静かな作業域**: OCR 取り込み、下書きの照合、手入力、設定、出力。落ち着き、明瞭さ、精度、少ない手数を優先し、装飾的な演出を置かない。
  - **語りの場**: 確定の直後、開催の結論、振り返り、実績。[節目の演出](#節目の演出) の範囲で、構成、色、文字の大きさ、motion、文言による歓待を使ってよい。
- 歓待は作り込みの緻密さの上に成り立つ。整列、状態の一貫性、正確な値、少ない手数を崩して楽しさを足さない。汎用ダッシュボードや AI Slop に見える定型意匠（焦点の定まらない構成、同じ強さの KPI card の反復、内容のない装飾）を避ける。
- 開催回、試合番号、OCR、下書き、確定、順位、結果、出力という業務語彙を使い、対象、親スコープ、現在状態、実行可能な次の操作を判断できるようにする。
- 指標、件数、原因、信頼度、推薦、祝福は、利用者入力・保存済みデータを根拠とし、導出は要求で認めた範囲に限る。根拠のない値を補完せず、不明、未分類、計算不能、対象なし、未取得、集計待ちはその状態を明示する。記録にないことの断定で、会話の材料を誤解や個人への能力断定に変えないためである。
- PC、タブレット、モバイルで配置が変わっても、情報、状態、操作、現在地、戻り先の意味と主要情報を保つ。量は再配置、必要な横スクロール、段階的開示、要約と詳細の対応で保つ。
- 意味は構造、ラベル、境界、整列、accessible name で伝え、主要操作と未知の操作は発見できる形で示す。

## 情報設計

### 対象と導線

- 対象の関係は `開催 ⊃ 試合 ⊃ 4人の結果` とする。下書きは確定前の試合、OCR と手入力は試合を記録する手段、戦績比較と実績は確定記録の横断ビュー、出力は確定記録を持ち出す道具であり、後の三者は対象の階層に置かない。
- 主ナビは対象と横断ビューで構成し、取り込み手段は「記録する」操作の中に置く。管理機能は権限のある利用者だけに別群で示す。現在地、必要な親スコープ、主要な検索・絞り込みは初見で判断できる位置に置く。
- 記録は対象の文脈から始める。開催の中から始めた記録は、開催、次の試合番号、直前の試合から確定できる作品・シーズン・マップを、手段によらず同じ規則で引き継ぐ。候補が一つしかない必須の選択は既定で選ぶ。
- 詳細画面には所属する開催や一覧への導線を持たせる。閲覧の往復はブラウザーの戻る・進むに任せ、filter、sort、page、selection、hash はその画面の URL に保持する。`returnTo` の連鎖や独自の閲覧履歴を作らず、画面内の導線は所属開催、対象試合、一覧など行き先が明確なものにする。
- ブラウザー title と主ナビの現在地は route の意味を示す。pathname 遷移は安定した main landmark へ focus を移し、同じページの条件変更、履歴移動、隣接移動の専用 focus を上書きしない。未知の URL は黙って置き換えず復帰先を示す。

### 画面の型

画面は次の型から選び、型ごとに主役、見出し、操作の位置、幅、終わり方を揃える。

| 型 | 主な画面 | 主役（初期表示の錨） | 画面見出し | 主要操作の位置 | 幅 | 終わり方と次の入口 |
| --- | --- | --- | --- | --- | --- | --- |
| 一覧 | 試合一覧、開催一覧、下書き | 探している行を見分けられる data surface | なし | data surface の先頭。条件は対象の直上 | default | 行から詳細へ |
| 詳細 | 試合詳細 | 対象の identity と結果 | あり | 編集・出力は見出しの近く。破壊的操作は記録情報の中で控えめに | default | 所属開催、前後の移動 |
| 開催ハブ | 開催詳細 | 次に記録する試合と、この開催の結論 | あり（開催の identity） | 「第N試合を記録」 | default | 記録の開始、試合、前後の開催 |
| 照合ワークスペース | OCR 結果確認、下書きからの入力、手入力 | 現在の対象と、次の修正または確定 | なし | 末尾の実行領域 | source image を伴えば workspace、手入力は default | 確定した結果を示し、同じ開催の次の試合へ進める |
| 振り返り | 戦績比較、実績 | 判断対象の結果と比較 | なし | 条件は対象の近く | analysis | 根拠の試合へ |
| 取り込み・出力・設定 | OCR 取り込み、出力、設定管理 | 作業対象と実行可否 | なし | 作用する対象の近く | default（短い form・案内は readable） | 完了結果を示し、元の文脈へ戻る |

- 見出しのない型は、主要 content surface に用途を表す `aria-label` と landmark を与え、surface 内の section heading と control label を保つ。空の header slot を残さない。状態通知の title は page title の代用ではなく局所 heading として保ってよい。
- 幅は寸法名ではなく用途名で、URL の path と query で決まる内容形状から選び、読み込み中・失敗時も保つ。global navigation は page と端を揃え、readable の page では default の幅を使う。長文になり得る description、help、error、notice、empty state、narrative は、親の面を狭めず文字だけを共通の readable measure 以内へ制限する。label、table、chart、横比較には適用しない。
- 初回 route loading、route-level error / access terminal、feature loading は、pathname と安全化済み query から確定する幅、shell、戻る導線、見出しのある型の header、常設 action（pathname / query だけで移動先が確定するもの）、文脈 slot を ready と同じ順序で保つ。データで決まる action を推測して足さず、見出しのない型に title skeleton や空の header slot を作らない。状態の切替で作業領域や現在地を作り直して layout を跳ねさせないためである。

### 有限のタスクループ

- タスクは、きっかけ、最小の操作、確認できる結果、明確な終了からなる有限の流れにする。同じ開催の次の試合へ進む入口は核となる流れとして示してよいが、外的な再訪誘導、緊急性の演出、予測不能な報酬、再利用させるだけの CTA は加えない。記録を終えたら離れられるようにするためである。予め分かる規則で競争を楽しませること（実績の固定配点。[実績要求の配点](requirements/player-achievements.md#配点) が正本）はこの禁止に当たらない。
- 通知、再訪誘導、保存済み条件、shortcut は、要求で定義した便益と停止方法を持つ場合だけ使い、FOMO や不安、export を妨げる lock-in を作らない。
- 未保存入力は workflow の identity に属する。表示幅や補助 query の変更では保持し、別作業への移動・外部離脱では破棄確認を行う。保存中の入力を送信 snapshot から切り離さず、完了前に遮断した離脱を結果判明後に再開しない。
- 完了・失敗・download は開始時の対象と形式に結びつけ、離れた画面や別対象の結果として表示しない。中断可能な read / download は所有する画面の終了時に中断する。

## 視覚階層と強調

- 初期表示範囲に視覚的な錨を原則1つ定める。錨は見出しを飾る容器ではなく、[画面の型](#画面の型) が定める主要結果、主要操作、または現在状態そのものとする。未完了の作業では次に完了すべき操作、確定済みの閲覧では判断対象の結果を第一視線にし、共存する場合も強弱をつける。4人比較など同格の反復は一つの比較群として扱い、外側へ同じ強さの錨を重ねない。
- 強調は3段階で組み立てる。**主焦点**は位置、読み順、余白、文字の大きさまたはウェイトで示し、高コントラストの塗りは主要操作だけが使う。**内容構造**は見出し、整列、関係的余白、列で示し、誤認する場合にだけ divider を補う（通常の section や説明を淡色面で囲わない）。**局所標識**は選択、現在状態、順位、分類、注意を、対象の要素だけに付く短いラベル、marker、icon、compact な fill / border で示す。
- 文字の大きさ、ウェイト、コントラストを同時に最大にするのは主焦点に限り、ラベルは値より、補足は本文より、metadata は判断材料より弱める。色を除いた grayscale と blur でも主焦点、比較群、補助情報の順序が残ることを先に成立させる。
- 同一タスク範囲で最大強度の表現は1つとし、強調を足すときは弱める要素も決める。初期表示範囲の独立した大きな淡色面は1つまでとし、同格比較へ反復する場合は群全体を一つの錨として読めるようにする。
- 太字（主要強調）は次の3用途に限る。label、heading、button、link、選択中・現在地、status、data value という種類だけでは太字にせず、主要操作も塗りと配置を先に使う。減らした太字を濃い背景や大きな文字で一律に補わない。
  - **答え**: タスクの問いに答える値・短い文言（順位、総資産、比較結果、結論）。一覧では探している行を見分ける見出しも含む。4人比較は全員を同じ強さにし、試合結果では名前と順位も主情報とする。
  - **祝福**: 勝者、実績の達成と獲得ポイントなど称える対象。[節目の演出](#節目の演出) の範囲で祝福の面・色・icon を併用してよい。
  - **手当て**: 作業を止める問題が何でどこにあるかを示す一言。原因と直し方は通常の太さで示し、利用者を責めない。
- 最下位、後退、未達成、未記録など個人の不調だけを取り出して強調しない。比較群の一員として同じ強さで示すか、通常表示で淡々と示す。0 回や未記録の反復は、値がある項目より弱く示してよい。
- まとまりは利用者の問いと作用する対象から決める。主情報、メタ情報、詳しく調べる操作、別候補への移動は外形ではなく役割でまとめ、分類・件数・属性は主情報の近くに、解釈に必要な条件は初期表示に置く。内容のない kicker、section 番号、大文字ラベル、同じ強さの KPI card や CTA を反復しない。

## 色・面・境界

### 色と意味トークン

- 機能が使う色は参照色、意味トークン、コンポーネント用途の順に参照し、一回限りの色値を直接指定しない。参照値の共有は member sequence と play-order sequence の間に限り、ほかの意味トークンは自身の参照値を持つ。
- 視覚基盤は light mode のみとする。白に近い canvas、無彩色から低彩度の neutral surface、十分な明度差の text と border で構成し、neutral は OKLCH の明度順に canvas、surface、inset / selected、text、border、control へ割り当てる。
- 操作色（action）は主要操作の塗り、選択、focus、操作可能性の強調に限る。主要操作は操作色の塗り、副操作は枠付きの neutral、quiet 操作は面なしとする。
- 破壊的操作の起点（削除・破棄の button）は quiet な danger 表現に留め、塗りの danger は影響を示した確認 dialog の確定だけに使う。画面で最も強い色を破壊的操作に与えないためである。
- 4人の基準色順は `1=青`、`2=赤`、`3=黄`、`4=緑` とし、固定メンバーの canonical 順（member sequence）と各試合のプレー順（play-order sequence）に同じ順を使う。両者は参照 palette を共有してよいが、意味トークン、formatter、label、component は分ける。併記の規則は [4人の共通結果台帳](#4人の共通結果台帳) に従う。4色順は2つの sequence 以外（任意のグラフ系列、操作、状態、傾向、装飾）へ流用しない。
- 順位はどちらの sequence とも別の尺度であり、独立した意味トークンと `N位` の文字・形で示す。順位色では1位だけが祝福の金色を持ち、2〜4位は落ち着いた区別に留めて、下位を警告色に見せない。
- 操作、状態、順位、汎用グラフ系列、2つの sequence、祝福は別の意味トークンを持つ。error、warning、success は sequence 色と区別できる範囲で赤、黄、緑の色相を使ってよいが、ラベル、icon、形を併用し、同時表示で取り違えないことを確認する。区別できない組み合わせは neutral を基調にする。
- 状態 tone（error、warning、success、要確認、処理中）は、通知、標章、toast、control のどこでも同じ枠と面の強さを使い、枠は control の意味枠に必要な 3:1 を基準にする。

### 淡色面・disclosure・標章

- 淡色背景は、選択中または現在の scope、状態・注意、入力や操作の inset、compact な標章、[節目の演出](#節目の演出) の祝福面に限る。重要という理由だけで要約、説明、見出しを淡色面へ置かず、面を足すのは「何の選択・状態・操作領域・標識・祝福か」を答えられる場合に限る。
- disclosure は情報を開閉する操作であり、選択や inset とは別に扱う。展開 panel は自身の背景を持たず、内包する状態や独立した操作領域だけが面を持つ。字下げと hover は disclosure 部品が所有する。
- `1位`、分類名など短く反復される走査用ラベルは標章として背景色、形、border を持ってよい。標章は文字だけでも意味が分かり、種類ごとに一貫した寸法と強度を持ち、clickable、selected、warning と区別できるようにする。

### 面と罫線の所有

- page canvas は global navigation、関連画面への導線、見出しのある型の画面見出し、content 間の余白を受け持つ。作業・結果・data は白い content surface に置き、1タスクまたは1 data scope につき原則1面とする。画面見出しは surface の外に置き、面をまたぐ下線を既定で持たせない。内余白なしの surface は child が外余白を所有する明確な理由がある場合だけ使う。
- surface の内側を section ごとの card に分割しない。見出し、整列、列、余白で構成し、同時に独立して扱う workspace、独立して反復する record、境界が操作の理解に必要な bounded panel だけが別面を持つ。empty、pagination、loading など従属する状態は親の面を使い、table は内余白のある surface の中で共通 data table primitive を使う。
- グルーピングは整列と余白から始め、divider は余白と見出しだけでは誤認する場合と、table の row / column、control、状態通知など境界自体が意味を持つ場合に限る（通常 section では片側1本）。
- 1つの視覚境界は1つの owner だけが描く。sibling 間の divider は親 composition、部品の perimeter と内部境界はその部品が所有し、平行線や二重線を作らない。境界は淡色背景、border、角丸のうち必要最小の手段で表し、装飾だけの separator は accessibility tree へ意味を足さない。
- 通常の入力・選択欄と枠付きの副操作は控えめな共通の補助境界を使う（3:1 を保証しない採用方針）。選択マーク、select の矢印、focus、要確認・error の意味枠は実際の隣接色に対して 3:1 以上を保つ。境界 recipe と tone の優先順位は shared UI の control presentation が所有する。
- shadow は dialog、tooltip、toast など浮遊 UI に限る。gradient、glow、大きな surface contrast は [節目の演出](#節目の演出) の祝福面以外で装飾に使わない。
- 角丸は役割と包含階層を表す。`xs` は badge、marker、data cell、`sm` は control と小型 panel、`md` は record、card、notice、`lg` は page-level surface、dialog、toast、`full` は円、pill、progress track に使い、table は外周角丸を持たない。見える入れ子では内側を一段以上弱くし、同心性は実際の padding と paint を含む visual review で確認する。

## 文字・余白・レイアウト

### 文字

- 可視文字は `12px` を下限とし（chart axis も同じ）、本文、操作、主要データは原則 `14px` 以上、`12px` はラベルと補助 metadata に限る。サイズは `12 / 14 / 16 / 18 / 20 / 24 / 30px` から選び、`24 / 30px` は画面見出しと [節目の演出](#節目の演出) の結果数値に使う。収まらない場合も scale 内に保ち、component 幅、情報量、折り返し、局所 scroll、段階的開示の順に見直す。
- 文字色は `text-primary` を結論・結果・識別の要点、`text-body` を本文、`text-secondary` を補足、`text-muted` を本文との差が足りない補助ラベルに使い、`text-muted` は実際の背景でのコントラストを確認する。
- ウェイトは 400（通常表示: 本文、値、form label、表の見出し、操作、navigation、tab、状態・順位の標識）、500（内容構造: section・dialog の見出し）、600（主要強調: [太字の3用途](#視覚階層と強調)）の3段階に限る。端末フォントでは 500 が 400 と同じ face になり得るため、見出しはサイズと余白でも識別できるようにする。
- 読む内容と記録情報は次の文字 recipe を基本とし、class の組み合わせは共通文字 recipe が所有する。heading level は文書構造で別に選ぶ。表、chart、control、長文、節目の結果数値は用途別の共通 recipe を使い、新しい組み合わせが必要なら共通 recipe 側で定義する。element の既定スタイルは base layer に置き、明示された recipe を優先させる。

  | 内容の役割 | サイズ / 行高 | ウェイト | 文字色 |
  | --- | --- | --- | --- |
  | 主要な結論・短い主情報 | 20 / 28px | 600 | `text-primary` |
  | 一覧・反復行の主要結果 | 14 / 20px | 600 | `text-primary` |
  | 内容構造・小見出し | 14 / 20px | 500 | `text-primary` |
  | 通常本文・値 | 14 / 20px | 400 | `text-body` |
  | 補足・メタ情報・ラベル | 12 / 16px | 400 | `text-muted` |

- 入力用の文字は共通の入力文字 recipe を使い、読むための metadata ラベルを入力ラベルやエラーへ流用しない。

### 余白

- 余白は `4 / 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64px` から選び、距離が表す関係を先に決める。
  - page frame 直下と surface 内で page scope を分ける主要 block は `24px`、section・form の主要 sibling と同格の card / record 間は `16px`。文章中心の内容は近い項目を `8px`、問いの異なる群を `24px` で区切り、長い detail / analysis の独立した最上位 section 間だけ `32px` を許容する。
  - 複数の内容群を持つ card / record の内余白は `16px`、一つの状態・値・操作を示す compact な panel と走査密度を優先する data record は `12px`。page-level surface の内余白は狭い viewport で `16px`、`sm` 以上で `24px`。
  - action 間と inline item 間は `8px`、compound control 内、一つの値・標識内、support text 同士と control から support text は `4px`、field の label から control は `8px`。dialog は header、body、feedback、footer を別の群にする。
  - `2px` は一つの label / value 内の密接な関係と光学補正、`1px` は境界補正、`20px` は component 内部、`48 / 64px` は page-level の empty / error と可変長メモを持つ反復 record 間に限る。寸法、hit target、scroll geometry は余白 scale と別に扱う。
- 包含階層では外側の群ほど同じか大きい余白を持たせる。table、chart、matrix、compact badge は走査密度を優先し、外側で呼吸を作る。狭幅の page gutter は `12px` を許容する。
- sibling 間の余白は親 composition、内余白は component、page gutter と page sibling 間隔は page layout primitive が所有する。再利用 child に外 margin を持たせず、状態置換でも同じ owner と間隔を保つ。safe area は fixed layer の viewport が所有する。

### レイアウト

- page、data surface、workspace は外余白の内側で利用可能な横幅を使い、読み幅の制約は prose や単一 field 群へ局所的に掛ける。走査と比較が速くなる表・図表は密にし、不規則な欠け、根拠のない非対称、任意の値や z-index を足さない。
- 再利用部品の内部配置は intrinsic な折り返しや名前付き container query で割当幅に応じて切り替える。page 全体の横 scroll は作らず、table、図表、source image など横の関係を保つ領域だけが可視の案内とともに局所 scroll を持つ。縦 scroll が不要な page で scrollbar の空きを常時予約しない。
- 切れ目のない長い値（ID、URL、外部 error）だけへ局所的な wrap / scroll を指定し、全画面へ `overflow-wrap: anywhere` を継承させない。balance や pretty wrap も役割ごとに指定する。
- 一行の control、status、action cluster、table cell は中央、短い label / value 行は baseline、可変高の複合 record は上端、横並びの form row は control の下端で揃える。対応関係のための例外は局所的に明示し、任意の offset で調整しない。
- 内余白を持つ操作面や cell は外端を周囲の内容端へ揃え、文字を内余白の分だけ字下げする。負の余白で文字だけを揃えない。sticky な要素は global navigation の実高の下で止める。

### データ表現

- 日時、金額、試合番号、状態名は共通 formatter / ViewModel を使い、件数と比較値には対象、単位、分母または基準を添え、整列する数値は tabular numerals にする。前後の差は「改善」「後退」「維持」「初戦」と値を併記する。
- 時系列の timeline は順序付きリストと1列の marker 軸で構成し、marker は順序を文字でも示す。record 内の群は近接させ、record 間はそれより明確に離して、メモの展開後も次の record の開始位置を追えるようにする。
- 同格の disclosure を列で並べる場合、一つの展開の前後で同じ行の別 trigger や操作の位置を保つ。

## 操作文法とコンポーネント境界

共通化は外形や event handler の類似ではなく、目的、対象、作用、前後の状態、制約、feedback、失敗時の回復が同じかで判断する。同じなら画面が違っても同じ shared UI primitive または操作 pattern を使い、業務上の結果や制約が違えば外形が似ていても別の操作として扱う。

### 抽象化の単位と所有権

- shared UI は、意味に対応する構造、keyboard / focus、accessible name、hit target、disabled / pending、局所 feedback、内部の responsive arrangement と intrinsic constraint を所有する。feature は業務語彙、URL / query / cache、権限、入力変換、副作用、業務状態遷移、app は route と画面 composition、shared domain は業務 identity、順序、formatter を所有する。依存方向と配置は [Web 実装規約の Layering](web-rule.md#layering) に従う。
- shared UI へ切り出すのは、複数の現在用途を一つの小さい契約で覆える場合か、accessibility、制約、feedback、状態同期の重要な判断を隠せる場合に限る。名前だけの wrapper、判断を props へ移すだけの万能 component、将来用途だけの schema は作らない。複数画面で共有する業務 UI は業務別の shared module に置き、共有されることと業務非依存であることを区別する。
- 親 composition は位置、並び順、外側の寸法・余白、sibling 間の gap / divider、伸縮と積み替えを所有する。再利用 component は親の slot に従って伸縮し、特定の利用箇所を理由に固定寸法、外 margin、隣接 separator を持たない（利用可能領域を定義する layout primitive は除く）。consumer は外側 container で寸法を指定する。
- 汎用部品は通常表示を既定とし、主要コンテンツであることが契約に含まれる部品だけが主要強調を持つ。主役は feature composition が選んで共通文字 recipe を適用し、任意のウェイトを渡す API や親全体の太字で補正しない。意味構造（`th`、`scope`、heading level）とウェイトを分ける。
- label と値は共通の label / value pattern、表と軸の異なる行列は共通 data table と table scroll area、読み取り群に補助操作を添えるときは内容群と操作群の pattern を使う。SVG 図表は保存済みの数値・系列名を読み取れる代替表を持ち、多数の観測点を Tab 順に入れない。

### 選択・表示切替・表示範囲

- 部品は見た目ではなく意味で選び、選択と即時実行を区別する。説明を読み比べて一つを選ぶ候補は native radio group と説明付きの選択行、開催や試合など日時・件数・状態を読み比べる単一選択は現在値と変更 trigger を持つ共通 dialog field（「すべて」「選択しない」も候補として扱い、どの文脈でも同じ文法）、一行ラベルの単一選択は shared の一行 Select、多数の簡潔な候補は select か検索可能な選択を使う。値だけを変える少数の mode は segmented control、同じ対象の view や対応 panel を切り替えるものは tab、補助詳細は disclosure とし、panel を伴わない排他条件に tab semantics を付けない。上下2階層の tab を同じ強さで競合させない。
- 候補の名前は対象を識別する安定した label とし、件数・状態・補足は description、選択は checked で関連付け、名前に説明を繰り返さない。群の名前は可視 legend か可視見出しが持ち、単一の選択群だけを扱う dialog では title を群の名前に使う。
- filter は scope を変える操作であり、data surface の近くに、それを支える階層で置く。主要条件、必要時だけ開く詳細条件、件数、scope を示す一つの全解除を一つの操作群として対応させる（card や淡色面で囲うことは要求しない）。閉じて見えなくなる条件の非既定値は、trigger の要約か一覧直上の個別に解除できる条件として示し、常時見えている条件や sort を再掲しない（条件全体を dialog に畳む狭い幅では全条件を示してよい）。親と下位を同じ値の二重の選択状態として並べない。
- 件数は取得できた範囲だけを事実として示し、未取得や失敗は `0件` ではなく件数不明として再取得操作とともに示す。同一 scope の総件数は一か所にまとめ、範囲と総数を同時に判断する一覧では pagination を owner とする。
- filter の見た目と操作契約は横断化してよいが、URL、query、cache、cursor、候補間の依存、既定値、更新文言は feature が所有する。取得済み内容を保ったまま条件を変える場合は [取得状態とフィードバック](#取得状態とフィードバック) に従い、描画の追従に専用のアニメーション、固定待機時間、成功通知を加えない。

### 移動・実行・確定

- app 内の routing と document の移動を区別し、disabled / pending でも実要素と focus を保ったまま activation だけを制限する。開始した native navigation を pending 表示で取り消さない。
- 取り込み・手入力・OCR 確認の最終実行は共通の task action panel にまとめ、可否・結果の feedback と実行操作を一群にする。dialog の確定は一貫した footer、読み順、主要度を持ち、キャンセルを DOM と視覚の両方で確定より先に置き、pending 中の不用意な閉鎖を防ぐ。
- 非同期 button は通常時と pending 時の文言・icon の領域を確保し、切替の前後で寸法と隣接操作の位置を保つ。

### 更新・再試行・初期化・破棄

- 更新は、現在の表示条件のまま再取得する操作である。`ready → updating with stale content → ready` を基本とし、失敗しても取得済み内容を残して局所表示する。再取得の起点は利用者の更新 / 再試行と [Web 実装規約の Server State](web-rule.md#server-state) が明示した限定例外だけとし、一定間隔、遅延 timer、tab の復帰、window focus、network reconnect を起点にしない。表示中の内容が変わる時点を利用者が予期できるようにするためである。
- 再試行は、失敗した操作を同じ入力と scope でやり直す回復操作である。`error → pending → success | error` を失敗箇所の近くで示し、処理中も失敗案内と再試行操作、入力、選択、scroll 位置を保つ。route retry は query と error boundary を同時に reset する。
- 初期化は、変更できる値を明示された既定値へ戻す操作である。対象 scope をラベルで示し、主要操作にするのは変更がある場合に限る。
- 破棄は、未確定の変更を取り除き `dirty → clean` へ戻す操作である。失われる内容を先に示し、影響が大きい場合だけ確認を挟む。保存済み data の削除と未保存変更の破棄は別の文言で表す。
- 4つの操作は icon、文言、loading 表示の組合せで識別できるようにし、共通化しても各状態遷移と回復契約を保つ。業務状態の表示は、metadata や color からの推測ではなく、明示された状態を共通表現へ変換して行う。

## 入力・ワークスペース・アクセシビリティ

- 入力中の現在対象（撮影先、確認中の項目、参照画像）と、確定前に照合する主要結果を識別の要点として強調する。設定の確認値は編集 control と区別して label / value で示す。確認 dialog は設定、結果・送信対象、注意、確定操作を群に分け、長い名称を確認前に全文読めるようにする。
- OCR 結果修正と手入力は、入力 field と対応する source image、同じプレーヤー・項目順、編集結果の feedback を一つの workspace として保つ。編集中の field と照合する画像の該当箇所を同時に見られる配置と少ない修正手数を守り、画像と field の往復を増やさない。
- 読み取れなかった値、未確認の値、実際の 0 は入力欄と確認の表示で区別し、OCR が値を返したことだけで確認済みとして示さない。
- 準備不足は利用者が最初に直せる欄へ案内を集約し、操作を試みる前から error として示さない。前提が満たされるまで操作できない欄に、原因と同じ error を重ねない。
- coarse pointer の操作は viewport 幅にかかわらず 44px 以上の hit target を持ち、compact 化は `pointer: fine` が明示された場合だけ許容する。icon-only action は常に 44px 以上とする。
- focus 枠は一つの対象に一度だけ描き、切り抜き境界で切らない。forced colors でも選択の印と focus 枠を残す。dialog と候補 popup は所属する layer と唯一の scroller の中で、拡大表示や低い viewport でもすべての操作へ到達できるようにする。
- camera preview、source image、分類 tray など同じ画像を対応付ける frame は、状態や配置の前後で aspect ratio を保ち、画像全体を確認できる収め方を使う。

## UI ライティングと分析の断定

- 文体は短く、具体的に、落ち着いて書く。称えるときは事実と行為を称え、能力や人格を断定しない。不調を笑いの材料にせず、根拠のない励ましや場当たりの冗談を足さない。要求正本で定義された仲間内の語彙（`桃鉄型`、`遊戯王型` など）と本人が合意した呼び名はそのまま使ってよい。
- 一つの文言は、対象、現在状態、結果、影響、次の操作、判断に必要な根拠のいずれかを伝える。同じ事実は一か所で伝え、条件付きの注意は条件が成立した箇所だけに出す。期間と対象は `直近8戦と荒れ方` のように見出しへ統合し、復唱しない。
- 容器や表示形式を説明する語（`カード表示`、`この欄`）、自明な言い換えにしかならない label / value、内容を増やさない説明の強調（背景、見出し、太字、独立 section）を置かない。解釈を変える前提（期間、対象範囲、単位）は一度だけ明示する。
- 曖昧な構造、不正確な値、欠けた状態、発見しにくい操作は、説明文ではなく構造、コンポーネント、data contract、状態表現を直して解消する。生成・編集の内部都合（section 番号、重複回避、候補の選別）を利用者向け説明にせず、省略が解釈を変える場合だけ結果と範囲を示す。
- 分析文の強さを `事実 → 傾向 → 仮説 → 提案` で区別し、要求正本と根拠が許す段階までに留める。「分かったこと → 根拠となる試合・件数 → 実戦上の意味 → 必要な場合だけ手法」の順で示し、数学知識を前提にしない。仮説は次の対戦で確かめる対象として示し、提案は要求で明示された場合だけ根拠とともに示す。観測していない原因や推薦へ広げず、手法名を主要ラベルにしない。
- 信頼性は例外として扱う。OCR 品質、data 欠損、分析上の不確かさを別の原因として受け取り、解釈を実質的に変える場合だけ影響範囲とともに警告する。`参考値`、`信頼度低め`、`対象なし` を混同せず、metadata 欠落から健全性を推測せず、通常の状態の安心文言は出さない。
- 見出し、ラベル、button、badge は名詞句か短い操作句として句点を付けず、完全文は句点で閉じる。全体との比は `未確認3件／全8件` のように対象、単位、分母を示す。
- 保存済み data を取り除く操作は「削除」、未保存または一時的な入力・画像を取り除く操作は「破棄」、条件を既定値へ戻す操作は「初期条件へ戻す」と表す。利用者向け文言と accessible name に component 名、token、内部 field、worker など実装上の呼称を使わない。

## 取得状態・フィードバック・モーション

### 取得状態とフィードバック

- 表示対象の意味上の同一性で「置き換える」か「維持する」かを決める。初回表示と、異なる pathname で内容が未準備の場合は最終 layout に近い structural skeleton を使う。同一 pathname 内の filter、scope、sort、page の変更と refetch では既存内容を保って局所的に更新中を示し、新しい条件で誤操作を招く範囲だけを操作不能にする（減光・ぼかしもその範囲に限る）。表示中と要求中の scope を区別して知らせ、見た目だけ残して支援技術から隠すことを保持としない。安全に変更できる条件欄は取得中も操作可能なまま focus を保ち、最後の条件を反映し、利用者が移した focus を完了時に戻さない。
- 待機の表示は実際の状態に合わせる。進行中の読込、処理中、この画面では終わらない待ち（集計待ちなど）、確認できない結果を区別し、終わりのない待ちを読み込み中として示し続けない。
- 通知の単位は、一つの利用者操作とその結果を成立させる取得のまとまりとする（API、query key、component、Suspense boundary の数では決めない）。一つの待機には因果の近い表示を一つ置き、親子の spinner、overlay、toast を重ねない。待機表示の領域は通常時から確保し、出現・消失だけで周囲を動かさない。視覚表示と読み上げは同じ単位を使い、`aria-busy` は更新対象に付けて live region の通知を保留させず、同じ結果を繰り返さず、通知のために focus を移さない。
- error、not found、empty、stale data を別状態にし、回復は [操作文法](#更新再試行初期化破棄) に従う。empty state の導線は現在の権限と前提で実行できるものに限って安全な主要操作を1件示し、前提の準備（作品、開催など）が欠けていればその準備へ導く。
- 補助情報の取得に失敗しても主表示は保つ。保存の確定、表示用 data の再取得、集計の結果を区別し、結果不明と確定した成功・失敗も区別する。

完了・失敗の通知先は、結果の確認場所と回復の必要性で決める。

| 状況 | 通知先 |
| --- | --- |
| 保存・作成・確定・削除の後に遷移する、または操作面が閉じて確認場所が残らない | 短い toast で一度知らせる。遷移先が確定した結果を明瞭に示す場合は、その表示を通知先にしてよい |
| 結果が同じ場所に明瞭に残る | 結果表示を使い、値だけでは保存の確定が分からない場合は操作付近の短い完了表示を使う |
| 一覧の手動更新、条件変更、付随する再取得の成功 | 待機表示を終えて結果を示し、成功 toast は足さない |
| 入力不備、操作不能、保存・削除・取得・download の失敗、結果不明 | 原因・影響と回復手段をその場に残し、toast だけにしない |
| OCR・分析などの非同期処理 | 受付・開始と完了を区別し、継続中の状態と回復操作を対象領域に残す |

- 同じ結果を toast と inline 表示へ二重に出さず、状態が明らかな選択、入力復元、cache の再取得だけで toast を増やさない。toast の重複除去、上限、寿命、読み上げ、配置は共通 host が所有し、主要操作や入力中の control を覆わない。

### 操作面の反応

- 文字・icon・寸法を保ち、面の濃さで操作へ応える。操作可能性、選択・tone・invalid の意味、一時的な hover / pressed、focus を分け、意味の基底色と hover 量を分離する。hover は遅延なく現在値から短く補間し、pressed・focus・操作制限は即時に返し、touch から hover を作らない。
- 反応は気づける強さを持たせる。操作部品は通常 → hover → pressed で面を小さく濃くし（編集用 control に押し込み表現は足さない）、表の行はそれより弱い hover で読む位置を補助する（行全体に pressed、pointer cursor、tabIndex を足さない）。tone のある control はその意味色の範囲で応答し、readOnly は focus・文字選択・copy を保つ。
- 補間の時間と曲線、色対、反応の接続は shared UI が所有し、feature は用途・状態 props で使う。部品別の時間や任意色を公開せず、hover のために wrapper や余白を足さない。

### モーション

- motion は、操作への即時 feedback、状態の因果、同じ対象の連続性の補助と、[節目の演出](#節目の演出) に使う。文字、形、位置、accessible state だけで意味を成立させた上で、用途別の共通 token と主に opacity / transform を使う。
- 通常の内容では layout shift、bounce / overshoot、stagger、視線を奪う移動を作らない。route content、Suspense の fallback と完成内容、初回 content、一覧 row を登場や置換の演出として animate せず、disclosure の本文は開閉と同時に配置へ反映する。
- 値の変化を伝える図表や数値は mark や値だけを補間してよい。viewport への進入を trigger にせず、図表は完成値から描き、表示中の同じ対象の値が変わった場合だけ補間する。
- 楽観更新の pending、confirmed、error は静止状態でも区別し、追加・削除の presence motion は rollback、server correction、同時 mutation を含む正しさを先に検証する。
- 常時 loop は時間が不定な loading に限り、完了や対象外で止める。非必須 motion は `prefers-reduced-motion` で省略する。application state を animation の完了に依存させない境界は [Web 実装規約の Client Lifecycle](web-rule.md#client-lifecycle--suspense--motion) に従う。

### 節目の演出

確定の直後、開催の結論、実績の達成など、4人が結果を受け取る節目では、語りの場として演出を許可する。

- 手段は、結果を主役にする構成、祝福の色と面、`24 / 30px` の結果数値、勝者や初達成を称える文言、一度だけの有限な motion である。token と recipe は最初の実用途で shared UI と global stylesheet に定義し、画面ごとの一回限りの値を置かない。
- 予算は1画面に1つの節目とし（同格の4人を含む一群は一つと数える）、静かな作業域では使わない。
- 根拠はサーバーで確定した値と要求で定義した判定に限り、表示中の結果と同じ対象・版を使う。記録にない経過を語らない。
- 結果、操作、focus は演出を待たずに使えるようにし、静止状態でも結果と祝福が伝わるようにする。演出は一度だけ再生し、再表示、履歴での再訪、再取得では再演しない。動きを減らす設定では静止版を使い、音は既定で使わない。
- 祝福は勝者や達成した人を称えるために使い、下位や未達成の人を対比として目立たせない。

## 4人の共通結果台帳

- OCR 確認の要約、試合詳細、開催結果、分析では、4人の同一性、順序、整列を共通の視覚文法として反復する。同じ card の複製ではなく、文脈に合う表、列、行、図表へ変形してよい。
- 固定メンバーは `いーゆー → ぽんた → あかねまみ → おーたか` の順と名前で識別し、member sequence はこの順に4色を対応させる。この順と色を共通台帳、分析表、グラフ系列・凡例へ一貫して適用し、順位、指標値、プレー順で並べ替えない。ただし、1試合の順位・総資産を読む結果台帳と、開催一覧の各行の開催ごとの順位は1位からの順位順とする（同率は同じ順位、その中は canonical 順）。色は名前を補助する走査用の手掛かりとし、同一性を色だけに依存させない。
- 利用者が列見出しなどで並び替えた詳細表は、その表に限って指定順を優先してよい。並び替え後も色と名前の対応を変えず、現在の sort と既定順へ戻す方法を示す。共通台帳、要約、グラフ系列・凡例はこの例外に含めない。
- play-order sequence も同じ4色順のため、member sequence と違う色が同じ人物に付く場合がある。同じ行・表・比較群で両者を併記するときは play-order marker だけに4色を使い、固定メンバー名は neutral にして `プレー順N` を別の可視ラベルで示し、marker の形や配置でも区別する。編集 workspace のプレー順の色はプレー順 marker へ集約する。
- source image と連動する編集 workspace は画像上の並びに合わせてよいが、各入力に固定メンバー名と `プレー順N` を示す。確定後は1試合の結果台帳を順位順、共通台帳・分析表を canonical 順で表示し、順位、プレーヤー名、総資産を主情報とする。画面固有の補助指標は対象要求を正本とする。
- 主要結果は比較の取得と独立に表示し、比較の失敗や対象試合なしでも保存済みの結果を残す。試合の識別情報は文字で残し、ナビゲーションと出力は明示した操作として表す。

## 画面固有の要求

本節は、対象要求に正本がない画面固有の表示要求を置く。索引と本書冒頭が定める「画面固有の目的・順序・指標は対象要求が所有する」の明示的な例外であり、次の項目は本節を正本とする。対象要求へ移す場合は、移動と同じ変更で本節の該当項目を削除し、参照元を更新する。

- 分析の入口は「平均順位の差が縮まったか」「最近の負けが通常より続いているか」「桃鉄型など別の型を試す根拠があるか」という会話へ答えられる構成にする。順位内訳、平均順位と差、直近範囲、総資産・収益を優先候補とし、型の変更は推薦ではなく根拠付きの仮説として示す。移す場合の受け入れ先: [比較要求](requirements/series-comparison.md#3-information-architecture--state)。

## 視覚レビューの観点

visual review を evidence に選んだ場合の観点である。選択基準と自動検証との境界は [テスト・品質規約の UI の検証を選ぶ基準](test-rule.md#ui-の検証を選ぶ基準) が所有し、配置や反応の一貫性を、座標・DOM 構造・animation 設定を恒久 test へ固定する理由にしない。screenshot は補助とし、理解や読みやすさを秒数・評点へ置き換えず、判断した文脈と所見を伝える。

| 変更 | 確認する観点 |
| --- | --- |
| 共通 | hierarchy、読み幅、関係的余白、product specificity、restraint、structural fit。初見点検と cognitive walkthrough で目的、現在地、主要操作を説明できるか |
| 階層・IA・色の意味 | 影響する利用段階の代表画面で「いま見る対象」と「次の操作」が分かるか。grayscale / blur でも主役が残り、色なしで役割を区別でき、順位がどちらの sequence にも見えないか。通常状態で信頼性の注意や同じ事実の反復がないか |
| 文字・ウェイト・共通 pattern | 異なる用途の代表画面で主情報・本文・メタ情報が同じ役割として読め、通常の label・操作・metadata が主要結果と競合しないか。500 と 400 が同じ face でも見出しを判別でき、状態と現在地を太字に頼らず認識でき、折り返しや操作位置が破綻しないか。OS ごとの描画を未確認ならその境界を報告する |
| 角丸・文字 scale・読み幅 | surface、dialog、panel、control、badge、画像 frame が同時に現れる画面で包含階層が保たれるか。長い日本語の notice や error が wide viewport でも readable measure を超えないか。desktop と mobile の dense data view で欠落、衝突、不自然な縮小、page の横 scroll がないか |
| 余白・spacing owner・見出しの省略 | loading、error、empty、dialog、fixed feedback を含む状態で header、surface、section、action が不意に動かないか。group 間が group 内より広く、focus outline が隣接 action と衝突せず、safe area を含む gutter が欠けないか。見出しを省いた画面に空 slot が残らず、landmark と section heading から現在地を説明できるか |
| component の親 slot と境界 | 狭幅と広幅で intrinsic constraint が保たれ、divider と部品の perimeter が二重にならないか |
| 照合ワークスペース | 画像と field の対応が分かり、入力を保ったまま修正を完了し、誤操作から戻れるかを現行と比較する。完了時間や操作数の測定は、定性的に解消できない具体的な疑問がある場合だけ選ぶ |
| 節目の演出 | 結果と操作が演出を待たずに使え、静止状態と動きを減らす設定でも祝福が伝わるか。再表示で再演せず、下位や未達成を対比として目立たせず、作業域へ持ち込んでいないか |
