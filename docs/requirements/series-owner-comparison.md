# オーナー別戦績比較 要求仕様

目的: 選択した比較範囲の中で、オーナー別に固定4名それぞれの成績・展開を気軽に見比べ、仲間内で話のネタにできるようにする。差が大きい結果だけでなく、近い値や同じ値も会話の材料として扱う。

対象: [MOM-3](https://linear.app/ponta/issue/MOM-3)、選択試合の対応表示は [MOM-22](https://linear.app/ponta/issue/MOM-22)。各自の端末を見ながらDiscord越しに話す利用を想定する。

| 関心事 | 正本 |
| --- | --- |
| オーナー別比較の目的、指標、表示、入力・成果物・URL固有の契約 | 本書 |
| 比較ページ全体のscope、順位・金額・同値などの共通定義 | [戦績比較](series-comparison.md) |
| 事前計算、成果物、更新状態、互換性・公開 | [分析バッチ](series-analysis-batch.md) |
| 共通UI、品質証拠、必須gate | [UI規約](../ui-rule.md)、[テスト・品質規約](../test-rule.md)、[開発作業規約](../dev-rule.md) |
| HTTP・成果物の構造、DB schema | Tapir endpoint、JSON Schema、momo-db |

## 1. 成功条件

- 4人が自分や仲間の記録をオーナー間で見比べ、「この記録ではこんな値だった」「思ったほど違わない」といった会話の材料を得られる。差の発見、原因の特定、次戦の作戦変更は成功の必須条件にしない。
- 選択した作品・シーズン・マップの範囲内で、オーナー別に4人それぞれの成績・展開を比較できる。任意条件を指定しない場合は、複数条件が混在した記録の比較となる。
- 同じ指標のオーナー4人分×プレーヤー4人分を見比べ、オーナー名と成績の主体であるプレーヤー名を取り違えない。
- オーナー別試合数を確認し、対象なし、少数例、観測された0を区別できる。
- 保存済みオーナーの訂正、試合の追加・削除が、分析更新後の所属と数値に反映される。
- 指定したプレーヤー・指標について、オーナーA・Bそれぞれの値と試合数を、説明者の補助なしに読み取れる。対象なし・参考・同値を取り違えない。
- 別々の端末で見ている人が、作品・条件・指標を名前またはURLで揃えられる。表示している範囲と最終更新を確認でき、違う条件・時点の結果を同じものと取り違えない。
- 初版の操作範囲は集計値の一覧比較までとし、対象試合一覧を開く操作は要求しない。表の表示だけを利用価値の達成とせず、8節の読解課題も確認する。

## 2. 利用者と確定した範囲

| 判断 | 決定 |
| --- | --- |
| オーナーの意味 | 現在の試合登録画面で保存する `ownerMemberId`。固定4名のいずれか |
| 主な問い | Aさんがオーナーの試合／Bさんがオーナーの試合で、4人それぞれの成績・展開がどう違うか |
| 提供価値 | 仲間内で話のネタにする。オーナーによる実際の有利不利や、ゲームの公平性を判定する機能は求めない |
| 利用場面 | 各自が自分の端末を見ながらDiscord越しに話す。ひとつの共有画面を見ている前提にしない |
| 保存済みオーナー | 複数人の記録があり、実際のオーナーに合わせて入力している。入力確認や補正機能の追加は今回の要件にしない |
| 指標の対象分野 | 順位、資産、物件収益、目的地、銀次 |
| 表示場所・方式 | 既存の「分析する」→「条件別」にオーナー比較を追加し、同じ指標を一覧で比較する |
| 少数例 | 比較表ではオーナー4人を表示し、0試合は「対象なし」、1〜2試合は件数と参考であることを添える。表示名は既存の「参考値」に統一する。選択範囲全体が0戦の場合は共通の空状態に従う |
| 個別試合への導線 | 初版は集計値の比較まで。オーナー別の対象試合一覧は追加しない |

初版では、ページ全体のオーナーfilter、オーナーごとの推移・高度分析・振り返り生成、本人のオーナー時／それ以外の専用比較は追加しない。記録項目、CSV/TSV、Discord通知、試合詳細の通算値もこの機能のために拡張しない。成果物契約はAPI・Web・Workerを同時に揃え、旧世代の互換コードは維持しない。

「本来はオーナー差がないはず」は利用者の期待であり、ゲームの仕様や公平性を本機能で検証した事実として扱わない。会話の材料を得るために、行動提案、統計的検定、条件補正モデル、AIによる解説・あだ名を追加しない。

## 3. 対象データと集計単位

- 認証済みの有効アカウントが閲覧する。権限は既存の戦績比較と同じとする。
- 作品を必須、シーズンとマップを独立した任意条件とする既存scopeを使う。総合、実在するシーズン、マップ、シーズン×マップのすべてでオーナー比較を提供する。
- scope内の確定済み試合だけを、現在保存されているオーナーにより分類する。下書きを含めず、作成者アカウントや開催の属性からオーナーを推測しない。
- オーナーは試合の属性とし、開催内でオーナーが変わっても試合ごとに分類する。そのオーナーの試合から固定4名全員の結果を使い、オーナー本人の結果だけを抽出しない。
- 選択scope内でオーナーが `o` の試合集合を `M_o`、その試合数を `N_o` とする。各試合はちょうど一つの集合に所属し、4人のオーナーの `N_o` の合計は親scopeの試合数に等しい。
- 各プレーヤーの指標には同じ `M_o` を使う。分母は `N_o` であり、開催数や4人分の明細件数ではない。
- 固定4名の識別と表示順は既存のメンバー正本に従う。成績や対象試合の有無によってオーナー・プレーヤーの順序を変えない。
- 保存順位、金額、平均、同値、丸めの共通定義は [戦績比較](series-comparison.md#2-data--scope-invariants) に従う。

4人の順位をまとめて平均すると、どのオーナーの試合集合も `(1 + 2 + 3 + 4) / 4 = 2.5` になる。そのため、順位の比較はプレーヤーごとに行う。

## 4. 初版の指標

確定した対象分野を、次の指標で具体化する。試合数が異なるオーナー同士でも比較できるよう、主表示は平均と率を使い、回数には対象試合数を対応づける。すべてオーナー別・プレーヤー別に算出する。

| 分野 | 指標 | 定義・読み方 |
| --- | --- | --- |
| 順位 | 平均順位 | 本人の保存順位の平均。小さいほど上位 |
| 順位 | 順位分布、1位回数・1位率 | 本人の1〜4位の各件数と、件数を `N_o` で割った率。1位分は1位率として読み取れるようにする |
| 資産 | 平均総資産 | 本人の保存総資産の平均。0円・負の金額も含める |
| 物件収益 | 平均物件収益 | 本人の保存物件収益の平均。0を含む保存値を使う |
| 目的地 | 1試合あたりの目的地到着回数 | 本人の保存目的地回数の合計を `N_o` で割る。到着0回の試合も含める |
| 銀次 | 遭遇率・遭遇試合数 | 本人の銀次回数が1回以上の試合数と、その試合数を `N_o` で割った率 |
| 銀次 | 1試合あたりの遭遇回数・合計回数 | 本人の銀次回数の合計と、合計を `N_o` で割った値。同じ試合での複数回遭遇も数える |

- 銀次の遭遇率は「本人が遭遇した試合の割合」であり、「4人の誰かが遭遇した試合の割合」ではない。複数回遭遇しても遭遇試合数には1試合として数える。
- 順位分布の各件数の合計は `N_o` となり、`N_o > 0` では丸め前の各率の合計は1となる。同じオーナーの4人分の1位回数の合計も `N_o` となる。
- 金額の中央値・分布、接戦・大差の分類、親scope平均との差、オーナーの有利不利の自動順位づけは初版の指標に含めない。
- 件数と平均・率を使って観測された差を示す。シーズン・マップ・番手・開催時期などの偏りを補正したオーナーの効果や、統計的な有意差として表現しない。
- 同じ親scopeでも、オーナーごとのマップ・シーズン等の構成割合が等しいとは限らない。試合数が同じことを条件が揃っている証拠にしない。「選択範囲の記録比較」として扱い、補正されたオーナーの影響と読ませない。

### 件数と品質

| オーナー別試合数 | 表示 |
| --- | --- |
| 0 | 「0戦」と「対象なし」。値は共通の「—」とし、0位・0円・0回/試合・0%として表示しない |
| 1〜2 | 数値を表示し、試合数と既存の「参考値」を添える |
| 3以上 | 数値と試合数を表示する。件数境界を統計的な確実性の証明として扱わない |

品質は親scopeの試合数ではなく `N_o` で判定する。すべての指標で分母が共通なので、同じオーナーの件数・品質を列見出しにまとめる。共通の品質表現を使い、通常値に「正常」「信頼度十分」などの標章は加えない。品質が列全体に適用されることは支援技術でも読み取れるようにする。

`N_o > 0` かつ本人の目的地・銀次が全試合0回の場合は、実際に観測された0として表示する。集計が取得できていない状態を対象0件や観測値0に置き換えない。

## 5. 表示と操作

### 既存画面への配置

- 「分析する」→「条件別」の「番手比較」の次へ、「オーナー比較」を同格の節として置く。目次も「番手」「オーナー」「売り場×目的地」「スリの銀次」の順にし、既存の節見出し・目次リンク・余白の文法に従う。
- ページ上部の作品・シーズン・マップ、親scopeの総戦数、最終更新、「表示を更新」を共有する。これらの表示・操作をオーナー比較内へ複製しない。
- 内容は既存の比較surface内に置く。節全体を独立したcardや淡色面で囲まず、節見出し、操作、比較結果、必要時に開く読み方の順に構成する。具体的な寸法・文字・表の表現は [UI規約](../ui-rule.md) と既存の共通部品に従う。
- オーナー別の値は親scopeとは分母が異なる条件別集計である。他の指標、振り返り、高度分析、試合詳細の通算値の集計範囲を変えず、親scopeの同じ値を再掲する欄にはしない。

### 指標の選択と読み方

- 主表示は選択中の1指標の一覧とする。節内に共通のselectを置き、現在の指標名を常に確認できるようにする。可視のラベルは省略し、accessible nameを「オーナー比較の指標」とする。候補は4節の7種類とし、平均順位を初期値とする。目的・切り口のtab階層へ指標tabを増やさない。
- 選択肢は平均順位、順位分布、平均総資産、平均物件収益、目的地到着回数（1試合平均）、銀次遭遇率、銀次遭遇回数（1試合平均）とする。既存指標と意味・単位を揃え、同じ量に別名や別の丸め方を作らない。
- 指標切替は保存済みの表示値だけを変え、scope・分母・集計時点・選択試合を変えない。切替中もcontrolとfocusを維持し、ページや節の先頭へ不意に移動させない。
- 平均・率を主表示とし、分子や合計を補助として添える。銀次遭遇率では「遭遇N戦」、平均遭遇回数では「合計N回」を対応させる。件数は「戦」、回数は「回」を使い分ける。
- 順位分布は既存の「各順位の回数」と同じ1〜4位の順序・順位表現を使い、各プレーヤー・オーナーの組合せを1本の100%構成と各順位の回数・率で示す。1位分を別の主指標として重複させない。数値をhoverや色だけで伝えない。
- 平均・率・金額・未定義値は戦績比較の共通formatterを使う。観測された0・負値を保持し、指標名と単位、率の分子、列の対象戦数を対応づける。
- 共通指標の意味は既存の「指標の読み方」に従う。オーナー節の導入説明文と専用の読み方アコーディオンは設けない。対象戦数・参考値・対象なしは表内に常時表示する。

### 一覧の軸と端末差

- 「番手比較」と同じく、行をプレーヤー、列を比較条件であるオーナーとする4×4の一覧にする。「行: プレーヤー」「列: オーナー」の軸を明示し、同じプレーヤーの行を横に読んで比較できるようにする。両軸とも既存の固定メンバー順を使う。
- 成績の主体であるプレーヤー行には既存のメンバー表示を使い、オーナー列は名前と役割で識別する。両軸を同じ強さのメンバー標識で競合させず、番手用の標識へ置き換えない。
- 本人がオーナーの組合せも通常の値を表示する。直接対決表のような「vs」表現や対角cellの除外、番手比較の「得意」「苦手」の判定は持ち込まない。順位分布以外の値を新しい有利・不利の塗り分けや自動順位づけで示さない。
- オーナーごとの対象戦数と品質は列見出しに置き、4人に共通する分母だと分かるようにする。対象0戦の列も残し、別オーナーや親scopeの値を補わない。横・縦に移動しても、値のプレーヤー名・オーナー名・件数を確認できるようにする。
- 表は共通のacademic tableの文字・横罫線・整列を使う。番手表の読み方を引き継ぐことを、枠付き・着色セルを複製する指示としない。行見出しと列見出しの対応を保ち、表内scrollはkeyboardでも利用・離脱できるようにする。
- PC・mobileで指標名、名前の順序、数値、対象範囲、分母を変えない。mobileでは1人の行に着目して4条件を読めることを優先し、全16cellを一画面に収めることは要求しない。必要な横スクロールは表内に閉じ、案内を付け、主要数値を縮小して収めない。

### 空状態と既存導線

- オーナー比較を含む表示可能な成果物があり、親scopeに1戦以上ある場合はオーナー4人の列を維持する。記録のあるオーナーが1人だけなら、集計値と4人の列に加え、「この範囲で記録があるオーナーは1人です。」と短く示す。プレーヤーが不足しているとは表現しない。
- 親scope全体が0戦なら、既存ページの「この範囲に確定済みの試合がありません」と条件を戻す導線に従う。オーナー比較だけ全0戦の表を別途表示しない。作品なし・成果物未取得・取得失敗も既存ページの状態に従う。
- オーナー別の対象試合一覧、試合詳細へのリンク、cellからのdrilldownは追加しない。既存の根拠試合への導線、ページ共通の選択試合の結果表示と戻り先は維持し、オーナー比較を開く・指標を変える操作では選択解除しない。

### 選択試合の対応表示

- 試合結果の「前後の戦績を見る」から移動したときも、ページ共通の選択試合に対応するオーナー列を示す。全7指標で、列見出しと4人全員のcellを同じ輪郭等で強調し、列見出しに「この試合のオーナー」と表示する。色だけに依存せず、オーナー本人の行だけを対象にしない。
- 隣接するcellの境界に枠を重ねず、列の外側と内側で線幅を揃える。強調の有無でcellの寸法・内容位置を変えない。
- 強調した列の値・戦数・品質はそのオーナーの試合全体の集計であり、選択試合単独の値へ置き換えない。順位分布では列を強調し、内部の特定順位には選択試合のringを付けない。
- 表示中のartifact・scope・試合に一致する有効なmatch contextだけを使う。ownerに一意に対応する列、正の対象戦数、4人分の対応cellが揃わない場合は列全体を強調しない。URLや別取得の試合詳細から対応を推測しない。
- 試合・scope・artifactの切替と解除は、選択試合表示・表・既存指標の強調と一体で行う。切替中に保護された旧表示を残す場合も、異なる試合の強調を混ぜない。初回失敗、成功済みcontextの一時失敗、404/410による無効化は[共通のWeb状態契約](series-analysis-batch.md#web-state)に従う。
- 固定見出し・行hover・横scrollでも列の対応と値を読め、指標変更でfocusやscroll位置を失わない。行・列見出しの意味を保ち、新しいcell操作やtab stop、自動scrollは追加しない。

### 別端末で同じ話題を見る

- 選択中の指標名はselectの現在値を表示上の正本とし、表のaccessible nameにも対応させる。共通の比較条件要約で作品・非既定の条件を確認し、未指定が全シーズン・全マップを意味することは既存の条件選択から確認できるようにする。既定条件や選択指標を同義の見出し・badgeへ重複表示しない。
- URLから作品・シーズン・マップ、「条件別」のオーナー比較、選択指標を復元する。節への到達は既存の目次とfragment移動、指標は既存のURL状態管理を拡張して扱う。同じURLを別端末で開く場合も、閲覧権限は既存ページに従う。
- 指標未指定時は通知せず平均順位とする。不正・未対応の指標値は平均順位へ正規化して理由を短く示し、有効なscopeを変えたり別指標の値を流用したりしない。従来のURLも有効とする。
- 指標変更ではscope、view、選択試合、安全な戻り先を保ち、fragmentをオーナー比較に対応させる。目次経由でなくスクロールして指標を選んだ場合も、そのURLから該当節へ到達できる。操作中のfocus・読んでいる位置は維持し、指標切替ごとに履歴を積み上げず既存の表示設定変更と同じ履歴置換を使う。目次移動・ページ往復からのbrowser backでは、その履歴の条件・指標・戻り位置を復元する。
- 別の切り口へ移って戻っても選択指標を保つ。作品・シーズン・マップ変更時も指標を維持し、選択試合の解除や条件の正規化は既存のscope変更規則に従う。
- URLが復元するのは比較条件と表示であり、過去の数値のsnapshotではない。結果が更新された後に開けば、その時点で表示可能な成果物を読む。
- 端末間で値が違う場合は条件・指標・共通の最終更新を確認し、既存の「表示を更新」を使う。オーナー比較専用の更新時刻・更新button・自動再集計は設けない。
- Discordへの投稿、自動通知、利用者間の選択の同期、自動再取得、共有roomは追加しない。URLは通常のブラウザのコピーで扱えればよく、専用の共有画面を必須にしない。

## 6. 更新・失敗・既存成果物

- 新機能の提供時は保存済みの過去試合も再集計し、オーナーを入力し直すことを要求しない。訂正履歴の比較は行わず、現在保存されている値を正とする。
- オーナーをAからBへ訂正した場合、再計算成功後にはその試合の4人分の結果がAの集合からBの集合へ移る。他の保存値が同じなら、親scope全体の指標値は変わらない。
- 試合の追加・削除、作品・シーズン・マップの変更も、該当する集合と分母へ反映する。あるオーナーの最後の1試合がなくなっても、親scopeに試合が残る間はその列を対象なしとして維持する。親scope全体が0戦になった場合は共通の空状態に従う。
- オーナー名・プレーヤー名は既存の表示metadata取得に従う。表示名の変更を別オーナーとして扱わず、名前から集計しない。
- オーナー比較と同時に表示する既存分析は同じ成果物を使う。更新中・失敗時の現行契約の直前成功成果物表示、新しい結果への切替、取得失敗・期限切れ時の扱いは [分析バッチ](series-analysis-batch.md#6-api--web--admin) に従う。
- 旧形式の成果物は表示しない。非互換な形式変更では [切替契約](series-analysis-batch.md#8-compatibility--release--rollback) に従い、API・Web・Workerと既存作品の再計算を揃えてから公開を再開する。

## 7. 実装に渡す境界

### 入力と計算

- 同じsnapshotから取得した保存済み `ownerMemberId` を分析入力と入力checksumに含める。同一試合の4行で一致し、参加する固定4名のいずれかであることを検証する。不明・欠落・不一致は作品の計算を失敗させ、別のオーナーへ補正しない。表示名は分類キーやchecksumに使わない。
- オーナー訂正は通常の試合更新で分析revisionと再計算要求を同時に進める。4人分が一緒に所属を移り、親scopeの指標は変わらない。専用の再計算経路や保存済み試合の再入力を要求しない。
- 既存の各scope内で4節の指標だけを一度の走査で事前計算する。集計用の領域と追加payloadは4オーナー×4プレーヤー×固定指標数に収め、オーナーごとの高度分析・振り返り・試合明細を追加しない。

### 成果物

aggregateの必須 `ownerComparison` に列、行、全7指標を保存する。構造は [aggregate schema](../schemas/series-analysis-aggregate-v5.schema.json)、計算は [owner集計](../../apps/processing-worker/crates/analysis-core/src/compute/owner.rs)、意味検証は [owner validator](../../apps/processing-worker/crates/analysis-core/src/payload/owner.rs) を確認する。

- 親scopeに試合があれば、`owners` と `rows` は既存 `players` と同じ固定4名・同じ順序とし、各行の `cells` もオーナー順の4要素にする。対象0戦の列も含め、重複・欠落・未知参照・順序違いを拒否する。
- 親scopeが0戦なら `owners: []`、`rows: []`、`recordedOwnerCount: 0` とし、必須fieldを省略しない。Webは共通の空状態を表示する。
- `owners[].targetCount` は `N_o`、`qualityStatus` は0戦で `no_target`、1〜2戦で `reference`、3戦以上で `ok`。`recordedOwnerCount` は対象があるオーナー数とする。分母と品質は列に一度だけ保存し、親scopeの `dataQuality` やreviewの品質件数へ加算しない。
- 対象0戦のcellはcountを0、平均・率を `null` とする。順位分布は1〜4位の4要素を保ち、各countは0、rateは `null`。Webは対象なしの補助countも観測値の「0回」と表示しない。
- 金額は保存単位の万円、率は0〜1の有限数とし、表示用に丸めない。整数合計のoverflowを拒否する。各平均・率は同じ整数分子と分母による除算結果に一致させ、NaN・Infinity・canonical encodingは共通成果物契約に従う。
- 意味検証は、オーナー別試合数の合計と親scope、対象ありの列数、各cellの順位件数・平均順位、同じownerの4人分の各順位件数を照合する。目的地・銀次のcountと平均、銀次の遭遇試合数と率、遭遇試合数がcountと `N_o` 以下であること、countが0と遭遇試合数が0の同値も確認する。不正な成果物は公開しない。
- 列・行のmember IDは既存metadata取得で表示名を補い、cellは `ownerMemberId` で列を参照する。cellごとのDB問合せ、drilldown用ID、根拠試合IDは追加しない。chunkの `item_count` は親scopeのプレーヤー明細数のままとする。
- 値・件数・品質はWorkerが確定する。APIは保存済み成果物の契約・checksum・上限・要求identityを検証し、Webとともにオーナー集計を再計算しない。

### HTTPと選択試合

- 全指標は一度のaggregate読取りに含める。オーナーや表示指標をAPIのscope、resource query key、ジョブへ加えない。各resourceは同じartifactに固定し、読取りのpermit・timeout・byte/node上限は分析バッチの共通契約に従う。
- includedのmatch-context HTTP応答には `match.ownerMemberId` を必須とし、excludedでは `match: null` を維持する。APIは試合所属・現在revision・保存chunkのsource revisionを照合する同じSELECTからownerを取得し、一致するsnapshotだけを使う。別取得の試合詳細や表示名から所属を推測しない。
- ownerは保存payloadのchecksum・decodeを検証した後のHTTP projectionで付加し、ID構造、参加者への所属、付加後のnode/byte上限を確認する。保存match-contextの形式は変えず、この対応表示だけのための全件再計算・promotion・DB変更は要求しない。
- HTTPの構造はTapir由来のOpenAPI・Web生成契約へ揃え、cache keyはHTTP shapeを区別する。比較画面と試合結果画面で同じ取得・無効化・失効回復を使う。確定した不存在・失効の後に古い成功contextを復活させず、その他の一時失敗は [Web状態契約](series-analysis-batch.md#web-state) に従う。
- 応答後の訂正は通常のmutation後のreset・明示更新・再訪時の取得で反映する。自動監視を追加せず、読取時点の整合性と常時最新を混同しない。
- 非互換なHTTP変更は対応するAPI/Webの組で切り替え、rollbackも同じ組で行う。開いたままの旧Webは再読込みを必要とし、旧route・decoderを恒久維持しない。保存形式の非互換変更は [分析バッチの切替契約](series-analysis-batch.md#8-compatibility--release--rollback) に従う。

### URL

`ownerMetric` が選択指標の正本で、`view=context` と `#metric-owner` でオーナー節を復元する。

| `ownerMetric` | 指標 |
| --- | --- |
| `rank.average` | 平均順位（既定） |
| `rank.distribution` | 順位分布 |
| `assets.average` | 平均総資産 |
| `revenue.average` | 平均物件収益 |
| `destination.average` | 目的地到着回数（1試合平均） |
| `ginji.encounterRate` | 銀次遭遇率 |
| `ginji.average` | 銀次遭遇回数（1試合平均） |

- 未指定は通知なく既定値にし、明示した既定値もcanonical URLでは省略する。不正値は平均順位へ正規化し、既存の条件補正通知で理由を示す。
- 指標変更は履歴置換でsearchとfragmentを一度に確定し、scope・view・`focusMatchId`・安全な `returnTo` を保持する。通信・再計算・取得中の遮蔽を起こさず、selectのfocusとページ・表内の位置を保つ。scope・viewの変更でも指標を保持し、選択試合の解除だけは既存scope変更規則に従う。
- 通常の目次移動、別端末でのURL読込み、reloadでは節へ移動する。browser backではそのvisitの保存位置と起点復帰を優先し、位置がなければ既存fragmentの復元に従う。URLは表示条件を共有し、過去の数値を固定しない。
- 表示変更の位置保持は、発行元visit・操作・正規化後のtargetを対応させた一度限りのintentで扱う。該当commitにだけ冪等に適用し、別target・POP・unmountでは失効させる。永続したhistory flagや「次の移動を抑止する」booleanにしない。続くcanonical化が新しい操作を上書きせず、指標ごとのremountやURLと同期する第二の選択stateを増やさない。

共通UIへの接続と読解は5節、必須gateは [Change Gates](../dev-rule.md#4-change-gates)、DB schema・migrationを変える場合の事前確認は `AGENTS.md` と [DB利用規約](../db-rule.md) に従う。

### 表から答えを得られることの確認

manual reviewでは、番手比較から続けてオーナー比較を読み、指定したプレーヤー・指標についてオーナーA・Bの値と分母を特定し、対象0件・観測された0・参考値を区別できるかを確認する。銀次の遭遇率と平均回数、同値、本人がオーナーのcell、記録が1オーナーだけの例も含める。値の存在だけのassertionや、16cellが画面内に収まることでは代用しない。

PC・mobileで同じ問いに答えられることを確認する。代表課題は「自分または仲間の銀次や順位をオーナー間で見比べ、値・件数を添えて会話にできる」とする。PCで選んだ条件・指標を別端末で復元し、画面共有や座標の指示に頼らず、同じ名前の指標とプレーヤーの値を特定できるかも確認する。「明確な差はない」と感じる結果でも失敗扱いにせず、差の捏造や公平性の判定へ誘導しない。

既存の「今の差」「番手比較」「スリの銀次」と行き来しても、同じ意味の数値書式・単位・参考値表示を読み替えずに済むかを確認する。指標変更によるfocusや読んでいる位置の喪失、オーナー専用の条件・更新操作の重複、親scope全体が空のときだけ違う表示経路になることも点検する。

条件を混ぜた総合平均の大小関係が条件別では逆転する架空例も使い、画面が条件を揃えた実験結果を約束していないことを点検する。これは設計上の読解確認であり、利用者に統計知識を問う試験にはしない。エージェントによる表示確認と、利用者が説明なしに読み取れた証拠は区別する。

### 手計算できる具体例

以下は説明用の架空データであり、実際の戦績ではない。作品・シーズン・マップはすべて同じとする。

| 試合 | オーナー | Aの順位 | Bの順位 | Cの順位 | Dの順位 |
| --- | --- | --- | --- | --- | --- |
| 1 | A | 1 | 2 | 3 | 4 |
| 2 | A | 3 | 1 | 4 | 2 |
| 3 | B | 4 | 3 | 2 | 1 |

| プレーヤー / オーナー | A（2戦・参考値） | B（1戦・参考値） | C（0戦・対象なし） | D（0戦・対象なし） |
| --- | --- | --- | --- | --- |
| A | 2位 | 4位 | — | — |
| B | 1.5位 | 3位 | — | — |
| C | 3.5位 | 2位 | — | — |
| D | 3位 | 1位 | — | — |

- 試合2のオーナーをAからBへ訂正すると、Aの対象が1戦、Bが2戦になる。プレーヤーAの平均はAオーナー時1.0位、Bオーナー時3.5位となり、親scope全体の平均順位は変わらない。
- あるオーナーの2試合でプレーヤーAの銀次回数が0回・3回なら、合計3回、1試合あたり1.5回、遭遇1試合、遭遇率50%となる。遭遇率を150%とはせず、遭遇した試合だけを分母にして1試合あたり3回とも表示しない。
- 同じ2試合の目的地回数が0回・2回なら平均1回、総資産が-100万円・300万円なら平均100万円となる。
