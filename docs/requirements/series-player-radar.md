# プレーヤーレーダー比較 要求仕様

状態: 要求確定（2026-09-29）。利用者が「目的地なしの6軸」「現時点で基準を作る」を採用した。作品共通の固定基準で、各観点の成績と得点の揃い方から万能性を読む。総合点・平均点・総合順位は算出も表示もしない。機能実装・公開は未実施。

対象: 本実装は [MOM-29](https://linear.app/ponta/issue/MOM-29)。先行検討・試作・プロダクトレビューの記録は [MOM-30](https://linear.app/ponta/issue/MOM-30)。戦績比較の追加機能として扱う。

## 1. 目的と確定要求

- 複数の観点でプレーヤーの成績を点数化し、レーダーチャートで各人の特徴を比較できるようにする。
- 各軸で成績の強み・弱みと、幅広い観点で好成績を残せているかという万能性を比較する。各軸は外側ほど良い成績を表す。均等に低い点数の図を、万能性が高いと評価しない。
- システムは軸点の合計・平均・重み付き合成値・総合順位を計算、保存、表示しない。必要な利用者は数値表から自分で計算する。万能性の指数や図形の面積で代替の総合点を作らない。強さの順位づけを行うレーティングは別の検討事項とし、このレーダーの受入条件にしない。
- 平均順位、物件収益のP90・平均、総資産のP10・中央値・P90の6軸を採用する。全試合の平均的な成績だけでなく、普段・低い側・高い側の特徴を読む。
- 保存済みの順位・総資産・物件収益から算出する。OCRで得られる結果情報を超える新たな試合中の事実は、今回のために取得しない。
- 作品内の固定4人を比較し、シーズン・マップで絞り込めるようにする。
- 採点の閾値は作品ごとの記録から自動計算し、作品内で共通にする。マップを絞っても同じ指標値は同じ点数にする。シーズン・マップの絞り込みへの対応と、採点基準の単位は分けて扱う。
- 目的地は戦略によって選ばない場合があるため、得点軸にしない。銀次・条件付き成績も初版のレーダーと追加の補助表には含めず、既存の詳細分析を維持する。
- 初回基準は候補計算時点に存在する、その作品の全シーズン・全マップの確定記録から作る。試作の冬までの記録へ固定せず、3・4節に定める採用方式を使う。
- 閾値は毎回の集計では更新しない。管理者が必要なタイミングで計算・更新できるようにする。
- 固定基準に対して好成績を伸ばし、満点を含む特徴的な形を表せるようにする。一方、満点が容易になりすぎたときは基準を見直せるようにする。
- 満点は基準作成時の記録に照らしてかなり好成績な水準とする。達成者がいない軸も許容し、各軸で4人の誰かを必ず満点にしない。理論上の最高成績だけを満点にする要求でもない。
- 基準更新後は過去シーズンも新基準で採点し、使用基準を表示する。過去に見た点数が変わることを許容し、初版では当時の点数への切替を要求しない。
- 各軸を1〜10点で表示し、4人分を同じ軸・目盛りで個別に並べる。軸別の点数と元の成績を数値表でも照合できるようにする。
- 対象なし・少数例・基準不足は各軸で区別する。採点できない軸がある人や条件でも、ほかの採点可能な軸と元の成績は読めるようにする。
- システムが4節の基準見直しの目安を表示し、管理者が基準候補の計算、変更前後の確認、適用を行う。目安に達しただけでは基準を自動変更しない。

## 2. 既存機能との境界

| 関心事 | 正本・前提 |
| --- | --- |
| レーダーの目的、評価指標、採点、基準の更新 | 本書 |
| 固定4人、作品・シーズン・マップ、確定試合、金額・順位の意味 | [戦績比較](series-comparison.md)、[ドメインルール](../domain-rule.md) |
| 非同期計算、成果物の一括公開、状態、権限、互換性 | [分析バッチ](series-analysis-batch.md) |
| 画面の共通要件、品質証拠、変更gate | [UI規約](../ui-rule.md)、[テスト・品質規約](../test-rule.md)、[開発作業規約](../dev-rule.md) |
| 保存形式、API、成果物の構造 | 実装時にmomo-db、Tapir、JSON Schemaで定義する |

現在の分析入力には、各試合の4人分の順位・総資産・物件収益・事件簿6項目と、開催・作品・シーズン・マップ・オーナー・番手がある。事件簿は目的地、プラス駅、マイナス駅、カード駅、カード売り場、スリの銀次の回数である。

カードの種類・使用順、移動経路、購入機会、銀次に遭遇する機会の総数は記録していない。保存値から新たな行動ログを推定したり、事件簿の合計を総行動回数に見立てたりしない。

既存の試合追加・訂正・削除による分析更新と、今回追加する採点基準の更新は別の意味を持つ。通常の分析更新で採点基準を暗黙に作り直さない。

初版では、重ね描き、利用者による軸・重み・閾値の編集、過去基準への表示切替、作品間ランキングを追加しない。レーダーに採用しない指標のために新しい詳細画面を一通り作ることも、今回の必須範囲には含めない。既存の詳細分析で読める指標は、その場所を利用する。

## 3. 採用する6軸

最上部から時計回りに次の順序へ固定する。絞り込み・作品・プレーヤーごとに軸を入れ替えない。

| 順序 | 軸 | 元の指標・意味 |
| --- | --- | --- |
| 1 | 平均順位 | 保存済み順位の合計 / 対象試合数。小さいほど良い |
| 2 | 物件収益のP90 | 大きな収益を得た側の境界。最高額ではない |
| 3 | 平均物件収益 | 対象試合の物件収益の合計 / 対象試合数。大きな収益の試合も影響する |
| 4 | 総資産のP10 | 残した資産が低い側の境界。3・4位だった試合だけの値ではない |
| 5 | 総資産の中央値 | 全試合の真ん中の水準。偶数件では中央2値の平均 |
| 6 | 総資産のP90 | 大きく資産を残せた側の境界。勝利した試合だけの値ではない |

金額の5軸は大きいほど良い。負の総資産と観測値0を保持する。P10・中央値・P90は、小さい順に並べた値の位置 `(n - 1) × p` を線形補間した分位点とし、`p` はそれぞれ0.1・0.5・0.9とする。最低額・最高額や、その範囲の試合の平均ではない。ばらつきの小ささ自体を高評価にせず、低い側でも残せた資産額の水準を評価する。

すべての軸で選択条件に該当する確定試合を使う。「目的地なし」は目的地を得点軸にしない意味であり、目的地到着0回の試合だけに絞る意味ではない。元の指標は選択した全試合から集計し、採点基準を作る20試合窓と混同しない。

6軸は順位1軸・収益2軸・資産3軸であり、6つの独立した能力ではない。収益の平均とP90は全試合の水準と高い側の成績を、資産の3軸は低い側・真ん中・高い側を読むために残す。相関がある軸を含むことを承知した構成であり、図の面積・形からゲーム全体の能力、戦略の巧拙、次戦の勝ちやすさを断定しない。

目的地、銀次、勝率や前戦下位からの入賞などの条件付き指標、最高額を用いる別案は初版へ持ち込まない。銀次遭遇後の実際の回復過程は記録されておらず、遭遇試合の最終成績を回復量・回復速度とは呼ばない。検討経緯と不採用理由はMOM-30へ残す。

## 4. 採点基準の作成・更新

- 採点基準を作品共通の保存済みデータとして持ち、各人の集計値をその基準で採点する。
- 比較中の4人の最大・最小値だけから点数を引き伸ばす方法は避ける。表示中のscopeからその都度閾値を生成せず、その作品の保存済み基準を選ぶ。マップの選択や追加によって別の基準へ自動で切り替えない。
- 基準作成には、採点対象と同じ意味の集計値を使う。例えば、1試合の金額分布と複数試合の平均金額分布を混同しない。
- 基準候補の計算、変更前後の閾値・点数の確認、適用を区別する。候補計算だけで現行表示を変えない。
- 基準の識別子、対象作品、軸構成・指標定義、計算方法、元にした記録の範囲、作成・適用時点を追跡できるようにする。
- 基準更新後の点数と基準を一緒に公開する。候補計算中や失敗で、公開中の基準・点数を部分的に置き換えない。
- 満点の出現だけを不具合や更新理由にしない。本節の見直しの目安を使う。

### 作成対象と集計窓

初回・更新とも、候補計算時点の対象作品の全シーズン・全マップの確定試合を、一貫した記録集合として固定する。「現時点」は候補を計算する時点を指し、画面を開くたびに基準を作り直す意味ではない。試作時の取得日時・冬の終了日・閾値の実測値を本番へ埋め込まない。

基準作成には40試合以上かつ8開催以上を必要とする。4人分を4試合と数えず、試合・開催の重複を除いた件数を使う。作品がこの条件を満たさない場合は基準未作成とし、不足件数と元の集計値を表示する。他作品の基準で補わない。

[戦績比較の対戦順](series-comparison.md#2-data--scope-invariants)に従って並べ、連続する20試合を1試合ずつ進めて集計する。各窓で4人それぞれの6指標を計算し、軸ごとに全窓・全員の値を同じ重みで集める。N試合なら各軸に `4 × (N - 19)` 個の集計値ができる。重複する窓と同じ4人の反復値であり、独立した多数の人の標本とは扱わない。

窓はシーズン・開催・マップの境界でも切り直さない。窓幅と移動幅を保存し、利用者が編集する設定にはしない。評価対象は選択条件の全試合とし、直近20試合に限定しない。

全マップ・個別マップ・新規マップに同じ作品共通基準を使う。全マップでは対象試合の元指標を改めて集計し、マップ別の点数を平均しない。マップ構成の違いも成績に影響するため、対象期間とマップ別件数へ到達できるようにする。構成差を上達と断定せず、マップ比率の補正は加えない。作品間の同点も同じ強さとは扱わない。

### 閾値と採点式

試作の「分布の幅から満点を延ばす」方式（`spread`）を採用する。軸の集計値を、平均順位は符号反転、金額はそのままとして、良いほど大きい向きへ揃える。この向きの基準作成用分布のP10・中央値・P90を `q10`・`c`・`q90` とする。分位点の補間は3節と同じ規則を使う。

`q10 < c < q90` が成立しなければ、その軸は分布から基準を作れないと示す。任意の幅・前回値・固定点で補わない。6軸すべての有効な境界を作れた候補だけを適用可能にし、失敗時は現行基準を維持する。初回も一部の軸だけを暗黙に適用しない。

- 下側の幅 `L = c - q10`、上側の幅 `U = q90 - c` とする。
- 平均順位は1位が最良なので、符号反転後の上限は `-1`。この軸だけ `U = min(U, (-1 - c) / 1.6)` とし、10点が理論上到達不能になることを防ぐ。
- 2〜10点へ上がる各境界を、`s < 6` なら `T_s = c + (s - 6) / 2.5 × L`、`s >= 6` なら `T_s = c + (s - 6) / 2.5 × U` で作る。
- 採点対象の同じ向きの値を `y` として、点数は `1 +（y >= T_s を満たす境界の個数）`。境界と同値なら高い点数を付け、結果は1〜10の整数になる。表示用の丸めは判定に使わない。

中央値は6点の下限、10点の下限は `c + 1.6 × U`。基準作成時の最高値を超えてもよく、4人の誰かを必ず満点にしない。たとえば金額軸の `q10=100、c=200、q90=300` なら6点の下限は200、10点の下限は360となる。

元の値・単位に戻した各境界と、元の記録範囲・件数、指標定義・採点方式の版を保存し、確認できるようにする。更新で変えるのは生成した基準の値であり、この式・窓幅・件数規則の変更は計算方法の版変更として扱う。

### 採点対象の件数と品質

全6軸で選択条件に該当する試合数と、その試合の開催数を使う。基準作成の件数と、表示対象の件数を別々に示す。

| 対象の記録 | 各軸の表示 |
| --- | --- |
| 0試合 | 対象なし。元の値・点数とも出さない |
| 1〜2試合 | 元の値と件数のみ。点数は件数不足で未採点 |
| 3試合以上で、40試合未満または8開催未満 | 有効な基準があれば採点し、その軸に「参考」と表示する |
| 40試合以上かつ8開催以上 | 有効な基準で採点し、通常表示する |
| 適用できる基準なし | 件数にかかわらず元の値・件数を表示し、点数は基準未作成等の理由を示す |

観測値0・負値は件数不足や欠測にしない。複数の不足条件があれば、対象件数と基準の状態をどちらも確認できるようにする。参考条件を満たさなくなっても統計的に安定したという保証にはしない。P10/P90が少数例で最低額・最高額に近づくことを説明する。

### 管理者の操作

1. 管理画面で対象作品の適用中の基準、作成時の記録範囲・件数、見直しの目安を確認する。
2. 管理者が基準候補の計算を依頼する。初回は基準未作成として扱い、必要件数を満たさなければ不足条件を示す。
3. 計算後、同じ評価対象記録での4人の各軸点数の変化、採点できなくなる軸とその理由、適用範囲を確認する。詳細で各閾値と算出方法を照合できるようにする。初回は変更前の点数を作らない。
4. 管理者が候補の適用を依頼する。候補を作っただけでは適用しない。数値を直接手入力する閾値編集は初版の対象にしない。
5. その基準を使った対象作品の必要なscopeを計算し、成功した点数と基準を一緒に公開する。受付・計算中・適用済み・失敗を区別する。

候補を作る記録集合と、変更前後を比べる評価対象記録を保存し、それぞれの時点・範囲・件数を示す。変更前後は基準の違い以外の入力を揃え、「採点基準の変更による差」として示す。確認後の変更は次のように扱う。

| 確認後の変更 | 必要な対応 |
| --- | --- |
| 候補作成元の集合に含まれない試合の追加 | 保存済みの候補を維持する。追加があったことを示し、最新の記録で変更前後の比較を更新して再確認する。追加のたびに候補の閾値を作り直さない |
| 候補作成元の試合の削除、成績・所属・対戦順等の計算に影響する訂正 | 影響を受ける候補を無効にし、理由を示して作り直す |
| 評価対象だけに含まれる試合の訂正・削除 | 候補の閾値を維持し、比較結果を更新して再確認する |
| 軸・指標定義・採点方式・適用範囲の変更 | 候補を無効にし、変更後の定義で作り直す |
| 別の管理操作で適用中の基準が変更された | 互換性を確認し、現在の基準との比較を更新して再確認する |

計算に影響しない表示名等の変更は、候補の無効化理由にしない。適用の受付時には確認した比較結果が現在も有効かを検証し、二重操作や再送で同じ候補を重複適用しない。受付後の試合追加は、新基準による分析更新へ引き継ぐ。記録が増えるたびに承認済みの適用をやり直す必要はない。一方、公開までに作成元の訂正や定義変更等で候補が無効になった場合は、適用を止めて旧基準を維持し、再確認が必要な理由を示す。

画面を離れても処理・候補・確認状態を失わず、管理画面へ戻って続けられるようにする。未適用の候補は取り下げられ、公開中の基準と点数を維持できる。通信失敗時は処理状態を確認してから再試行する。適用後に直前の基準へ戻す場合も、現在の定義との互換性と作成元記録の有効性を確認し、同じ比較・適用手順で現在の記録を再採点する。試合記録そのものは巻き戻さない。

直前基準へ戻すための比較を開いたことや、その操作を取り消したことでは適用中の基準を変えない。候補の閲覧・選択、適用の受付、公開済みの状態を別々に示し、閲覧している候補を適用中と呼ばない。取消後・再読込後・別作品から戻った後も、管理欄の基準名と公開結果の来歴が一致することを確認する。

計算中・失敗時は直前に成功した基準と点数を維持する。一度も基準作成に成功していなければ採点値を出さず、既存の戦績比較は継続して利用できるようにする。権限・非同期実行・部分公開の禁止は [分析バッチ](series-analysis-batch.md) に従う。

### 見直しの目安

見直しは作品共通基準ごとに、全マップを合わせた記録で判断する。選択中のシーズン・マップで監視範囲を変えない。満点付近への集中は次の規則で確認する。

1. 基準作成元の最終試合より後の対戦順にある確定試合を、20試合ずつ重複なく区切る。端数は次の区間へ繰り越す。作成元の試合と、それ以前へ追加した過去の試合は新しい期間の判定へ含めない。
2. 各区間の4人の6指標を適用中の固定基準で採点する。直近の完成済み2区間（40試合）が8開催以上にわたる場合に、同じ軸で「4人中3人以上が9点以上」が両区間とも成立すれば見直しの目安とする。該当軸・対象期間・件数を表示する。
3. 2区間または8開催に満たなければ、判断に必要な追加記録が不足と示す。1人の好成績、単発の満点、異なる軸で1回ずつ起きた高得点では提案しない。20試合区間の点数は監視用であり、通常画面の「参考」を解除する根拠にしない。
4. 基準・対象試合の識別子と計算に影響する版・該当理由を根拠として保存する。「今の基準を継続する」を選んだ同一根拠は新しい提案として再表示しない。次の20試合区間の完成、対象記録の訂正・削除、基準変更で根拠が変われば再評価する。端数の通常追加だけでは再提案しない。

新基準を適用したら、その基準の作成元から監視期間を定め直す。直前基準の再適用時も、その基準の元の作成範囲を使う。見直しの判断のために新しい閾値を毎回生成せず、自動変更や自動適用もしない。

基準未作成の作品が40試合・8開催に達したこと、作成元の計算に影響する訂正・削除、作成元にないマップの確定記録の追加も、別の確認理由として管理者へ示す。同じ理由・記録状態を繰り返し通知しない。作品共通基準なので新規マップにも同じ基準を使い、記録訂正後も管理者の適用までは保存済み閾値を維持する。

目安は管理画面の補助情報であり、更新の強制や通常比較画面の繰り返す警告にはしない。基準作成元の訂正等による確認事項と、満点付近への集中による任意の見直しは区別する。

基準の計算方法自体を変更する場合は、単なる再採点と区別して指標・採点方法の版を進める。基準の適用範囲や軸定義との互換性を確認せず、古い閾値へ新しい意味を与えない。

### 更新後の過去期間

過去シーズンも現在適用中の基準で採点することは確定要求とする。新しい基準と、その基準で採点した過去・現在の各scopeを一組として表示する。元の記録が同じでも基準変更で点数が変わり得るため、使用した基準、基準の適用範囲、元の指標値を確認できるようにする。画面では基準の適用日・対象範囲を読める名前で示し、内部の識別子だけを見せない。基準変更による差を成績の向上・低下として扱わない。

基準の版と指標の計算方法の版は区別する。試合の追加で更新される分析入力の版を、採点基準の版として扱わない。通常の作品再計算や画面の表示更新を、採点基準の見直し操作に読み替えない。

### 分析成果物との接続

基準の識別子・内容を計算入力と成果物の来歴に含める。同じ試合入力・algorithm versionであっても、採点基準が異なる結果を同じ再利用対象として扱わない。基準変更で結果が変わったことを、既存の非決定性検出で誤判定しない契約にする。

API・Webで各軸の採点、見直し目安を補完計算しない。基準切替前の計算が遅れて完了しても、異なる基準の点数を現在のものとして公開しない。計算中に旧結果を表示する場合は、その結果の基準表示も維持する。具体的な保存形式・versionの接続は実装設計で定義し、[分析バッチ](series-analysis-batch.md) の公開・再利用・互換性の契約へ反映する。

## 5. 採用判断と実装への引継ぎ

利用者が実データの試作を確認し、2026-09-29に目的地なしの6軸と、現時点の全記録で基準を作る方式を採用した。作品共通、分布幅を使う採点式、20試合窓、件数・参考表示の条件は4節を初版の契約とする。これらは試作を踏まえた製品上の設定であり、統計的な有意差や将来の安定性を保証する数値ではない。

試作では候補比較、時期を分けた採点、窓幅・開催除外の感度、PC・mobile相当の表示、対象なし・参考・基準不足、模擬管理操作を確認した。同じ4人・同じ記録を繰り返し参照しており、完全に未見の検証データとは扱わない。採用の合意と、利用者の読解テスト・本番処理の検証は区別する。

本実装ではP10/P90の意味、同じ軸の4人比較、参考・未採点、基準変更による点数差を説明なしでも読み取れるかを確認する。キーボード・タッチ・支援技術で数値と根拠へ到達できること、管理者が計算・比較・適用を取り違えず、失敗や取消から戻れることを検証する。試作の成功を本番の認可・保存・非同期処理・公開の証拠にはしない。

検討・レビューの記録は [MOM-30](https://linear.app/ponta/issue/MOM-30) に集約する。試作の別案・感度分析・模擬管理コード・結果形式を本番の依存やAPIとして残さず、採用した指標・点数・品質・根拠だけを既存の分析成果物へ接続する。実データと試算値を公開文書へ含めない。

## 6. 表示と読み方

### 比較への入口と情報の順序

既存の戦績比較「今の差」に「プレーヤーレーダー」の区画を置く。比較条件と対象試合数、4人のレーダー、数値による内訳、算出方法の順に読める構成とする。比較のためだけに新しい全体ナビゲーションや独立した設定画面を作らない。

作品・シーズン・マップ、使用基準の適用日・対象範囲、参考値など判断に必要な状態は、方法説明を開かなくても分かるようにする。詳細へ移動して戻っても、既存のURL復元・focusの規則に従って比較条件と読み位置を維持する。集計全体の点数に、特定の1試合だけで説明できるような目印を付けない。

通常の比較を先に表示し、軸の意味・採点根拠へ進める。過去の軸案、採点方式・基準作成期間の選択、感度診断、管理操作の模擬状態を一般利用者の設定へ持ち込まない。実際の基準管理は管理者の操作として分ける。

### レーダーと数値表

- 各軸は1〜10の整数点とし、4人に共通の軸順・向き・大きさ・尺度・適用基準で個別に表示する。中心を0、外周を10に固定する。0は作図上の基点であり、採点結果や欠測の代用値にはしない。
- 軸順と4人の並び順を固定する。点数順で軸を並べ替えたり、成績の変化に応じてプレーヤーの表示位置を動かしたりしない。
- 点と線で各軸の値を読み取れるようにし、平滑化や塗り面積の大きさで優劣を伝えない。広い画面では4人を並べ、狭い画面では1人ずつ読める配置にする。
- 「数値で比較」から、同じ軸の4人分の点数・品質を一度に照合できる表に到達できるようにする。mobileでも前の人の値を記憶して比較するだけの構成にしない。行・列見出しで軸とプレーヤーの対応を示し、必要なスクロールは表内に収める。
- 各軸から元の指標値、単位、分母、採点の境界、算出方法へたどれるようにする。キーボード・タッチ・支援技術で同じ情報へ到達でき、hoverだけに値や注意を置かない。色だけで名前・値・品質を区別しない。
- 参考値は該当する軸の文字と点・線の描き方で区別する。「参考値を含む」という全体注記だけに頼らない。図のテキスト表現からも各軸の点数・未採点・参考の区別を確認できるようにする。
- 基準の境界判定は4節の規則で表示用に丸める前の値に対して行い、原指標と点数を同じ値として扱わない。
- 点数は指標を段階に分けたものであり、異なる軸の1点差を等しい能力差・等しい改善量として読ませない。同点の中にも元の値の差があり、1点・10点を超える差は図から読めないため元の値を確認できるようにする。
- 狭い画面で表を収めるためだけに文字を極端に小さくしない。必要な横スクロールを表内に留め、行見出しと列見出しを保って比較できるようにする。
- グラフに描けない軸を0点や中間点で埋めず、欠けた頂点をまたいで閉じた図形を作らない。軸ごとの値と理由は数値表で確認できるようにする。

### 合算・順位づけをしない

各人のレーダーと数値表に軸別の点数・品質・元の値を示す。グラフの上下、比較表、管理者の基準変更前後、保存する分析結果を含め、軸点を合算した点数や総合順位を作らない。利用者が自分で計算することは妨げず、システムに合算の切替や任意の重み設定を追加しない。

採点できない軸は欠けた状態で理由を示し、ほかの軸は表示を続ける。ある人の1軸が未採点であることを理由に、4人の利用可能な軸を隠さない。管理者の基準変更前後は、同じ記録の各軸点を比較する。

### 表示できないとき・更新中

| 状態 | 利用者に伝えること・できること |
| --- | --- |
| 対象試合なし | 選択条件に試合がない。比較条件を変更できる |
| 件数不足 | 該当軸の対象試合数・開催数と不足理由。範囲を広げる選択肢がある場合は条件変更へ進める。観測値0やシステム障害として扱わない |
| 基準未作成・適用できる基準なし | その範囲はまだ採点できない。既存の集計値は読める。管理者には作成条件と操作への入口を示す |
| 更新中・更新失敗、以前の結果あり | 直前の結果とその基準・時点を示し、最新結果との違いを明確にする。既存の訂正済み試合に対する古い分析の非表示規則は維持する |
| 更新失敗、以前の結果なし | 採点結果を出さず、状態と次に取れる操作を示す。再読込・再試行は既存の権限と更新の規則に従う |

少数例や基準未作成は通常起こる状態として示し、エラーの強調を乱用しない。表示の読み方に内部用語のscope・artifact・versionを要求しない。

有効なシーズンとマップの組み合わせに記録がなければ、その条件を保ったまま対象0件を示す。別の試合集合へ黙って置き換えず、全記録などへ戻る操作を用意する。無効なURL指定を既定値へ正規化した場合は、その理由と現在の条件を示す。戻る・進むで比較条件を復元し、条件変更の結果件数を支援技術へ通知する。

## 9. 設計上の根拠

- 総合指標は、同じ重みでも軸の選び方で実質的な重みが変わり、重複や集約方法によって順位が変わり得る。今回、合算と総合順位を対象から外し、軸別比較へ絞った判断の参考とする。[OECD・EU・JRC『Handbook on Constructing Composite Indicators』](https://www.oecd.org/en/publications/handbook-on-constructing-composite-indicators-methodology-and-user-guide_9789264043466-en.html)
- レーダーの面積は軸の並び順に依存する。軸順を固定し、面積を万能性の数値や強さの順位に変換しない。[Duanら, 2023](https://pure.johnshopkins.edu/en/publications/origami-plot-a-novel-multivariate-data-visualization-tool-that-im/)
- グラフの内容には利用できるテキスト表現も必要である。同じ値を表で照合できる要件へ適用する。[W3C WAI: Complex Images](https://www.w3.org/WAI/tutorials/images/complex/)
- 状態の可視化、記憶に頼らない比較、取消・復帰、必要な情報から詳細へ進む構成を採用する。[Nielsenの10原則](https://www.nngroup.com/articles/ten-usability-heuristics/)、[Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)
- 少数例や未作成などの通常状態を重大なエラーのように示さない。[NN/g: Hostile Patterns in Error Messages](https://www.nngroup.com/articles/hostile-error-messages/)

本機能への具体的な適用は本書の設計判断である。これらの資料だけで、適切な軸数・必要件数・閾値が実証されたとは扱わない。

敵対的レビューの所見・試作の修正・検証の限界は [MOM-30](https://linear.app/ponta/issue/MOM-30) に残す。仕様の正本は本書とし、レビュー記録を別の実装契約にはしない。
